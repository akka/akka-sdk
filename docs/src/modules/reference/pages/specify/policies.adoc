= Policies

Organizations govern spec-driven development with *policy as code* — a version-controlled definition of the mandatory floor every project inherits: which xref:sdk:enforced-mode.adoc#exit-conditions[exit conditions] are required, which mode is allowed, what "ship" does, and the toolchain to use. Developers can tighten the floor, never loosen it.

== The governance repository

The policy lives in the organization's own git repository, by convention named:

[source]
----
<source-provider>/<org>/akka-specify-governance
----

For example, `github.com/manulife/akka-specify-governance`. The repository is provider-agnostic (GitHub, GitLab, Bitbucket, or an enterprise-hosted server) and is governed by the organization's own access controls — private repository, SSO, RBAC, branch protection, and optionally signed tags. Akka does not host it.

In v1 the governance repository *is* the source of truth: the organization owns the whole chain, and no Akka platform service is required.

== Repository layout

The repository needs one required file and one recommended one:

[source]
----
akka-specify-governance/
├── policy.yaml            # required — the org floor (schema below)
└── .github/workflows/     # recommended — CI that enforces the floor
    └── conformance.yml
----

`policy.yaml`:: The single source of truth for the floor, at the repository root. `/akka:setup` fetches this file; its schema is described below.
CI workflow:: A pipeline that runs the Akka conformance check against `policy.yaml`. Because a developer can bypass local checks, the organization's own CI is the enforcement backstop — the gate a change must pass to merge or ship. Use the `.github/workflows/` directory on GitHub, or the equivalent for your provider.

== Governance levels

Each condition in the policy is assigned a *governance level* — a clean 2×2 of default state (on or off) and developer configurability (locked or configurable):

[cols="1,3"]
|===
| Level | Meaning

| `always-apply`
| On, locked. The condition always applies; a developer may add stricter conditions but cannot strike it.

| `never-apply`
| Off, locked. The condition never applies and a developer cannot enable it.

| `on-but-dev-configurable`
| On by default; a developer may strike it, and the strike is recorded.

| `off-but-dev-configurable`
| Off by default; a developer may opt in.
|===

Only the two locked levels always win. Where the policy is silent, the platform-intrinsic conditions and the recommended-default library fill in. The floor is a floor, not a ceiling: it constrains only in the stricter direction.

== What a policy defines

Alongside conditions and their levels, a policy sets:

* the allowed conformance mode(s) and whether the mode is locked (see xref:reference:specify/mode.adoc[`/akka:mode`]);
* the *ship definition* — the organization-authored terminal action(s) and the conditions that must be green before ship fires (see xref:sdk:enforced-mode.adoc#shipping[Shipping and receipts]);
* waiver rules — whether waivers are allowed, and whether they require approval;
* the toolchain pin — the approved Akka CLI, plugin, and SDK versions.

== Exit conditions in a policy

Each entry under `exit_conditions` is one of two things:

*Adopt a library condition* -- reference an existing condition from the xref:reference:specify/default-library.adoc[default library] by its `id` and set its governance level (and any parameters). The id is how Akka Specify knows the entry is an exit condition: it resolves the id back to the library, which already defines the condition's type, `pass` predicate, and auditor, and applies it to every project the policy governs.

[source,yaml]
----
- ref: PROJ-SCAN-SAST-CLEAN        # an id from the default library
  level: ALWAYS-APPLY
- ref: PROJ-TEST-COVERAGE
  level: ON-BUT-DEV-CONFIGURABLE
  params: { min_line_coverage: 0.80 }
----

*Define a corporate condition* -- to require something the library does not cover, declare a new condition inline with its own `id` and the fields the tooling needs to check it: the `dod_type` it belongs to, the `invariant` in business terms, the binary `pass` predicate, the `signal`/`probe` its auditor uses, and its `autonomy` (for example `human-signoff`). This is how a new organization-specific exit condition is created and added to projects.

[source,yaml]
----
- id: CORP-DATA-RESIDENCY-EU       # a new corporate condition
  level: ALWAYS-APPLY
  tier: product
  dod_type: security-compliance
  invariant: "customer PII is stored only in EU-region datastores"
  pass: "count(pii_entities where region not startswith 'eu-') == 0"
  autonomy: human-signoff
----

See the xref:reference:specify/exit-condition-schema.adoc[exit condition schema] for the full field set, and the xref:reference:specify/default-library.adoc[default library] for the adoptable ids.

== Example policy.yaml

A representative floor. Adopt library conditions by `ref`, set each one's governance level, and define corporate conditions inline within a type:

[source,yaml]
----
apiVersion: akka-specify/v1
kind: OrgPolicy
org: manulife
version: 3                     # bump on every change; pinned into .akka/policy.lock

mode:
  default: enforced            # enforced | a-la-carte
  allowed: [enforced]
  locked: true                 # developers cannot drop out of Enforced

ship:                          # org-authored terminal action(s)
  steps:
    - name: push-to-governed-repo
      action: "git push origin release"
  in_scope_auditor_tiers: [product-local, project, process]
  emit_receipt: true

toolchain:
  akka_cli: "3.0.65"           # approved version; drift triggers /akka:setup
  locked: true

exit_conditions:
  # Adopt and lock library conditions by id
  - ref: PROJ-SCAN-SAST-CLEAN
    level: ALWAYS-APPLY
  - ref: SEC-SECRETS-NOT-COMMITTED
    level: ALWAYS-APPLY
  - ref: PROJ-TEST-COVERAGE
    level: ON-BUT-DEV-CONFIGURABLE
    params: { min_line_coverage: 0.80 }
  # A corporate condition, defined inline within a type
  - id: CORP-DATA-RESIDENCY-EU
    level: ALWAYS-APPLY
    tier: product
    dod_type: security-compliance
    invariant: "customer PII is stored only in EU-region datastores"
    pass: "count(pii_entities where region not startswith 'eu-') == 0"
    autonomy: human-signoff

completion_policy:
  default_preset: all-must-pass          # confidence-pass | percent-threshold | all-must-pass
  human_review_required_for: [security-compliance, data-integrity]

waivers:
  allowed: true
  require_approval_for: [ALWAYS-APPLY]   # locked-condition waivers need approval
  default_expiry_days: 30
  approvers: ["@manulife/platform-governance"]

rollout:
  mode: warn-then-enforce                # newly-locked conditions don't turn projects red overnight
  enforce_after: "2026-09-01"
----

== How a project sources the floor

`/akka:setup` resolves the policy for a project:

. Fetch the organization's governance repository at a pinned ref and, if signed tags are used, verify them.
. Merge the layers — organization floor, then project, then developer additions — applying locks.
. Materialize the result: the Enforced command surface, the MCP configuration, and the default conditions with their lock state.
. Write a resolved `.akka/policy.lock` recording the repository URL and commit SHA the project is bound to.

Because the floor is pulled live rather than vendored, a new project always gets the current policy, never a stale template.

== Drift and enforcement

The locked policy version participates in the xref:sdk:enforced-mode.adoc#dod-types[Environment & Dependencies] drift check: when the organization publishes a new floor, the project's `.akka/policy.lock` becomes stale, the condition goes red, and the fix is to re-run `/akka:setup` (subject to a warn-then-enforce grace period so a newly locked condition does not turn every in-flight project red overnight).

The enforcement backstop is the *organization's own CI*, which reads the same repository and fails the build if the floor is not met. The local CLI is advisory and guided; CI is the gate — the same way enterprises already enforce standards. You can bypass checks locally, but you cannot merge or ship past CI.
