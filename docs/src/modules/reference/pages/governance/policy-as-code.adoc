= Policy as code

Organizations govern spec-driven development with *policy as code* — a version-controlled definition of the mandatory floor every project inherits: which xref:sdk:enforced-mode.adoc#exit-conditions[exit conditions] are required, which mode is allowed, what "ship" does, and the toolchain to use. Developers can tighten the floor, never loosen it.

== The governance repository

The policy lives in the organization's own git repository, by convention named:

[source]
----
<source-provider>/<org>/akka-specify-governance
----

For example, `github.com/manulife/akka-specify-governance`. The repository is provider-agnostic (GitHub, GitLab, Bitbucket, or an enterprise-hosted server) and is governed by the organization's own access controls — private repository, SSO, RBAC, branch protection, and optionally signed tags. Akka does not host it.

In v1 the governance repository *is* the source of truth: the organization owns the whole chain, and no Akka platform service is required.

== Governance levels

Each condition in the policy is assigned a *governance level* — a clean 2×2 of default state (on or off) and developer configurability (locked or configurable):

[cols="1,3"]
|===
| Level | Meaning

| `always-apply`
| On, locked. The condition always applies; a developer may add stricter conditions but cannot strike it.

| `never-apply`
| Off, locked. The condition never applies and a developer cannot enable it.

| `on-but-dev-configurable`
| On by default; a developer may strike it, and the strike is recorded.

| `off-but-dev-configurable`
| Off by default; a developer may opt in.
|===

Only the two locked levels always win. Where the policy is silent, the platform-intrinsic conditions and the recommended-default library fill in. The floor is a floor, not a ceiling: it constrains only in the stricter direction.

== What a policy defines

Alongside conditions and their levels, a policy sets:

* the allowed conformance mode(s) and whether the mode is locked (see xref:reference:specify/mode.adoc[`/akka:mode`]);
* the *ship definition* — the organization-authored terminal action(s) and the conditions that must be green before ship fires (see xref:sdk:enforced-mode.adoc#shipping[Shipping and receipts]);
* waiver rules — whether waivers are allowed, and whether they require approval;
* the toolchain pin — the approved Akka CLI, plugin, and SDK versions.

== How a project sources the floor

`/akka:setup` resolves the policy for a project:

. Fetch the organization's governance repository at a pinned ref and, if signed tags are used, verify them.
. Merge the layers — organization floor, then project, then developer additions — applying locks.
. Materialize the result: the Enforced command surface, the MCP configuration, and the default conditions with their lock state.
. Write a resolved `.akka/policy.lock` recording the repository URL and commit SHA the project is bound to.

Because the floor is pulled live rather than vendored, a new project always gets the current policy, never a stale template.

== Drift and enforcement

The locked policy version participates in the xref:sdk:enforced-mode.adoc#dod-types[Environment & Dependencies] drift check: when the organization publishes a new floor, the project's `.akka/policy.lock` becomes stale, the condition goes red, and the fix is to re-run `/akka:setup` (subject to a warn-then-enforce grace period so a newly locked condition does not turn every in-flight project red overnight).

The enforcement backstop is the *organization's own CI*, which reads the same repository and fails the build if the floor is not met. The local CLI is advisory and guided; CI is the gate — the same way enterprises already enforce standards. You can bypass checks locally, but you cannot merge or ship past CI.
