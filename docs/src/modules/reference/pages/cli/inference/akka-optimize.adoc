:page-persona: builder-developer, operator

The `akka optimize` commands govern how requests reach a model provider and what an organization sanctions, spends, trains, and evaluates. See xref:inference:routing/index.adoc[Routing requests to models] for the tasks the routing commands support.

Commands that deploy and serve a model are a separate family. See xref:reference:cli/inference/akka-models.adoc[`akka models`].

Every command on this page is a subcommand of [.cli-prefix-source]`{cli-optimize}`. Commands are written without that prefix throughout. The copy button on each example copies the command with the prefix included.

Documents sent with `-f FILE` are JSON. Passing `-f -` reads the document from standard input instead.

[#rulesets]
== Static routing rulesets

A ruleset holds the attribute-matching rules that choose a destination for a request. See xref:reference:descriptors/routing-ruleset.adoc[Routing ruleset] for the predicates and attributes a rule can use.

The singular forms `ruleset` and `rule` are accepted as aliases.

=== Listing and reading rulesets

To list every ruleset with its revision and priority:

[source, shell, role="cli-prefixed"]
----
rulesets list
----

To print the current document for one ruleset:

[source, shell, role="cli-prefixed"]
----
rulesets get NAME
----

To read a past revision instead of the current one:

[source, shell, role="cli-prefixed"]
----
rulesets get NAME --revision 3
----

=== Applying and deleting rulesets

To create or replace a ruleset in full:

[source, shell, role="cli-prefixed"]
----
rulesets apply NAME -f ruleset.json
----

To write only while the ruleset is still at a known revision, pass `--if-revision`. The write fails if another author has changed the ruleset in the meantime:

[source, shell, role="cli-prefixed"]
----
rulesets apply NAME -f ruleset.json --if-revision 3
----

To retire a ruleset:

[source, shell, role="cli-prefixed"]
----
rulesets delete NAME
----

The record of a retired ruleset survives its deletion.

=== Editing a single rule

To add or replace one rule without sending the rest of the ruleset:

[source, shell, role="cli-prefixed"]
----
rulesets rules apply RULESET RULE -f rule.json
----

To remove one rule:

[source, shell, role="cli-prefixed"]
----
rulesets rules delete RULESET RULE
----

=== Testing a ruleset

To see what a ruleset would decide for a sample request, with no traffic involved:

[source, shell, role="cli-prefixed"]
----
rulesets test NAME -f request.json
----

=== Execution order and history

Rulesets are evaluated in priority order. To read the order set for a ruleset:

[source, shell, role="cli-prefixed"]
----
rulesets priority NAME
----

To change it:

[source, shell, role="cli-prefixed"]
----
rulesets priority NAME --set 10
----

To list every change made to a ruleset, with its revision and who made it:

[source, shell, role="cli-prefixed"]
----
rulesets history NAME
----

[#routing-classifiers]
== Routing classifiers

A classifier is a named pointer to a model provider that a rule can select. Registration is immutable, so a retrained model is registered under a new id. The forms `routing-classifier`, `classifiers`, and `classifier` are accepted as aliases.

=== Listing and reading classifiers

To list what is registered, with retired entries omitted:

[source, shell, role="cli-prefixed"]
----
routing-classifiers list
----

To print one classifier as it is stored:

[source, shell, role="cli-prefixed"]
----
routing-classifiers get ID
----

=== Registering and retiring classifiers

To register a classifier:

[source, shell, role="cli-prefixed"]
----
routing-classifiers apply ID -f classifier.json
----

Registration is immutable. Sending the same document again under the same id succeeds, and reinstates the entry if it had been retired. Sending a different document under an existing id is refused. A retrained model is registered under a new id.

To retire a classifier:

[source, shell, role="cli-prefixed"]
----
routing-classifiers delete ID
----

Retirement is unconditional. Nothing checks whether a rule still names the classifier, so repoint any rule that selects it before retiring it. The command asks for confirmation first.

=== Reading classifier history

To list the registration, retirement, and reinstatement of a classifier, with who made each change and when:

[source, shell, role="cli-prefixed"]
----
routing-classifiers history ID
----

[#model-registry]
== Model registry

`models` is the registry of models an organization sanctions for use. The alias `model` is accepted.

[NOTE]
====
`{cli-optimize} models` and `{cli-models}` are different command families. This one records which models an organization permits and the conditions attached to them. `{cli-models}`, documented in xref:reference:cli/inference/akka-models.adoc[`akka models`], runs a model on hardware. `{cli-optimize} models list` and `{cli-models} list` therefore report different things.
====

[cols="2,3", options="header"]
|===
| Command
| Description

| `models list`
| List the portfolio.

| `models get NAME`
| Show one registry entry.

| `models apply NAME -f FILE`
| Register a model or update its metadata.

| `models promote NAME`
| Promote a candidate to active.

| `models deprecate NAME`
| Discourage new use of a model.

| `models retire NAME`
| End the sanction to use a model.

| `models resolve NAME --action ACTION`
| Resolve a decision on the model that owns it.

| `models signoff NAME --condition C`
| Record human sign-off closing a risk condition.

| `models waive NAME --condition C`
| Record a time-bound waiver on an open condition.

| `models strike NAME --condition C`
| Turn off a condition that does not apply.

| `models conditions list NAME`
| Every condition on a model and its state.

| `models attestations list NAME`
| Every attestation recorded against a model.

| `models attestations create NAME -f FILE`
| Record an externally-run evaluation or report.

| `models actions list NAME`
| What may be decided about this model, and how guarded each choice is.
|===

=== Deploying a registered model

Registering a model and running one are different actions on different resources. The commands that deploy a model to an inference cluster, carve the hardware it runs on, and expose it on a hostname belong to the `akka models` family. See xref:reference:cli/inference/akka-models.adoc[`akka models`].

[#use-cases]
== Semantic routing

The commands in this section govern the use-cases a semantic router recognizes and what serves each one. See xref:inference:routing/request-meaning.adoc[Routing on request meaning] for how the routing itself works.

=== Use cases

`use-cases` covers the use-cases discovered in traffic and the decisions taken about them.

[cols="2,3", options="header"]
|===
| Command
| Description

| `use-cases list`
| The discovered use-cases.

| `use-cases get NAME`
| One use-case.

| `use-cases funnel`
| Counts at each observe-to-route stage.

| `use-cases non-admission`
| Why the rest are not eligible, and what unblocks them.

| `use-cases resolve NAME --action ACTION`
| Resolve the safety decision on a use-case.

| `use-cases actions NAME`
| What may be decided about this use-case.
|===

[#working-set-and-manifests]
==== The working set and its manifests

Discovery runs against live traffic. The working set is what has been discovered so far, and a manifest fixes that set so it can enforce routing. See xref:inference:routing/defining-use-cases.adoc[Defining use cases] for what a use-case is and how one is discovered.

[cols="2,3", options="header"]
|===
| Command
| Description

| `use-cases status`
| The working set, and whether it can be frozen.

| `use-cases working-set`
| The use-cases currently being discovered in traffic.

| `use-cases exemplars list ID\|LABEL`
| One use-case and the requests nearest its centre.

| `use-cases label ID LABEL`
| Name a use-case in the working set.

| `use-cases freeze --as TAG --backend LABEL=BACKEND`
| Fix the working set as a manifest.

| `use-cases manifests list`
| Every manifest, and whether it can enforce.

| `use-cases manifests get TAG\|MANIFEST`
| One manifest as it was frozen.

| `use-cases manifests diff TAG`
| A manifest against the working set as it stands now.

| `use-cases manifests deploy TAG`
| Make a manifest the live routing policy.

| `use-cases manifests delete TAG`
| Tombstone a manifest.

| `use-cases captures get ID`
| One captured exchange in full.
|===

=== Routing policies

`routing-policies` states what serves a use-case, and in what share. The aliases `routing-policy`, `policies`, and `policy` are accepted.

[cols="2,3", options="header"]
|===
| Command
| Description

| `routing-policies get USECASE`
| The current policy and its history.

| `routing-policies apply USECASE -f FILE`
| Publish a policy version.

| `routing-policies rollback USECASE`
| Republish a previous version.

| `routing-policies veto USECASE`
| Refuse routing changes until lifted.

| `routing-policies route MODEL --usecase X [--shadow N] [--canary N]`
| Set the shadow and canary dials. `0` removes a dial.
|===

== Optimize

The commands in this section cover cost, incidents, pricing, and the training and evaluation of models.

=== Budget

`budget` covers spend, savings, caps and ceilings. The alias `budgets` is accepted.

[cols="2,3", options="header"]
|===
| Command
| Description

| `budget get`
| Spend, projection, savings and unit cost.

| `budget apply -f FILE`
| Set caps, ceilings and counterfactual pins.

| `budget resolve AGENT --action ACTION`
| Resolve a spend decision.

| `budget list`
| Anomalies, blocked requests and scrub failures.
|===

=== Incidents

`incidents` is the incident feed, unioned from its sources. The alias `incident` is accepted.

[cols="2,3", options="header"]
|===
| Command
| Description

| `incidents list`
| The incident feed.
|===

=== Pricing catalog

`pricing-catalog` holds per-token model prices, versioned. The aliases `pricing-catalogs`, `catalog`, and `catalogs` are accepted.

[cols="2,3", options="header"]
|===
| Command
| Description

| `pricing-catalog apply -f FILE`

=== Training runs

`training-runs` manages training runs. The aliases `training-run`, `runs`, and `run` are accepted.

[cols="2,3", options="header"]
|===
| Command
| Description

| `training-runs apply -f PLAN`

=== Training pipelines

[cols="2,3", options="header"]
|===
| Command
| Description

| `training-pipelines apply -f PLAN`

| `training-pipelines list`

| `training-pipelines get PIPELINE`

=== Trained models

=== Training evaluations

`training-evaluations` manages evaluations of trained models. The alias `training-evaluation` is accepted.

[cols="2,3", options="header"]
|===
| Command
| Description

| `training-evaluations apply --model MODEL --dataset HASH`
| Score a trained model against a dataset.

| `training-evaluations list`
| List evaluations and what they scored.

| `training-evaluations get EVALUATION`
| Show what an evaluation scored and where it got to.

| `training-evaluations report EVALUATION`

| `training-evaluations predictions EVALUATION`

=== Training datasets

`datasets` manages training datasets. The alias `dataset` is accepted.

[cols="2,3", options="header"]
|===
| Command
| Description

| `datasets create -f FILE`
| Register chat-format JSONL examples. The alias `register` is accepted.

| `datasets list`
| List registered datasets, newest first.

| `datasets get HASH`

=== Sessions and curations

A session is a raw conversation corpus. A curation judges raw sessions into a training dataset.

[cols="2,3", options="header"]
|===
| Command
| Description

| `sessions create -f CORPUS --source SOURCE`
| Upload a raw conversation corpus.

| `curations apply -f FILE`
| Start a curation run.

| `curations wait CURATION`
| Wait for a curation to finish.

| `curations get ID`
| Phase, counts, mean score and resulting dataset.
|===

=== Evaluation

`eval` covers datasets, experiments and the evaluators that score them.

[cols="2,3", options="header"]
|===
| Command
| Description

| `eval datasets create -f FILE`
| Upload a dataset file and version it.

| `eval datasets list`
| Datasets that have been imported, most recently imported first.

| `eval datasets get ID`
| One dataset: what it holds, what scores it, and every version it has had.

| `eval datasets items ID --version V`
| The items in one version of a dataset.

| `eval imports get ID`
| How far an import has got.

| `eval experiments apply -f FILE`
| Start an experiment.

| `eval experiments get ID`
| How far an experiment has got, and what it has found.

| `eval experiments record ID`
| The finished record: the run's report, or the numbers behind it.

| `eval experiments item EXPERIMENT ITEM`
| One item's run, and what each evaluator said about it.

| `eval experiments compare ID --baseline ID`
| An experiment against a baseline, item by item.

| `eval experiments history NAME`
| Every run of a recurring experiment, most recent first.

| `eval evaluators list`
| Registered evaluators, their kind and their version.
|===

== Captures

`captures` reads recorded interaction artifacts off a filesystem. The alias `capture` is accepted.

These commands serve debugging and diagnostics. They read artifacts from a directory on disk, which is where a capture written during local development or a support investigation lands.

[NOTE]
====
Captures recorded in production are stored in a location the CLI cannot reach in this version. The commands below read a filesystem directory only.
====

[cols="2,3", options="header"]
|===
| Command
| Description

| `captures list DIRECTORY`
| Every artifact in a directory, newest first.

| `captures show ARTIFACT`
| One artifact, read forward.
|===
