9+h| Akka Verify

| VER-01 | Akka Region (Verify) | Runtime writes interaction and control records | Interaction transcript (masked only where sanitizers are configured), token counts, control inventory | Akka runtime | Regional Postgres (event journal) | [.conn-private]#Private# in-region | Existing runtime database credentials | 
| VER-02 | Akka Region (Verify) | Evaluator judges an interaction | Interaction transcript sent to the judge model; verdict written back | Akka runtime, after each interaction | Ledger, and the configured LLM provider | [.conn-private]#Private# to the ledger; egress to the model provider (or the Optimize gateway) | Runtime-internal for the ledger; provider API key for the model | The judge model receives the full interaction. Use an in-region model to keep evaluation data in the region.
| VER-03 | Admins and operators | Operator views interactions | Interaction records | User (console or CLI) | Service backoffice API through backoffice-proxy | Same path as existing console and CLI access | Akka access token plus Kubernetes SubjectAccessReview for the backoffice role | Access requires the backoffice role in the project.
| VER-04 | Deployed Akka services (Optimize) | Offline evaluation experiments: record, replay, and report | Evaluation datasets, replayed prompts, model outputs, experiment reports and scores | Developer (akka optimize eval experiments) | offline-evaluation service, the target agent, and the storage account | [.conn-public]#Public# to the region ingress (TLS); private in-region (Akka route) | Akka platform JWT | Experiment reports are stored in the region. Replay sends prompts to the target URL that the developer gives.
