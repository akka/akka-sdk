Routing connects a use case to the backend that serves it. After the semantic router matches a request to a use case, defined in xref:inference:semantic-routing/defining-use-cases.adoc[Defining use cases], the routing rules for that use case determine which model provider receives the request.

== Working sets and Manifests
The gateway router is always observing the incoming traffic, producing new embeddings, and identifying groupings of requests that belong to discovered use cases. This always-learning set of use cases and rankings is called the _working set_. 

The gateway router identifies which use cases are stable and which ones are still changing. When you have assigned labels to all of the use cases above the relevance threshold, you can take a snapshot of the working set and assign backend routing names to the use cases.

This immutable, versioned, and provenance-verifiable artifact is called a _use case manifest_ or just _manifest_ for short. Only one manifest can be active and in-use by the gateway router at a time, so there are commands to deploy and undeploy these manifests.

When creating the manifest, the operator supplies `backend` names (which correspond to the gateway proxy configuration) for each use case. This creates a route table based on the meaning of requests. 

For examples of manipulating working sets and manifests, see xref:inference:akka-cli.adoc#working-set-and-manifests[The working set and its manifests] in the Akka CLI reference.
