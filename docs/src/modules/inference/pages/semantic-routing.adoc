= Semantic routing

:page-persona: builder-developer, builder-ai-ml
:page-banner: inference

Semantic routing selects the destination for a request based on the meaning of its content. Request meaning is discovered at runtime when the request is received. This semantic meaning gets matched against a list of known _use cases_, each of which has been mapped to a link:{url-agentgateway-backends}[backend, window="new"].

The determination of _meaning_ in a request is done through pure math and does not use an LLM. This is different than xref:inference:akka-cli.adoc#routing-classifiers[classification], which does use a model.

== Where to route
Developers have a number of options available when it comes to routing model requests based on meaning. Some language-specific SDKs have this functionality, including some agentic frameworks that support it through configuration (e.g. YAML). However, the only way to be sure that you're applying semantic routing rules across all traffic and also prove that fact for governance and compliance is to send all agentic traffic through an _AI gateway_.

== Architecture

image:semantic-routing.svg[Semantic routing architecture with an evidence log, width=740]

The first and most important rule is that agents can never know they're going through a gateway. Just like standard HTTP proxies, the infrastructure takes care of directing traffic to the proxy and this decision is never made inside user-space application code.

Agents send their requests to a gateway. The gateway passes each request to the semantic router. The router examines the content of the request and returns the backend that should serve it. The gateway forwards the request to the model provider named in that decision and returns the response to the calling agent.

The router streams a verifiable record of each decision to an evidence log. Each record covers one routing decision, so the backend chosen for a past request can be checked after the fact. Crucially, this decision can withstand governance and compliance scrutiny. It can tell an operator what decision was made, when it was made, based on which context, for which input, and based on which unique hashed version of the routing rules were active in the gateway. The entire evidence chain is cryptographically unforgeable. 

The router derives its decision from the content of the request. An agent does not name a model when it sends a request, so the set of providers behind the gateway can change without a change to agent code.

The providers behind the gateway carry different characteristics. A general-purpose model offers broad capability at higher cost per token. A low-latency model returns faster responses for simpler requests. A self-hosted model runs on infrastructure you control, covered in xref:inference:vllm.adoc[vLLM].

See xref:inference:semantic-routing/defining-use-cases.adoc[Defining use cases] for how a request is matched to a use case. See xref:inference:semantic-routing/routing-use-cases.adoc[Routing use cases] for how each use case reaches a backend.
