This page walks from an empty project through the four things a first red-team campaign needs: the pack, an attacker corpus, a campaign class, and one run.

== Overview

A red-team campaign is a JUnit test gated on `-Dredteam=true`.
`mvn verify` compiles it and leaves it out of the commit build; `mvn verify -Dredteam=true` runs it.
The suite lives under `src/test/java/<your-package>/redteam/` alongside the project's other tests, and reads the same `SystemUnderTest` adapter the evaluation suite uses.

== Add the redteam pack

From the project root:

[listing]
----
akka redteam init
----

The command overlays the redteam tree onto the project's `src/test/java` and prints the dependency block to add to the pom.
It edits no pom itself.

Add the dependency block to the project's pom:

[source,xml,indent=0]
----
<dependency>
  <groupId>io.akka</groupId>
  <artifactId>evalkit-redteam</artifactId>
  <version>0.2.0-SNAPSHOT</version>
  <scope>test</scope>
</dependency>
----

`evalkit-redteam` builds on `evalkit`, so the evaluation dependency comes in transitively.

== Pull a corpus

Red-team campaigns run against an attacker corpus.
The command downloads the latest date-versioned artifact into the customer's classpath:

[listing]
----
akka redteam corpora pull
----

For the corpora that ship, the license terms, and how to add corpora of your own, see xref:testing:red-teaming/corpora.adoc[].

== Reuse the evaluation adapter

The same `SystemUnderTest` implementation the evaluation campaign uses reaches the target for a red-team campaign.
For the shape and the code, see xref:testing:evaluation/getting-started.adoc[] — the adapter section applies unchanged.

<1> `@EnabledIfSystemProperty` gates the test on `-Dredteam=true`.
`mvn verify` alone compiles the class and skips execution.
<2> Every scorer says whether a rule was broken.
Multiple scorers cover multiple hazards; a rule is broken when any bound scorer returns `BROKE_THROUGH`.
<3> The plan names the campaign, the scorers, and how the campaign runs the corpus of attacker goals.
<4> Static wrappers turn one attacker goal into many prompts by role-playing the request, base64-encoding the payload, or splitting it across turns.
See xref:testing:red-teaming/techniques.adoc[].
<5> An adaptive technique revises its prompt based on the target's last reply.
See xref:testing:red-teaming/adaptive-attacks.adoc[].
<6> The budget caps the campaign's cost — model tokens across every scorer plus wall-clock elapsed.
The campaign stops when either bound is reached, whichever comes first.
<7> `runAgainst(target)` walks the corpus, applies the techniques, scores every attempt, and returns a `RedTeamResult`.
<8> `assertNoBreakthroughs()` fails the test when any scorer returned `BROKE_THROUGH`, so CI catches regressions.

== Run it

Local:

[listing]
----
mvn verify -Dredteam=true
----

The rendered report lands under `target/evalkit/reports/<campaign>-redteam.txt`.
For what each panel of the report means, see xref:testing:red-teaming/reports.adoc[].
