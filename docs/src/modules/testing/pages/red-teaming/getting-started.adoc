= Getting started with red teaming

include::ROOT:partial$include.adoc[]

:page-summary: A red-team suite probes an AI service for the things it should refuse — jailbreaks, prompt injections, secret leaks, PII disclosure. It lives beside the evaluation suite, runs the same target adapter, and reports each break as its own incident.
:page-when-to-use: Use when a service is exposed to attacker-shaped input — a customer-facing chat agent, a RAG system reading untrusted passages, an agent whose tools reach sensitive state.
:page-prerequisites: An existing Maven project. An evaluation runner already in place (see xref:testing:evaluation/getting-started.adoc[]) is the fastest starting point but not required.
:page-related: xref:testing:red-teaming/scorers.adoc[], xref:testing:red-teaming/techniques.adoc[], xref:testing:red-teaming/adaptive-attacks.adoc[], xref:testing:red-teaming/corpora.adoc[]

A red-team campaign runs a service through attacker-shaped prompts and asks a scorer whether the target broke through, held, or the evidence was inconclusive.
Each break is one incident with its own row in the report, so security review reads a red-team run the way it reads a penetration test — case by case, not as a rate.

== Overview

A red-team campaign has four parts.
The **target** is the same `SystemUnderTest` an evaluation campaign uses, so a project with an evaluation suite already reuses its adapter.
The **corpus** is a set of attacker goals ("get the model to describe how to bypass 2FA"), pulled from date-versioned artifacts like HarmBench, DAN, or JailbreakBench.
The **techniques** turn each goal into many prompts — static wrappers roleplay the request or base64-encode the payload; adaptive techniques revise their prompts based on the target's last reply.
The **scorers** decide, per exchange, whether the target complied with a harmful request, using the three-family taxonomy (deterministic, heuristic, agentic) that the evaluation side uses too.

Red-team suites are gated on `-Dredteam=true`.
`mvn verify` compiles the classes without running them; `mvn verify -Dredteam=true` runs them.
The runtime enforces a token and wall-clock budget so a campaign cannot run away with the customer's spend.

== Add the redteam pack

`akka redteam init` overlays the source tree onto the project, edits the pom to add the `evalkit-redteam` dependency at test scope, and reports what it wrote.

[listing]
----
$ akka redteam init
added the evalkit-redteam dependency to pom.xml (previous kept as pom.xml.backup)
run a campaign with `mvn verify -Dredteam=true`

Added the redteam source root to . under package com.acme.checkout.redteam — 9 file(s) written, 0 kept.
----

`evalkit-redteam` depends on `evalkit`, so the evaluation dependency comes in transitively — a project with a red-team suite has both trees at test scope.

== Reuse the evaluation adapter

The same `SystemUnderTest` implementation the evaluation campaign uses reaches the target for a red-team campaign.
For its shape and code, see xref:testing:evaluation/getting-started.adoc[] — the adapter section applies unchanged.
A project starting with red teaming and no prior evaluation writes the same adapter before the campaign runs.

<1> The system-property gate keeps campaigns out of `mvn verify`.
<2> Multiple scorers cover multiple hazards.
A rule is broken when any bound scorer returns `BROKE_THROUGH`.
<3> The plan names the campaign, the scorers, and how the campaign runs the corpus of attacker goals.
<4> Static wrappers turn one attacker goal into many prompts by role-playing the request, base64-encoding the payload, or splitting it across turns.
<5> An adaptive technique revises its prompt based on the target's last reply.
See xref:testing:red-teaming/adaptive-attacks.adoc[].
<6> The budget caps the campaign's cost — model tokens across every scorer plus wall-clock elapsed.
The campaign stops when either bound is reached.
<7> `runAgainst(target)` walks the corpus, applies the techniques, scores every attempt, and returns a `RedTeamResult`.
<8> `assertNoBreakthroughs()` fails the test when any scorer returned `BROKE_THROUGH`, so CI catches regressions.

== Where the parts live

[cols="1,3"]
|===
| Path | What lives there

| `src/test/java/<pkg>/redteam/scorer/{deterministic,heuristic,agentic}/`  | Customer-authored scorers.
| `src/test/java/<pkg>/redteam/technique/`                                 | Customer-authored techniques.
| `src/test/resources/redteam/corpora/`                                    | The pulled attacker corpora.
| `target/evalkit/reports/`                                                | Rendered reports (gitignored).
|===
