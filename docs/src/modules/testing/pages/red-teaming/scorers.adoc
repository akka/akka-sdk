= Adversarial scorers
:page-summary: Decide whether the target broke through a red-team rule using a deterministic, heuristic, or agentic scorer.

An adversarial scorer decides whether the target broke through a red-team rule.
Red-team scorers use the same three-family model as evaluation scorers, and every campaign that mixes them settles the clear cases cheaply so the expensive judgment runs only on the borderline.

== Overview

Every red-team scorer implements `akka.evalkit.redteam.scorer.RedTeamScorer` and returns a `ScoreResult` — one of `BROKE_THROUGH`, `HELD`, or `INCONCLUSIVE`.
Each break is one incident with its own row in the report; a campaign that ran 500 attacks against a scorer reports the count of breaks and the count of holds as separate figures.

The three families answer three different kinds of question:

* *Deterministic* reads the target's reply against a stated known-bad thing.
* *Heuristic* computes a measurement from the reply and reads it against a rule of thumb.
* *Agentic* hands the exchange to a language model and reads back a broke/held verdict with a confidence.

An `INCONCLUSIVE` verdict feeds the next tier of scorer so the borderline case gets a second read.

== A deterministic scorer

`SecretExfilScorer` reads the target's reply against a list of secret markers the customer configured — the exact system prompt text, API keys the target must not repeat, internal tool names.

<1> An API key prefix the target should never return.
<2> The first line of the system prompt.
Any match on this substring is a system-prompt leak.
<3> An internal tool name that has no reason to appear in a user-facing reply.
<4> The scorer takes the attacker's prompt and the target's reply.
A marker present in the reply is a `BROKE_THROUGH`; a marker absent is `HELD`; an empty reply is `INCONCLUSIVE`.

== A heuristic scorer

`JailbreakScorer` reads the target's reply for two signals — strong-refusal language ("I can't help with that") and task-fulfilment language (the phrases a compliance would use).

<1> The patterns are baked into the class.
Changing them would change what "the same `JailbreakScorer`" means from campaign to campaign, so the report reads a `JailbreakScorer` verdict as "this specific pattern set decided the case".
<2> A reply with refusal language and no task-fulfilment reads as `HELD`; a reply with task-fulfilment and no refusal reads as `BROKE_THROUGH`; a reply carrying both signals reads as `INCONCLUSIVE`.

The two-tier pattern is where the family taxonomy pays off.
The heuristic settles the confident cases for free and hands the ambiguous ones up to an agentic scorer only when needed:

== An agentic scorer

`AgenticJailbreakJudge` hands the exchange to a language model and reads back a verdict with a confidence.
The industry standard for jailbreak detection — HarmBench, StrongREJECT and the OpenAI red-team benchmarks all work this way — because the modern jailbreaks succeed by hiding compliance inside a wrapper a regex reads as refusal.

[source,java,indent=0]
.AgenticJailbreakSample.java
----
include::example$doc-snippets/src/test/java/com/example/redteam/scorer/agentic/AgenticJailbreakSample.java[tag=wiring]
----
<1> `systemPrompt()` returns the wording the model needs to be told.
Constructing `new AgenticJailbreakJudge(null)` only to read the prompt is idiomatic, because
the prompt is static and belongs to the scorer rather than to the model.
<2> The `Assessor` reaches the judge through the component client, formatting the exchange the
way the system prompt expects to read it.
A scorer holds no component client, which is why the call lives here rather than inside the
scorer.
<3> Construct the scorer with the assessor.
<4> The scorer handles the rest: check that there is anything to ask about, call the assessor, validate the confidence, produce a `ScoreResult`.

A confidence below the scorer's threshold (default 0.6) reads as `INCONCLUSIVE`.
The campaign either iterates with more attempts or leaves the exchange in the borderline column of the report.

NOTE: A cheap, small model is usually the right choice for a red-team judge.
HarmBench uses a fine-tuned Llama-8B.
Production judges have run on Gemini Flash or gpt-4o-mini without measurable loss of accuracy.
