= Scenarios and rules

include::ROOT:partial$include.adoc[]

:page-summary: A scenario is one test case with a stable id; a rule is a named requirement the target upholds across the scenarios that reference it. Reports read verdicts scenario-by-scenario, rule-by-rule.
:page-when-to-use: Use when a rule needs a stable identity across runs, when a scenario needs a multi-turn precursor, or when the report should group verdicts by hazard.
:page-related: xref:testing:evaluation/scorers.adoc[], xref:testing:evaluation/campaigns.adoc[], xref:testing:evaluation/reports.adoc[]

A scenario is one test case the target reads and the runner scores.
A rule is a named requirement several scenarios share.
Reports group verdicts by rule, so a change that flips one scenario's verdict reads as movement in the rule it belongs to.

== The scenario record

Scenarios live under `src/test/resources/eval/datasets/` as JSONL, one per line.
Every scenario names an id, a prompt, and the rule it addresses.

[source,json]
----
{
  "id": "case-1",
  "prompt": "What is our refund window?",
  "expected": "14 days",
  "rule": "answers_refund_window",
  "hazards": []
}
----

`id` is the stable identifier reports reference.
`prompt` is the input sent to the target.
`expected` is the reference answer scorers read against.
`rule` is the rule this scenario is expected to satisfy.
`hazards` carries taxonomy-prefixed hazard keys (`ailuminate:privacy`, `owasp:llm01_prompt_injection`) so reports group verdicts by harm type.
See xref:testing:red-teaming/reference/hazards.adoc[] for the taxonomies.

== Multi-turn scenarios

A scenario carries an optional `precursor` that seeds the conversation before the rule is checked.
The precursor plays into the target as a conversation opener; the `prompt` is the turn that gets scored.

[source,json]
----
{
  "id": "case-2",
  "precursor": [
    {"role": "user", "content": "I bought a shirt"}
  ],
  "prompt": "How long do I have to return it?",
  "expected": "14 days",
  "rule": "answers_refund_window"
}
----

The runner records both the precursor turns and the graded turn, so a scorer reading tool calls or model calls sees the whole exchange.

== The rule declaration

Rules are declared in the campaign class and reference their scorers there.
Every rule declares the hazards it covers so the report can group results by harm type.

[source,java,indent=0]
----
Rule.of("answers_refund_window")
    .describedAs("The reply names 14 days as the refund window")
    .coveringHazards(Set.of(Hazard.PRIVACY));
----

A rule that covers no hazards is still valid.
The report shows its verdicts under the pass rate, but the rule is left out of the hazard rollup.

== The four run outcomes

Every scenario ends in one of four outcomes.
Which outcome a scenario carries depends on the scorer that decided it.

`Asserted` +
A deterministic scorer produced a pass or fail from comparison.
The claim and the reason appear on the report row so a reviewer can tell why the case decided the way it did.

`Measured` +
A heuristic scorer produced a share against a threshold.
The value and the pass flag appear on the row.

`Scored` +
An agentic scorer produced a graded verdict.
The band and the model's reason appear on the row.

`Inconclusive` +
The scorer had nothing to read.
The row appears in the report under the "What it cannot tell you" panel so the reviewer sees the case exists — the pass rate leaves the case out rather than counting it either way.

For how each family produces each outcome, see xref:testing:evaluation/scorers.adoc[].
For how the outcomes read on the rendered report, see xref:testing:evaluation/reports.adoc[].
