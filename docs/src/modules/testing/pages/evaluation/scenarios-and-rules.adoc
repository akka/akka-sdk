= Scenarios and requirements

include::ROOT:partial$include.adoc[]

:page-summary: A scenario is one test case with a stable id. Every run of one scenario is gathered into a requirement, and the report reads verdicts requirement by requirement rather than run by run.
:page-when-to-use: Use when a case needs a stable identity across runs, when a case needs the conversation seeded before the graded turn, or when reading how a repeated scenario reaches one verdict.
:page-related: xref:testing:evaluation/scorers.adoc[], xref:testing:evaluation/campaigns.adoc[], xref:testing:evaluation/reports.adoc[]

A scenario is one test case the target reads and a scorer settles.
A requirement is one scenario together with every run of it.

Running a scenario three times produces three runs and one requirement.
The report reads requirements, so a scenario that passes twice and fails once is one varied
requirement rather than a mixture of passes and failures.

== The scenario record

`Scenario` is a Java record. Build the list in the campaign class; evalkit ships no reader
for an on-disk format, so where a project keeps its cases is its own choice.

[source,java,indent=0]
----
new Scenario(
    "refund-timing",                           // <1>
    Optional.of("GenUC-16a"),                  // <2>
    Optional.empty(),                          // <3>
    List.of("30 days"),                        // <4>
    new Precursor.None(),                      // <5>
    "when do I get my refund?",                // <6>
    "the reply states a 30-day refund window"); // <7>
----
<1> The stable identifier the report references.
<2> The specification node the answer should come from, when the target tracks one.
Naming it lets the scenario be settled by comparison instead of by a model: a tick rather
than a paid, slightly random opinion.
<3> A `MetricRef` when this scenario should be settled by a named metric.
<4> Wording the reply must contain.
Most scenarios require none, and a shorter constructor omits this.
<5> What has to happen before the graded turn.
See <<_precursors>>.
<6> The turn that gets scored.
<7> What a correct answer does, in a sentence.
This is what a judge reads the reply against.

Which scorer settles a scenario follows from what it declares.
`ScorerRouter.byExpectation` sends a named spec node to comparison, required phrases to
`ContainsAll`, a named metric to that metric, and anything else to the judge.

== Precursors

`Precursor` is a sealed interface with four cases.

`None` +
The graded turn is the first thing said.

`Replay(List<String> userTurns)` +
The listed turns are said first, and the target answers each.
The conversation is real, so a scenario about the fourth turn is asked at the fourth turn.

`Fixture(String name, Map<String, String> parameters)` +
The target puts itself into a named state.
The target declares what it can build in `SystemUnderTest.fixtures()`, and a plan naming
one it cannot is refused before the campaign runs.

`FailingTool(String tool, String message, Precursor then)` +
A named tool is made to fail, then the wrapped precursor runs.
Used for scenarios about recovery.
A target that cannot break the named tool causes the campaign to be refused, because
answering with a working tool would report the system as recovering from a failure that
never happened.

Only `Replay` proves the system reached the state under its own power.
A fixture is a seeded starting point, and the report counts it as one.

== The six run outcomes

Every run ends in one of six outcomes.
Which one depends on the scorer that settled it.

`Asserted(passed, expected, actual)` +
A deterministic scorer compared two things.
Both sides appear on the report row, which is why it can print `expected GenUC-16a, found GenUC-17a`.

`Measured(metricId, metricVersion, value, threshold, passed, note)` +
A heuristic scorer computed a value against a threshold.

`Scored(Grade)` +
A judge returned a band against a rubric.

`Inconclusive(reason)` +
The scorer had nothing to read.
The pass rate leaves the run out rather than counting it either way.

`NotReached(cause, reason, precursor)` +
The run never got to the graded turn: the fixture would not build, or the system said nothing.
A fact about the harness, not a verdict on the system.

`Failed(reason)` +
The run itself broke.

The last three are why the outcome type is not a number.
A `double` has no way to say "this was never asked", and a report that scores absence as
zero accuses the system of something it was never given the chance to do.

== From runs to a verdict

`RequirementResult` gathers a scenario's runs and answers `verdict()` with one of five
values: `PASSED`, `FAILED`, `VARIED`, `UNDECIDED`, `NO_RESULT`.

`VARIED` is the one worth repeating for.
A requirement the system meets eight times in ten still passes five runs about a third of
the time, and one run cannot tell that apart from a requirement it always meets.

`UNDECIDED` and `NO_RESULT` are kept apart on purpose: a judge that would not commit and a
run that produced no evidence at all are different facts about a campaign.
