An evaluator decides the outcome of one recorded attempt.
Every evaluator implements the same one-method interface, and reports read the verdict alongside the evaluator's name so a reviewer knows what decided each case.

== Overview

Every evaluator implements `akka.evalkit.core.domain.Evaluator` and returns a `RunOutcome` — one of `Asserted` (a pass or fail from comparison), `Measured` (a number against a threshold), `Scored` (a grade from a rubric), `Inconclusive` (the evaluator had nothing to read), `NotReached` (the attempt never happened), or `Failed` (the evaluator itself broke).
An evaluator whose evidence runs out returns `Inconclusive`, and the report keeps that case out of the pass rate.

Three families answer three different kinds of question:

* *Deterministic* reads recorded values against stated expectations.
* *Heuristic* computes a measurement from the recorded interaction and reads it against a threshold.
* *Agentic* hands the exchange to a language model and reads back a score with the model's reason.

An eval case is settled by exactly one evaluator, chosen from what the case declares.
`EvaluatorRouter.byExpectation` sends a case naming a specification node to comparison,
one naming required phrases to `ContainsAll`, one naming a metric to that metric, and
everything else to the judge.

Choosing the cheapest evaluator that can answer is therefore something the case author
does, by declaring what the case is really about. A case that names a decision costs
nothing to settle; one that names nothing pays a model.

== A deterministic evaluator

`ToolPermission` checks that the agent called only tools on an allow list.

<1> Build the evaluator with the tools the eval case allows. An empty list on both sides throws at construction — an evaluator that authorises everything reports a check that examined nothing.
<2> Read the recorded tool calls into per-call findings.
Each finding names one tool and states whether it was authorised.
<3> Aggregate the findings into a `RunOutcome.Measured` carrying the share authorised, the threshold, and whether the attempt passed.

The scoring is proportional past the pass line, so a report can tell an attempt that squeaked in from one that walked in comfortably.

The budget is what the version records — changing it changes what a recorded score under the old value meant.

<2> `value()` is a share; `passed()` is the boolean the report groups by.
<3> An attempt that reported no latency at all is `Inconclusive` — reading zero as "instant" would put a made-up figure in the report.

NOTE: The score halves at the budget rather than stepping.
An attempt one millisecond over the line reads as 0.499; one twice as slow reads as 0.
The gradient is what the tuning conversations depend on.

== An agentic evaluator

`TurnFaithfulness` asks whether a reply is supported by the passages the target retrieved.
The judgment is a language reading (paraphrase, negation, partial support), so this metric ships as agentic: the customer supplies the model, evalkit supplies the system prompt.

[source,java,indent=0]
.TurnFaithfulnessSample.java
----
include::example$doc-snippets/src/test/java/com/example/eval/evaluator/agentic/TurnFaithfulnessSample.java[tag=wiring]
----
<1> The `Assessor` is a lambda that hands the question to the customer's Agent.
The `Question` carries the task and what to read it against.
<2> `systemPrompt()` on any built-in agentic metric returns the wording the model needs to be told.
Constructing `new TurnFaithfulness(null)` only to read the prompt is idiomatic here — the prompt is static.
<3> `.responseConformsTo(Assessment.class)` makes the SDK check the reply against those fields.
A model that returns malformed JSON is retried before the assessor sees it.
<4> Construct the evaluator with the assessor.
<5> The evaluator's `score(EvalContext)` handles the rest: check that there is anything to ask about, call the assessor, validate the returned score is a share in `[0, 1]`, produce a `Measured`.

----
<1> The `MetricRef` names the evaluator and its version.
The version is what a recorded score is filed under, and it changes whenever a setting change would silently redefine what "the same score" means.
<2> The evaluator's `id()` is what the report row prints and what the CLI matches on `--evaluator`.
<3> Return `Inconclusive` before reaching for `Measured` or `Asserted`.
An evaluator that read an empty reply as failed would report a defect the target never had a chance to make.
<4> A deterministic evaluator reads the reply against a stated expectation.
The regex is the expectation.
<5> `Asserted(boolean passed, String expected, String actual)` is what a deterministic evaluator returns.
Both sides land in the report row, which is why it can print `expected GenUC-16a, found GenUC-17a`.

== The built-in evaluators, in one table

For the reference tables listing every built-in evaluator and what each reads, see xref:testing:evaluation/reference/evaluators.adoc[].

* 3 deterministic: `ToolPermission`, `ToolCorrectness`, `ArgumentCorrectness`.
* 12 heuristic across three groups — budget (`LatencyBudget`, `TokenBudget`, `ModelCallBudget`), format (`RegexMatch`, `LengthInRange`, `JsonValidity`), text-overlap (`ExactMatch`, `TokenF1`), retrieval-quality (`ContextRecall`, `ContextPrecision`, `ReciprocalRank`, `NormalizedDiscountedCumulativeGain`).
* 7 agentic: `TaskCompletion`, `PlanQuality`, `PlanAdherence`, `StepEfficiency`, `TurnFaithfulness`, `TurnRelevancy`, `CitationFaithfulness`.

== Testing

Every evaluator tests the same way: build an `EvalContext` you control and read the `RunOutcome` back.
Deterministic and heuristic evaluators score off recorded values and computed measurements, so they run under `mvn verify` with the JVM alone.
Agentic evaluators use a stub `Assessor` returning `Assessment` directly.

Unit tests use the same TestKit setup, described in xref:testing:unit.adoc[].
