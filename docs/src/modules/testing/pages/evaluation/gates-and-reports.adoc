A gate is what a batch of cases must satisfy over all case results, and the report is what a run returns.

[#gates]
== Gates

A link:{attachmentsdir}/testkit/akka/javasdk/testkit/eval/Gate.html[Gate] is what the batch must satisfy over all case results.

[cols="2,3"]
|===
| Gate | Passes when

| `Gate.allCasesShouldPass()`
| No case has a failed result. This is the gate that applies when none is given.

| `Gate.passRateShouldBeAtLeast(minimumRate)`
| The share of cases with no failed result is at least `minimumRate`.

| `Gate.passRateShouldBeAtLeast(evaluatorClass, minimumRate)`
| The share of the evaluator's results that passed is at least `minimumRate`. Inconclusive results are left out of the count. The gate fails when the evaluator has no result to count. The class is a built-in nested in `Evaluators`, for example `Evaluators.ToolArgument.class`, or your own evaluator class.

| `Gate.targetShouldNotFail()`
| No case failed while loading its recorded calls or in the agent call.

| `gate.and(other)`
| Both gates hold. The verdict lists both details.
|===

A failed gate does not throw.
Assert on the report, and use the rendered report as the failure message.

[#reading-the-report]
== Reading the report

`run()` returns an link:{attachmentsdir}/testkit/akka/javasdk/testkit/eval/ExperimentRunner.EvalReport.html[EvalReport].

[cols="1,3"]
|===
| Accessor | Content

| `name()`
| The name given with `name(...)`, or the test method that ran the experiment and the start time, for example `SupportAgentEvalTest.qualityGate-20261001-101530-123`.

| `passed()`
| Whether the gate passed.

| `passRate()`
| The share of cases with no failed result.

| `results()`
| One `CaseResult` per case, in the order the cases were given: the case id, the `Interaction` and the results. `describe()` renders one case as in the report.

| `render()`
| The report as text.

| `reportFile()`
| The JSON file `run()` wrote, see <<json-report>>. Empty when the experiment was run with `withoutReportFile()` or the file could not be written.
|===

A rendered report of a passing batch:

[listing]
----
3/3 cases passed (100%)
gate: passed — pass rate 1.00 over 3 cases, required 0.90; tool-arguments rate 1.00 over 2 judged cases, required 1.00; no target failures
  tools 1/1
  tool-arguments 2/2
  forbidden-tools 2/2
  reply-contains 2/2
  tool-order 1/1
  reply-matches 1/1
  tool-call-budget 1/1
  model-call-budget 1/1
spend: 6 model calls, 123 tokens in, 321 out, 550 ms in total, slowest order-status at 489 ms, over 3/3 cases with evidence
----

Line by line:

. The cases with no failed result, and the pass rate.
. The gate's verdict and its detail. A combined gate lists the detail of each part.
. One line per evaluator, under its xref:testing:evaluation/eval-cases.adoc#evaluator-labels[label]: the cases it passed over the cases it judged. An evaluator that was inconclusive on some cases shows the count in brackets, for example `token-budget 0/0 (2 inconclusive)`.
. The spend: model calls, tokens and latency summed over the cases whose trace carried model calls, and the slowest case. The line is absent when no case carried model calls.
. After these lines, every failed case with its evidence, see <<reading-a-failed-case>>.

[#reading-a-failed-case]
== Reading a failed case

The rendered report ends with every failed case and its evidence.
This report is from a case that asks where order o_42 is, with an evaluator that expects `getOrder` to be called with `o_43`:

[listing]
----
0/1 cases passed (0%)
gate: FAILED — failed cases [wrong-order]
  tool-arguments 0/1
spend: 2 model calls, 123 tokens in, 321 out, 6 ms in total, slowest wrong-order at 6 ms, over 1/1 cases with evidence
case wrong-order FAILED
  reply: Order o_42 is shipped.
  tools: getOrder{orderId=o_42}
  model: 2 calls, 123 tokens in, 321 out, 6 ms
  FAIL tool-arguments: getOrder(orderId) expected o_43, was [o_42]
----

A failed case prints the reply, the tool calls with their arguments, the model spend, and every result with its detail.
When the agent mapped the model's text into the reply, a `model text:` line shows the model's own text as well.
The reply is cut to one line of at most 200 characters.

[#json-report]
== The JSON report

`run()` writes the run as one JSON document to `target/eval-reports/<name>.json`, for tools that collect runs or render their own reports.
The path is relative to the working directory, which is the module directory under Maven.
The report is named after the test method and the start time, or after the name given with `name(...)`.
`reportDirectory(path)` writes the file somewhere else, `withoutReportFile()` writes none.
A file that cannot be written is logged as a warning and does not fail the run.

[source,java]
----
var report =
    experimentRunner
        .cases(cases)
        .agent(SupportAgent::ask)
        .name("support-agent-quality")
        .gate(Gate.passRateShouldBeAtLeast(0.9))
        .run();
assertThat(report.passed()).withFailMessage(report::render).isTrue();
----

The document has the format `akka-eval-report`, version 1.
Every property is always present.
Absent evidence is an empty string, an empty array, or `null` for a tool result or error.
Durations are integer milliseconds, timestamps are ISO-8601 in UTC.
A reader ignores properties it does not know.
`formatVersion` increments when a property changes meaning or is removed.
The testkit jar carries the JSON Schema at `akka/javasdk/testkit/eval/eval-report.schema.json`.

[source,json]
----
{
  "format": "akka-eval-report",
  "formatVersion": 1,
  "name": "support-agent-quality",
  "startedAt": "2026-10-01T10:15:30.123Z",
  "finishedAt": "2026-10-01T10:16:02.456Z",
  "gate": { "passed": false, "detail": "pass rate 0.50 over 2 cases, required 0.90" },
  "summary": { "cases": 2, "passedCases": 1, "failedCases": 1, "passRate": 0.5 },
  "evaluators": [
    { "evaluator": "tools", "passed": 1, "failed": 0, "inconclusive": 0 },
    { "evaluator": "tool-arguments", "passed": 0, "failed": 1, "inconclusive": 0 }
  ],
  "spend": {
    "casesWithEvidence": 2, "modelCalls": 2,
    "inputTokens": 200, "outputTokens": 40, "latencyMs": 90
  },
  "cases": [
    {
      "id": "wrong-order",
      "passed": false,
      "interaction": {
        "input": "Where is o_43?",
        "userMessage": "Where is o_43?",
        "reply": "Order o_42 is shipped.",
        "finalModelText": "Order o_42 is shipped.",
        "latencyMs": 45, "inputTokens": 100, "outputTokens": 20, "blocked": false,
        "toolCalls": [
          { "name": "getOrder", "arguments": { "orderId": "o_42" },
            "result": "{\"status\":\"shipped\"}", "error": null }
        ],
        "modelCalls": [
          { "model": "gpt-4o", "provider": "openai", "finishReasons": ["STOP"],
            "inputTokens": 100, "outputTokens": 20, "durationMs": 40,
            "inputMessages": "...", "outputMessages": "..." }
        ],
        "guardrails": [
          { "name": "pii", "category": "privacy", "passed": true, "explanation": "" }
        ]
      },
      "results": [
        { "evaluator": "tool-arguments", "verdict": "FAIL",
          "detail": "getOrder(orderId) expected o_43, was [o_42]" }
      ]
    }
  ]
}
----

[cols="1,3"]
|===
| Property | Content

| `name`
| The name given with `name(...)`, or the test method and the start time.

| `startedAt`, `finishedAt`
| When the run started and when the last case was evaluated.

| `gate`
| The gate verdict and its detail, the same text `render()` prints. A combined gate joins the detail of each part with a semicolon.

| `summary`
| The case counts and the pass rate.

| `evaluators`
| One entry per evaluator label, in the order the labels first appear in the cases, with the counts of passed, failed and inconclusive results. The labels are the ones the text report uses, including `target` and `setup` for a case that did not reach evaluation.

| `spend`
| Model calls, tokens and latency summed over the cases whose evidence carries model calls. All zero when no case does.

| `cases`
| One entry per case, in the order the cases were given. `interaction` carries the input, the user message the agent sent the model, the reply, the model's final text, the latency, the token sums, whether a guardrail blocked the turn, and the traced tool calls, model calls and guardrail evaluations. `results` carries one entry per evaluator with the verdict `PASS`, `FAIL` or `INCONCLUSIVE` and the detail.
|===

A case whose agent call failed has an empty reply, the tool calls made before the failure, and a single `target` result with the verdict `FAIL`.
`modelCalls[].inputMessages` and `outputMessages` carry the full rendered messages, so the file grows with the length of the conversation.
