A gate is what a batch of cases must satisfy over all case results, and the report is what a run returns.

[#outcomes]
== The attempt verdict

An attempt is one case in one run.
Its results are the xref:sdk:evaluators.adoc#outcomes[outcomes] of the evaluators bound to the agent, one per evaluator. A failed agent call is a failed result named `target`, and an evaluator that recorded nothing within the evaluation timeout is inconclusive. The timeout is 10 seconds unless the experiment sets another with `evaluationTimeout(Duration)`.

The verdict of the attempt follows from the results of all its evaluators.

[cols="1,3"]
|===
| Attempt verdict | When

| `FAIL`
| Any result failed.

| `INCONCLUSIVE`
| No result failed and any result is inconclusive, or no result passed: every result is not applicable, or no evaluator is bound.

| `PASS`
| At least one result passed and the others are not applicable.
|===

Only a passed attempt counts as passed, so an evaluator that could not judge is visible in the gate and in the report rather than silently passed.
A not applicable result is neutral. The gates leave it out, and the report counts it.

[#gates]
== Gates

A link:{attachmentsdir}/testkit/akka/javasdk/testkit/eval/Gate.html[Gate] is what the batch must satisfy over all case results.

[cols="2,3"]
|===
| Gate | Passes when

| `Gate.allCasesShouldPass()`
| Every attempt passed. An inconclusive attempt fails the gate. This is the gate that applies when none is given.

| `Gate.passRateShouldBeAtLeast(minimumRate)`
| The share of attempts that passed is at least `minimumRate`. An inconclusive attempt counts against the rate.

| `Gate.passRateShouldBeAtLeast(evaluatorClass, minimumRate)`
| The share of the evaluator's results that passed is at least `minimumRate`. Inconclusive and not applicable results are left out of the count. The gate fails when the evaluator has no result to count. The evaluator is named by its component class.

| `Gate.targetShouldNotFail()`
| No attempt failed in the agent call.

| `Gate.guardrailShouldNotDeny(name)`
| The named guardrail denied nothing in any attempt. For a guardrail that must stay silent on legitimate traffic.

| `Gate.guardrailShouldDeny(name)`
| The named guardrail denied in every attempt. For a guardrail that must catch an attack every case carries.

| `gate.and(other)`
| Both gates hold. The verdict lists both details.
|===

The gates count attempts, not cases.
An attempt is one execution of one case, so an experiment with `repeat(3)` has three attempts per case.
`Gate.allCasesShouldPass()` then requires every case to pass in every run, and a pass rate is the share of all attempts that passed.
An attempt with an inconclusive result, or without a passed result, is inconclusive and does not pass, see <<outcomes>>.
A pass rate pools the attempts of all cases: one case that fails in every run and three cases that each fail once give the same rate.
See <<repeated-runs>>.

A failed gate does not throw.
Assert on the report, and use the rendered report as the failure message.

[#judged-batch]
=== Gating a judged batch

A judged score can differ between runs of the same reply, so hold a batch to the rate the xref:sdk:evaluators.adoc#judging[judge evaluator] passed rather than asserting on one judged case.
`Gate.passRateShouldBeAtLeast(JudgeEvaluator.class, minimumRate)` rates the evaluator over the attempts where it reached a verdict, and fails when it judged none.

[#reading-the-report]
== Reading the report

`run()` returns an link:{attachmentsdir}/testkit/akka/javasdk/testkit/eval/ExperimentRunner.EvalReport.html[EvalReport].

[cols="1,3"]
|===
| Accessor | Content

| `name()`
| The name given with `name(...)`, or the test method that ran the experiment, for example `OrderAgentEvalIntegrationTest.qualityGate`.

| `passed()`
| Whether the gate passed.

| `passRate()`
| The share of attempts that passed.

| `runs()`
| How many times every case ran, see <<repeated-runs>>.

| `results()`
| One `CaseResult` per attempt: every case in the order the cases were given, its runs ascending. A `CaseResult` carries the case id, the run, the `Evidence` and the results. `describe()` renders one attempt as in the report.

| `cases()`
| One `CaseSummary` per case, in the order the cases were given: the outcome over all runs, the passed, failed and inconclusive run counts, the case's attempts, and its requirements. The outcome is `PASSED` when every run passed, `FAILED` when every run failed, `INCONCLUSIVE` when every run was inconclusive, and `INCONSISTENT` otherwise. A `RequirementSummary` is one evaluator of the case, with the runs it passed, failed, was inconclusive and was not applicable in, and its outcome over the conclusive runs.

| `render()`
| The report as text.

| `document()`
| The report as data, a `ReportDocument` with every case, every attempt and its evidence, for tools that render their own reports.

| `reportFile()`
| The JSON file `run()` wrote to `target/eval-reports/<name>-<start time>.json`, for example `OrderAgentEvalIntegrationTest.qualityGate-20261001-101530-123.json`, holding `document()`. Every run keeps its own file. See the xref:sdk:attachment$eval-report.example.json[example report]. `ReportDocument.read(path)` reads it back. `reportDirectory(path)` on the experiment changes the directory, `withoutReportFile()` writes none. Empty when no file was written.
|===

A rendered report of a passing batch:

[listing]
----
3 cases, 1 run: 3/3 attempts passed (100%)
gate: passed — pass rate 1.00 over 3 attempts (3 cases, 1 run), required 0.90; order-lookup rate 1.00 over 3 judged attempts, required 1.00; no target failures
  judge 3/3
  order-lookup 3/3
  refund-policy 1/1 (2 not applicable)
  reply-grounding 2/2 (1 not applicable)
spend: 7 model responses, 0 tokens in, 0 out, 31 ms in total, slowest full-refund run 1 at 14 ms, over 3/3 attempts with a recorded interaction
----

Line by line:

. The cases, the runs, and the attempts that passed with their share. Inconclusive attempts follow when there are any: `3 cases, 1 run: 2/3 attempts passed (67%), 1 inconclusive`. An attempt is one case in one run, so without `repeat(n)` on the experiment the attempts are the cases.
. The gate's verdict and its detail. A combined gate lists the detail of each part. The detail counts attempts and names the runs a case failed or was inconclusive in: `failed cases [order-status (run 2)], inconclusive cases [refund (run 1)]`.
. One line per evaluator, under its component id: the attempts it passed over the attempts where it reached a verdict. The attempts where it was inconclusive or not applicable follow in brackets, for example `refund-policy 1/1 (2 not applicable)`.
. One line per guardrail that decided in the batch, for example `guardrail refund-limit: denied 1, allowed 0`. Absent when no guardrail decided.
. The spend: model responses, tokens and latency summed over the attempts with a recorded interaction, and the slowest attempt. A mocked model reports no tokens.
. `inconsistent across runs`, only when a requirement passed in some runs and failed in others: one line per such requirement with the runs it passed, failed and was inconclusive in, for example `order-status order-lookup: passed in runs 1, 3, failed in run 2`. A requirement that failed in every run is not listed here. See <<repeated-runs>>.
. After these lines, every attempt that did not pass, failed or inconclusive, with its evidence, see <<reading-a-failed-case>>.

[#reading-a-failed-case]
== Reading an attempt that did not pass

The rendered report ends with every attempt that did not pass, failed or inconclusive, and its evidence.
The evidence is what the attempt left in the ledger: the reply, the tool calls with their arguments, the model spend, and the guardrail decisions.
The report file holds more of the ledger record per attempt: the system message, the input as the model saw it, each model response with its tokens and tool calls, the model name and provider, and the value the command handler returned.

spend: 1 model responses, 0 tokens in, 0 out, 4 ms in total, slowest order-status run 1 at 4 ms, over 1/1 attempts with a recorded interaction
case order-status run 1 FAILED
  reply: Order o_42 was delivered yesterday.

  NOT_APPLICABLE reply-grounding: no order was looked up
----

An attempt that did not pass is named by its case and its run, and prints the reply, the tool calls with their arguments, the model spend, the guardrail decisions when there are any, and every result with its detail.
The reply is cut to one line of at most 200 characters.
`CaseResult.evidence()` gives the same facts as data: `reply()`, `returned()`, `toolCalls()`, `failure()`, `guardrails()`, `denied()`, and the `InteractionRecord` itself.
A `returned` line follows the reply when the command handler returned something other than the model text, for example a typed reply or a failure mapped in `onFailure`.

[#repeated-runs]
== Running every case several times

One run of a case against a real model is one sample, and a case that passes once may fail on the next run with the same input.
`repeat(n)` on the experiment runs every case `n` times in total, each time in a fresh session.

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[OrderAgentQualityIntegrationTest.java]
----
include::sdk:example$doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[tag=repeated-runs]
----
<1> Every case runs three times. The runner runs every case once, then every case again, so the attempts of one case are spread over the batch rather than sent to the model within the same seconds.
<2> The gate counts attempts: nine with three cases. 0.85 tolerates one attempt that did not pass, failed or inconclusive. 0.9 would require all nine.

The report lists the requirements that passed in some runs and failed in others under `inconsistent across runs`, see <<reading-the-report>>.
`cases()` carries the outcome of every case over all runs, and of every requirement over the runs where it was conclusive.
A requirement is one evaluator of one case, so a case whose evaluators fail in different runs is a case that failed in every run with two inconsistent requirements.

Three passes out of three do not show that a case always passes.
`n` runs cannot show a failure rate below one in `n`, and a case that fails one time in four still passes three runs out of three about four times in ten.
Choose `n` by the failure rate you need to detect, and gate on a rate rather than on a clean sweep when the model is real.

Nothing is reset between runs.
The stubs the agent's tools call serve every run, a `@BeforeEach` runs once per experiment, and state that a tool writes to an entity is still there in the next run.
A stub or an evaluator must not depend on state an attempt writes, or a side effect of run 1 reads as a failure of every later run.
The wall clock time and the model spend grow with the number of runs, and the calls of a judge are not part of the spend line.
