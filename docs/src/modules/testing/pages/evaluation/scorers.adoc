A scorer decides the verdict for one rule from one recorded run.
Every scorer implements the same one-method interface, and reports read the verdict alongside the scorer's name so a reviewer knows what decided each case.

== Overview

Every scorer implements `akka.evalkit.core.domain.Scorer` and returns a `RunOutcome` — one of `Asserted` (a pass or fail from comparison), `Measured` (a number against a threshold), `Scored` (a graded band from a rubric), `Inconclusive` (the scorer had nothing to read), `NotReached` (the run never happened), or `Failed` (the scorer itself broke).
A scorer whose evidence runs out returns `Inconclusive`, and the report keeps that case out of the pass rate.

Three families answer three different kinds of question:

* *Deterministic* reads recorded values against stated expectations.
* *Heuristic* computes a measurement from the recorded interaction and reads it against a threshold.
* *Agentic* hands the exchange to a language model and reads back a score with the model's reason.

The families run in ascending cost order — deterministic first, heuristic second, agentic last — and each family settles the confident cases so the more expensive tier only reaches the borderline ones.

== A deterministic scorer

`ToolPermission` checks that the agent called only tools on an allow list.

<1> Build the scorer with the tools the scenario allows. An empty list on both sides throws at construction — a scorer that authorises everything reports a check that examined nothing.
<2> Read the recorded tool calls into per-call findings.
Each finding names one tool and states whether it was authorised.
<3> Aggregate the findings into a `RunOutcome.Measured` carrying the share authorised, the threshold, and whether the run passed.

The scoring is proportional past the pass line, so a report can tell a run that squeaked in from one that walked in comfortably.

<2> `value()` is a share; `passed()` is the boolean the report groups by.
<3> A run that reported no latency at all is `Inconclusive` — reading zero as "instant" would put a made-up figure in the report.

NOTE: The score halves at the budget rather than stepping.
A run one millisecond over the line reads as 0.499; a run twice as slow reads as 0.
The gradient is what the tuning conversations depend on.

== An agentic scorer

`TurnFaithfulness` asks whether a reply is supported by the passages the target retrieved.
The judgment is a language reading (paraphrase, negation, partial support), so this metric ships as agentic: the customer supplies the model, evalkit supplies the system prompt.

----

----
<1> The `Assessor` is a lambda that hands the question to the customer's Agent.
The `Question` carries the task and what to read it against.
<2> `systemPrompt()` on any built-in agentic metric returns the wording the model needs to be told.
Constructing `new TurnFaithfulness(null)` only to read the prompt is idiomatic here — the prompt is static.
<3> `.responseConformsTo(Assessment.class)` enforces the JSON shape at the SDK layer.
A model that returns malformed JSON is retried before the assessor sees it.
<4> Construct the scorer with the assessor.
<5> The scorer's `score(Observation)` handles the rest: check that there is anything to ask about, call the assessor, validate the returned score is a share in `[0, 1]`, produce a `Measured`.

<1> The `MetricRef` names the scorer and its version.
The version is what a recorded score is filed under, and it changes whenever a setting change would silently redefine what "the same score" means.
<2> The scorer's `id()` is what the report row prints and what the CLI matches on `--scorer`.
<3> Return `Inconclusive` before reaching for `Measured` or `Asserted`.
A scorer that read an empty reply as failed would report a defect the target never had a chance to make.
<4> A deterministic scorer reads the reply against a stated expectation.
The regex is the expectation.
<5> `Asserted(boolean, claim, reason)` is the deterministic outcome shape.
`claim` and `reason` land in the report row so a reviewer can tell why the case decided the way it did.

== The built-in scorers, in one table

For the reference tables listing every built-in scorer and what each reads, see xref:testing:evaluation/reference/scorers.adoc[].

* 3 deterministic: `ToolPermission`, `ToolCorrectness`, `ArgumentCorrectness`.
* 12 heuristic across three groups — budget (`LatencyBudget`, `TokenBudget`, `ModelCallBudget`), format (`RegexMatch`, `LengthInRange`, `JsonValidity`), text-overlap (`ExactMatch`, `TokenF1`), retrieval-quality (`ContextRecall`, `ContextPrecision`, `ReciprocalRank`, `NormalizedDiscountedCumulativeGain`).
* 7 agentic: `TaskCompletion`, `PlanQuality`, `PlanAdherence`, `StepEfficiency`, `TurnFaithfulness`, `TurnRelevancy`, `CitationFaithfulness`.

== Testing

Every scorer tests the same way: build an `Observation` you control and read the `RunOutcome` back.
Deterministic and heuristic scorers reach no model, so they run under `mvn verify` without any provider configured.
Agentic scorers use a stub `Assessor` returning `Assessment` directly.

For the testkit shape shared with unit tests, see xref:sdk:testing.adoc[Testing SDK components].
