== Why an agent needs evaluation tests

A unit test asserts that a call returns one expected value.
An agent's reply cannot be asserted that way.
The model decides which tools to call, with which arguments, and how to word the reply, and a real model might not make the same decisions twice.
Asserting on the exact reply fails on a harmless rewording and passes on a reply that sounds right but invents an order.

An evaluation test sends the agent a fixed set of messages, the eval cases, and checks each turn with evaluators: which tools were called, in which order, with which arguments, what the reply must contain, and what a turn may cost.
Criteria that have no exact answer, such as tone, go to a model judge that scores the reply.
Because a real model varies, an evaluation counts results over the whole set and holds it to a rate, rather than holding every case to a pass.

The EvalKit is a set of utilities in the Akka TestKit for testing agents with an ordinary JUnit test.

* The agent runs in the TestKit runtime with its tools, session memory and guardrails.
* The evidence is the trace the runtime records for the turn. The test does not instrument the agent.
* With the model mocked by `TestModelProvider`, the same cases are deterministic and run in every build. Without the mock, they run against the real model on demand, with a gate on rates.
* Cases can be written in Java or derived from recorded production interactions.

This page builds an evaluation for the order agent of an online shop, from the agent to a gated batch.

== The test class

The evaluation is a `TestKitSupport` test.
It registers the stub as the agent's `OrderService` and leaves the model as configured in `application.conf`, so the agent answers with the model it uses in production.

----
include::sdk:example$doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[tag=class]

<1> The class runs only when the build sets the `eval` system property. Without it JUnit skips the class.
<2> The stub the agent's tools call.
<3> The `DependencyProvider` that serves the stub. It replaces the one the service's `ServiceSetup` creates.
<4> The orders the cases ask about. The stub is refilled before each test, so every test starts from the same orders.

Run it with the property set and the model's API key in the environment:

[source,bash]
----
mvn verify -Deval=true
----

`@EnabledIfSystemProperty` is one way to keep an expensive test out of the regular build.
A JUnit `@Tag` with a Failsafe `groups` filter, a Maven profile, or a class name the plugin does not select work as well.

== The first case

An `EvalCase` describes one turn with the agent.
It carries the message the agent receives and the evaluators that check what the agent did with it.
The first case asks where an order is and expects the agent to look the order up without refunding it.

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[OrderAgentQualityIntegrationTest.java]
----
include::sdk:example$doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[tag=status-case]
----
<1> The id names the case in the report.
<2> The message the agent receives.
<3> The evaluators. The agent must call `getOrder` with the order id from the question, must not issue a refund, and the reply must carry the order's status.

An experiment is a set of cases bound to an agent and a gate, run once for one report.

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[OrderAgentQualityIntegrationTest.java]
----
include::sdk:example$doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[tag=first-case]
----
<1> The cases. One, several, or a list.
<2> The agent's command handler. The runner calls it through the component client in a fresh session per case.
<3> Runs the cases and returns an `EvalReport`.
<4> Without a gate the report passes only when every case passes. The rendered report is the failure message, so a failed case prints its evidence.

A single case against a real model is not a reliable check.
The model may word the reply differently on another run, or call a tool it did not call before, and the case fails on that run.
The next step holds a set of cases to a rate instead.

== A batch behind a gate

Several cases run as one batch.
A `Gate` decides what the batch must satisfy over all case results.

<1> At least 90% of the cases must pass.
<2> Every declared tool argument must arrive as declared, in every case that declares one. A wrong argument is a defect even when the reply reads well.
<3> No case may fail in the agent call. An unavailable model fails the gate rather than lowering the pass rate.

The gates are combined with `and`, so all three must hold.

A rendered report of this batch:

[listing]
----
3/3 cases passed (100%)
gate: passed — pass rate 1.00 over 3 cases, required 0.90; tool-arguments rate 1.00 over 2 judged cases, required 1.00; no target failures
  tools 1/1
  tool-arguments 2/2
  forbidden-tools 2/2
  answer-contains 2/2
  tool-order 1/1
  answer-matches 1/1
  tool-call-budget 1/1
  model-call-budget 1/1
spend: 6 model calls, 123 tokens in, 321 out, 550 ms in total, slowest order-status at 489 ms, over 3/3 cases with evidence
----

The second line is the gate's verdict, with the detail of each of the three gates.
The indented lines are the pass counts per evaluator, over the cases that activated it.
The last line sums what the run spent.
