== Why an agent needs evaluation tests

A unit test asserts that a call returns one expected value.
An agent's reply cannot be asserted that way. The model decides which tools to call and how to word the reply, and a real model does not make the same decisions twice.

An evaluation test sends the agent a fixed set of messages, the eval cases, and lets evaluator components judge each interaction: the tool calls, the reply, or a criterion scored by a judge.
It counts the results over all cases and requires a minimum pass rate.

This page writes an evaluation in a form of integration test for the order agent of an online shop against the model the agent uses in production. The complete code is in the link:{sample-base-url}/doc-snippets/src/test/java/com/example/eval[doc-snippets sample, window="new"].

== The evaluators

An xref:sdk:evaluators.adoc[evaluator] is a component that judges one interaction of an agent.
Evaluators are part of the production code. You can also place an evaluator in the test sources and bind it to the agent in the test setup.
The first one checks tools called by the agent. A message that names an order must lead to a `getOrder` call. A message without an order id must lead to no tool call at all.

== The test class

The evaluation test registers the stub as the agent's `OrderService`, binds the evaluators to the agent, and leaves the model as configured in `application.conf`, so the agent and the judge answer with the model they use in production.

----
include::sdk:example$doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[tag=class]
----
<1> The class runs only when the build sets the `eval` system property. Without it JUnit skips the class.
<2> The stub the agent's tools call.
<3> The `DependencyProvider` that serves the stub. It replaces the one the service's `ServiceSetup` creates.
<4> The bindings. Each key is the component id of an evaluator, and `agents.order-agent` binds it to the agent. The `judge` entry also carries the criterion and the threshold the judge evaluator reads.
<5> The orders the cases ask about. The stub is refilled before each test, so every test starts from the same orders.

[#binding]
The bindings are the entries xref:sdk:evaluators.adoc#_binding_evaluators_to_agents[Binding evaluators to agents] describes, and a binding in `application.conf` applies in the test as well.
To keep a production evaluator out of the test, disable its binding in the test configuration with `enabled = false`.
The runner reads the bindings of the agent from the configuration the TestKit runs with and waits for one evaluation per bound evaluator.
It refuses a binding with a `sampling-ratio` below 1.0, because a sampled evaluator leaves cases without a verdict.
With `trigger-on-failure = true` the evaluator also judges an interaction that failed, for example when a tool threw. Without it, the runner does not expect the evaluator on a failed interaction.

Run it with the property set and the model's API key in the environment:

[source,bash]
----
mvn verify -Deval=true
----

`@EnabledIfSystemProperty` is one way to keep an expensive test out of the regular build.
Other options are a JUnit `@Tag` that the Failsafe `groups` filter selects, a Maven profile, or a class name outside the Failsafe include pattern.

== The first case

An `EvalCase` describes one turn with the agent.
What the agent must do with the command is stated by the bound evaluators, not by the case.

An experiment is a set of cases bound to an agent and a gate, run once for one report.

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[OrderAgentQualityIntegrationTest.java]
----
include::sdk:example$doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[tag=first-case]
----
<1> The cases. One, several, or a list.
<2> The agent's command handler. The runner calls it through the component client in a new session per case.
<3> Runs the cases, waits for the verdicts of the bound evaluators, and returns an `EvalReport`.
<4> Without a gate the report passes only when every case passes. The rendered report is the failure message, so a failed case prints its evidence.

A single case against a real model is not a reliable check.
The model may word the reply differently on another run, or call a tool it did not call before, and the case fails on that run.
The next step runs a set of cases and requires a minimum pass rate over all of them instead.
xref:testing:evaluation/gates-and-reports.adoc#repeated-runs[Running every case several times] names the cases that do not hold on every run.

== A batch behind a gate

Several cases run as one batch.
A `Gate` decides what the batch must satisfy over all case results.

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[OrderAgentQualityIntegrationTest.java]
----
include::sdk:example$doc-snippets/src/test/java/com/example/eval/OrderAgentQualityIntegrationTest.java[tag=batch]
----
<1> At least 90% of the cases must pass.
<2> The `order-lookup` evaluator must pass in every case where it reached a verdict.
<3> No case may fail in the agent call. An unavailable model fails the gate rather than lowering the pass rate.

The gates are combined with `and`, so all three must hold.

A rendered report of this batch:

[listing]
----
3 cases, 1 run: 3/3 attempts passed (100%)
gate: passed — pass rate 1.00 over 3 attempts (3 cases, 1 run), required 0.90; order-lookup rate 1.00 over 3 judged attempts, required 1.00; no target failures
  judge 3/3
  order-lookup 3/3
  refund-policy 1/1 (2 not applicable)
  reply-grounding 2/2 (1 not applicable)
spend: 7 model responses, 4310 tokens in, 212 out, 6120 ms in total, slowest full-refund run 1 at 2890 ms, over 3/3 attempts with a recorded interaction
----

The second line is the gate's verdict, with the detail of each of the three gates.
The indented lines are the pass counts per evaluator, with the attempts where the evaluator had nothing to check in brackets.
The last line sums what the run spent.
xref:testing:evaluation/gates-and-reports.adoc#reading-the-report[Reading the report] explains every line.

[#mocked]
== Running the cases with a mocked model

The same cases run without an API key when a `TestModelProvider` takes the place of the model, see xref:sdk:agents/testing.adoc[Testing agents].
The replies are then deterministic, so such a run checks that the agent, the tools and the evaluators fit together, not how good the model is.
This is useful on every build, to catch a broken tool or evaluator before the real model is involved, and to test how the evaluators react to a known bad reply.
The model of the judge agent is mocked the same way, with a `TestModelProvider` registered for the judge class, and its script answers with the JSON of the verdict record.
