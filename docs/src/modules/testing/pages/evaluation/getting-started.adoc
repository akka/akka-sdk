= Getting started with evaluation

include::ROOT:partial$include.adoc[]

:page-summary: An evaluation suite scores an Akka SDK service against a dataset. It lives under src/test/java, runs as an ordinary JUnit test, and reports pass rates per rule with the failing cases named individually.
:page-when-to-use: Use when a service is worth measuring — the reply's correctness, the tool usage, the latency budget, the faithfulness of a retrieved answer.
:page-prerequisites: An existing Maven project. Familiarity with JUnit.
:page-related: xref:testing:evaluation/scorers.adoc[], xref:testing:evaluation/scenarios-and-rules.adoc[], xref:testing:evaluation/campaigns.adoc[]

An evaluation suite is a set of JUnit tests that run a target service through a dataset of scenarios and score each reply against a rule.
The suite lives alongside the project's other tests under `src/test/java` and reads the same dependencies at test scope.
A campaign is one class in the suite, and its outcome is a report the CI job reads for regressions.

== Overview

An evaluation campaign has four parts.
The **target** is any implementation of `SystemUnderTest` — for a service on the Akka SDK, the implementation calls the service's own `ComponentClient`.
The **dataset** is a set of `Scenario` records, each naming a precursor state, a graded turn, and the outcome the target is expected to reach.
The **campaign** is a JUnit test class that assembles the dataset and the target, invokes `CampaignRunner.run(...)`, and asserts against the result.
The **runner** in `evalkit-core` walks every scenario in parallel lanes, records the interactions, and returns a `CampaignResult` that carries the assertions the campaign uses.

The suite is a test scope dependency, so a customer's production artifact carries no evalkit code.
Campaigns are gated on `-Deval=true` so `mvn verify` compiles the classes without running them; `mvn verify -Deval=true` runs them.

== Add the eval pack

`akka eval init` overlays the source tree onto the project, edits the pom to add the `evalkit` dependency at test scope, and reports what it wrote.

[listing]
----
$ akka eval init
kept   src/test/java/com/acme/checkout/eval/scorer/deterministic/package-info.java
added the evalkit dependency to pom.xml (previous kept as pom.xml.backup)
run a campaign with `mvn verify -Deval=true`

Added the eval source root to . under package com.acme.checkout.eval — 7 file(s) written, 0 kept.
----

The command is idempotent.
Running it again on a project that already declares the dependency reports "already declares" rather than editing the pom a second time; a file the customer has since written stays untouched, and the command reports each as `kept`.

The eval tree lands under `src/test/java/<groupId>.eval/`, where `<groupId>` comes from the project's pom.
For the flags that override that (`--package`, `--force`), see xref:reference:cli/akka-cli/akka_eval_init.adoc[].

== The target adapter

Every campaign talks to one `SystemUnderTest`.
The interface has two responsibilities: put the service into the state the scenario names, then submit the graded turn.
For an Akka SDK service, the implementation calls the service's own `ComponentClient` — the same client an integration test would use.

<1> The `ComponentClient` is injected the same way a service's integration tests receive it.
<2> `prepare(Precursor)` arranges the state a scenario names.
A fixture named `"signed-in"` in the scenario reads the fixture handler here.
<3> A precursor this adapter cannot arrange returns `Prepared.Failed`, which the runner records as `NotReached` — a fact about the adapter, not a verdict on the target.
<4> `submit(sessionId, userText)` speaks the graded turn.
For an Agent, that is a `.forAgent().inSession(...).method(...).invoke(...)` call.
<5> `fixtures()` declares the states the adapter can reach, so a campaign that names a fixture this adapter never declared is refused before running.

<1> The system-property gate keeps campaigns out of `mvn verify`.
The test is compiled and JUnit knows it exists; execution needs `-Deval=true`.
<2> Every scenario names an id, a precursor, the graded turn, and the outcome the target is expected to reach.
<3> The plan collects the scenarios into a campaign, sets the number of parallel lanes, and names the rubric an agentic scorer would use.

<5> `CampaignRunner.run(...)` walks every scenario, calls the adapter, scores each run, and returns a `CampaignResult`.
<6> The result carries the assertions.
`assertHeldAgainstBaseline` compares this run to a saved baseline and fails the test on regression.

== Where the parts live

[cols="1,3"]
|===
| Path | What lives there

| `src/test/java/<pkg>/eval/runner/`     | The `SystemUnderTest` adapter for this project.
| `src/test/java/<pkg>/eval/scorer/`     | Scorers, grouped by family (see xref:testing:evaluation/scorers.adoc[]).
| `src/test/java/<pkg>/eval/dataset/`    | `ScenarioSource` implementations and dataset loaders.
| `src/test/resources/eval/datasets/`    | The scenarios themselves as JSONL.
| `src/test/resources/eval/rubrics/`     | Agentic-scorer rubrics, versioned by filename.
| `src/test/resources/eval/baselines/`   | Prior runs the campaign compares against.
| `target/evalkit/reports/`              | Rendered reports (gitignored).
|===
