Every xref:sdk:exit-conditions.adoc[exit condition] is tagged with a *Definition-of-Done type* — a fixed, versioned category. The types are the scaffold the tooling walks to infer which conditions a feature needs, and the buckets that progress rolls up into. Each type is pinned to a distinct Akka observable surface, which is both what makes it checkable and what keeps the list non-arbitrary: if two types shared a surface, they would be merged.

Types are organized into three tiers by subject — the "three P's".

== Tier 1: Product

Does the software work? These are led by the developer and customer; the organization may add conditions.

[cols="1,3"]
|===
| Type | Covers

| Functional | Endpoint, event, view, and workflow behavior.
| Data Integrity | Entity state and its invariants.
| Reliability | Cluster behavior and fault injection — recovery, supervision, surviving node loss.
| Performance | Timing and throughput.
| Security & Compliance | Authorization, audit, and PII handling at runtime.
| Operability | Deployment, health, telemetry, and runtime cost.
| Experience | Browser-facing behavior — accessibility, responsiveness, and page performance. On by default; struck as a group when a service declares itself headless or API-only.
|===

== Tier 2: Project

Is the codebase healthy and standards-compliant? These are heavily organization-authored — they encode an enterprise's "way of working". Some Project conditions apply to the whole project rather than a single feature.

[cols="1,3"]
|===
| Type | Covers

| Documentation & Training | Documentation completeness, content-structure standards, training material, and changelog history.
| Repository Hygiene | Clean git history — no lingering or unmerged commits, rebased onto the base branch, branch policy honored, no orphaned dead code.
| Pipeline & Scanning | Prior commits passed CI/CD; code scanning (SAST, SCA, secrets, license) is complete and valid.
| Code & Test Health | Test coverage thresholds and test-pyramid balance, plus maintainability budgets — complexity, file size, duplication.
| Environment & Dependencies | Every dependency is identified, available, and verified, and the local environment matches the latest resolved governance and toolchain. Checked as a drift check, not a run-once flag.
|===

== Tier 3: Process

Did the AI build stay honest and efficient? These are part of the organization floor.

[cols="1,3"]
|===
| Type | Covers

| Process Integrity | Meta-guardrails on the build itself, including source-grounding — framework and API usage is cited to official documentation, with no invented APIs.
| Build Efficiency | Token-to-cost budgets and model routing for the AI build.
|===

== Ownership gradient

The tiers differ in who authors them. Product conditions are developer-led. Project and Process conditions are mostly the organization's floor — the enterprise's mandated standards — with developers adding on top. See xref:sdk:exit-conditions.adoc[Exit conditions and Definition of Done] for how provenance and the additive floor work.

[NOTE]
====
The core types are closed and versioned. Organizations extend "done" by adding conditions *within* a type, not by inventing new types.
====
