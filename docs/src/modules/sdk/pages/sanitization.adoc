== Overview

Data sanitization is a runtime-level governance capability built into Akka. Rather than relying on application code to remember to scrub PII at every integration point, you declare your sanitization policy once and the runtime enforces it automatically — across logs, agent model inputs, and tool outputs.

This matters because protecting personally identifiable information is simultaneously a legal obligation and a trust imperative. Regulations such as GDPR, CCPA, and HIPAA mandate careful handling of personal data. The EU AI Act goes further: when AI systems process personal data, organizations must be able to explain what data was used and how it was protected. Runtime-level PII scrubbing gives you a verifiable, auditable answer — sensitive information is masked before it ever reaches a model, satisfying both the right to erasure and the right to explanation.

By shifting sanitization from application logic into the runtime, you gain:

* **Consistency** — every code path an entry applies to is covered by the same policy, with nothing to remember at the call site.
* **Auditability** — governance and infosec teams can inspect a single configuration to verify what categories of PII are masked.
* **Reduced attack surface** — in the event of a breach, masked data limits exposure.

Sanitization is disabled by default. You enable it selectively through configuration, choosing exactly which categories of sensitive data to mask.

A sanitizer applies everywhere unless it says otherwise. The three application points are:

* `logs`: text written to logs
* `model-call`: text passed to the model in each model call of an agent
* `tool-result`: text passed to agent models from local tool or MCP tool output

Each sanitizer can name the points it masks at, and the agents it masks for. See <<Configuring sanitizers>>.

Text matched by a sanitizer is replaced by a mask of `*` containing the same number of characters as the original matched string.

For example, with a credit card sanitizer enabled, the following text:

[literal]
I'm having problems using my credit card 5204 46025 0000 006

Will be masked to:

[literal]
I'm having problems using my credit card *******************

Before being written in logs or passed to agent models.

=== Ad hoc sanitization

You can also mask text programmatically where it makes sense for a specific business case, for example before sending text to a third-party API or before passing it to an entity to store. To do this, xref:setup-and-dependency-injection.adoc[inject] an `akka.javasdk.SanitizerClient` into a component and call `sanitize` with the name of a configured sanitizer and the text.

A sanitizer scoped to an agent or to an application point masks the text you pass here as well. The name selects which sanitizer runs, and nothing else does. For a sanitizer that only application code uses, define `apply-at = ["client"]`, so that the runtime does not apply it anywhere on its own.

== Configuring sanitizers

You configure sanitizers as named entries of `akka.javasdk.sanitization.sanitizers`. The name is how application code reaches the sanitizer, and how it is reported. Each entry defines exactly one of:

* `pattern`: a Java regular expression matching the text to mask
* `predefined`: a built-in group of patterns, see <<Predefined groups>>
* `class`: an implementation class, see <<Sanitizer implementations>>

Each entry can also state where and for which agents it masks:

* `apply-at`: the application points to mask at, any of `model-call`, `tool-result`, `logs` and `client`, or `*`. An entry that defines no `apply-at`, or defines `*`, masks at every point it can. An agent-scoped entry cannot mask log messages, so for those it means model input and tool results. An entry with `client` masks nothing on its own, see <<Ad hoc sanitization>>.
* `agents`: the component ids of the agents to mask for. Use `*` for every agent.
* `agent-roles`: the roles of the agents to mask for. Use `*` for every agent that has a role.
* `enabled`: set it to `false` to drop the entry. A dropped entry masks nothing and constructs nothing.

An entry that defines neither `agents` nor `agent-roles` masks for every agent. An entry that defines both masks for an agent that matches either one.

The `customer-ids` entry above masks a hypothetical customer ID in the form S0123456789, so that text like:

[literal]
Customer S0847362951 reported an issue with their order

Is written to logs as:

[literal]
Customer *********** reported an issue with their order

The `logs` application point is global and cannot be combined with `agents` or `agent-roles`, but you can define the sanitizer twice with different names to enable it for all logs and for specific agents. The `client` application point cannot be combined with `agents` or `agent-roles` either.

Any other key of an entry is specific configuration for that sanitizer. An implementation reads it from the `SanitizerContext` constructor parameter, see <<Sanitizer implementations>>.

=== Predefined groups

A small set of common sanitizers is built into the Akka runtime. You select one with `predefined`:

[options="header" cols="1,1"]
|===
| Name | Description

|`EMAIL` | email addresses
|`PHONE` | International and national phone numbers
|`CREDIT_CARD`| VISA, Mastercard, American Express, Diners, Discover, JCB, and generic credit card numbers
|`IBAN`| international bank account numbers
|`IP_ADDRESS`| ipv4 and ipv6 network addresses
|===

=== Sanitizer implementations

When a regular expression cannot express what to mask, implement `akka.javasdk.TextSanitizer` and configure the class with `class`. Return the text unchanged when there is nothing to mask.

The constructor can take an `akka.javasdk.SanitizerContext`, which gives access to the entry name and its configuration, and any other injectable type, such as an `akka.javasdk.agent.ClassifierClient` to mask what a configured classifier detects.

An implementation can mask log messages, as a pattern can. The runtime calls it while it writes a log event, and the thread writing the event waits for the masked text. Keep such an implementation fast, and do not log from it.

== Performance considerations

An entry that masks at the `logs` application point is applied to every log entry. In high-throughput applications, numerous sanitization rules or complex regular expressions may impact performance. You should monitor application performance and optimize regex patterns if necessary.

== Testing sanitization

In tests you can access the sanitizer client from the `getSanitizerClient` method in `TestKit` or `TestKitSupport`, and mask with a configured sanitizer by name to assert that expected texts are masked given your service sanitizer configuration.
