`/akka:ship` is the final step of the xref:sdk:conformance-modes.adoc[Enforced flow]. It runs the in-scope xref:sdk:auditors.adoc[auditors] one last time and, if they pass, fires the terminal action the organization defined.

== Ship is organization-authored

Akka provides the mechanism; the organization writes what "ship" does. There is no fixed menu of ship profiles. A terminal action is any action or sequence the organization declares, together with the conditions that must be green before it fires:

* A solo developer might build, deploy, and activate.
* An enterprise might push to a remote repository or open a pull request, handing off to a downstream governance pipeline that owns deployment.

These are the range, not categories to choose from. See xref:reference:governance/policy-as-code.adoc[Policy as code] for how an organization authors the ship definition.

== The invariant

Regardless of what ship does, one rule holds: *ship fires only when every in-scope condition is green.* "Green or no ship" is not a policy knob — the target and its scope are configurable, but the gate is not. A ship may itself be a promotion pipeline (staging green, then promote, then production green); the same invariant applies at each stage.

== Ship scope defines what "done" guarantees

What ship targets determines which conditions can actually run, and therefore what "done" proves:

[cols="1,3"]
|===
| Ship target | What it can verify

| Deploy and activate
| The full definition of done, including live-service conditions — the running service is exercised against the specification.

| Push to repository / open a pull request
| Everything up to the handoff. Live-service conditions cannot run before deployment, so they *defer* downstream and Akka guarantees only the pre-handoff conditions.
|===

A condition a developer adds inherits the same environmental reality as the organization's: if ship has no live environment, a developer's live-tier condition defers downstream too.

== The conformance receipt

When ship completes, Akka writes a *conformance receipt* — the record of what "done" meant at the handoff:

* which conditions were green,
* which auditors ran,
* which conditions deferred, and to whom,
* any waivers in effect and their expiration.

The receipt is what makes a push-to-repository handoff trustworthy: the downstream owner sees exactly what was verified and what remains for them to check. Akka guarantees up to the handoff; the receipt carries the rest forward.

== Post-ship cleanup

In Enforced mode, a successful ship offers to shut down the local services the build-and-verify loop started — the local cluster and runtime, any mocked or fabricated dependencies, and browser or backoffice sessions. Cleanup is scoped to what this project started and never touches unrelated processes. This closes the lifecycle that `/akka:setup` opened: setup brings the local environment up, ship offers to bring it down.
