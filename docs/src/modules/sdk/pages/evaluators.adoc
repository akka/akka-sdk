== Overview

An link:{attachmentsdir}/api/akka/javasdk/evaluation/Evaluator.html[`Evaluator`] is a component that assesses agent interactions and workflow runs.
You bind it to one or more agents in configuration, and the runtime then invokes it for the interactions of a bound agent.
A workflow or an endpoint can also start an evaluation on request, see <<workflow-run>>.
Each invocation receives one subject to evaluate: an interaction, or a workflow run.
The evaluator returns a verdict, pass or fail, optionally with a score, a label, and attributes.
The runtime records the verdict in the ledger and exposes it in metrics and traces. An evaluator implements the eval control type; see xref:concepts:controls.adoc#evals[Controls] and xref:concepts:evaluation.adoc[].

You implement the evaluation once and bind it to agents or agent roles in `application.conf`. The runtime then triggers it for the interactions of those agents.
The same evaluators judge an agent in a test: xref:testing:evaluation/index.adoc[Evaluation] runs a set of eval cases against the agent and reads the verdicts of the bound evaluators.

Two kinds of evaluator exist:

* `Evaluator` handles one interaction in a single `evaluate` call. Use it when the evaluation completes in one step, for example a single judge call.
* xref:_durable_evaluators[`DurableEvaluator`] runs the evaluation as a sequence of steps with durable state, and resumes from the last completed step after a restart. Use it when the evaluation needs several calls.

Both kinds are bound to agents the same way and record the same kind of result.

NOTE: An Evaluator runs after the interaction has completed, in the background. It does not delay the agent's response, and its verdict cannot change what the agent does next. If a workflow must react to the verdict, for example retry a step that failed the evaluation, call the judge agent from the workflow, as described in xref:_reacting_to_a_verdict_in_a_workflow[Reacting to a verdict in a workflow].

== Implementing an evaluator

An evaluator extends `Evaluator`, is annotated with `@Component`, and implements `evaluate(EvaluationContext)`.
The context identifies the interaction to assess; the evaluator fetches that interaction from the xref:_the_ledger_client[ledger], reaches a verdict, and returns it through the `Effect` builder:

----
include::example$doc-snippets/src/main/java/com/example/evaluator/InteractionQualityEvaluator.java[tag=all]
----
<1> An evaluator is a component and needs a `@Component` id. The id is how the evaluator is referred to in configuration.
<2> Extend `Evaluator`.
<3> A `LedgerClient` is injected to fetch the interaction under evaluation.
<4> The subject of an evaluation triggered by a binding is a `Subject.Interaction`. Its `interactionId()` identifies the interaction; fetch its record from the ledger.
<5> `inconclusive` reports that the evaluator ran but reached no verdict, which is distinct from a failing verdict.
<6> `complete` with an `Evaluation` records the verdict.
<7> An `Evaluation` can carry a score, a label, and arbitrary attributes for downstream analysis.

The runtime creates a new evaluator instance for each evaluation, so the evaluator holds no state between interactions.

The runtime runs a limited number of evaluations of `Evaluator` components at the same time, so slow `evaluate` calls of one evaluator delay the evaluations of the other evaluators.
When `evaluate` does not return within 2 minutes, the runtime records a failed evaluation.
For an evaluation that can take longer, use a xref:_durable_evaluators[durable evaluator].

A criterion that has no exact answer, such as whether a reply is helpful, needs a model. xref:sdk:evaluators/examples.adoc[] shows evaluators that ask a judge agent for the verdict, starting with xref:sdk:evaluators/examples.adoc#judging[Scoring a reply against a criterion].

The link:{attachmentsdir}/api/akka/javasdk/evaluation/Subject.html[`Subject`] in the link:{attachmentsdir}/api/akka/javasdk/evaluation/EvaluationContext.html[`EvaluationContext`] is a sealed interface with two implementations. `Subject.Interaction` carries `agentComponentId()`, useful when one evaluator is bound to several agents, and `flowId()` when the agent ran inside an autonomous-agent flow. `Subject.Workflow` names a <<workflow-run,workflow run>>. An evaluator that handles both kinds switches over the subject.

[#outcomes]
=== Outcomes of an evaluation

The `Effect` returned by `evaluate` is one of three, and a thrown exception is the fourth outcome.
Every evaluation ends in one of them, recorded in the ledger.

[cols="1,2,2"]
|===
| Outcome | Effect | Use it when

| Verdict
| `effects().complete(evaluation)`
| The evaluator judged the interaction. `Evaluation.passed(reason)`, `Evaluation.failed(reason)` or `Evaluation.of(passed, reason)`, with an optional score and label.

| Inconclusive
| `effects().inconclusive(reason)`
| The evaluator wanted to judge and could not. The interaction failed and there is no reply, or the judge gave no usable answer. A reader treats it as a gap in the evidence.

| Not applicable
| `effects().notApplicable(reason)`
| The interaction gave the evaluator nothing to evaluate. A refund check on a turn without a refund, a tool call check when the agent called no tool. A reader treats it as neutral.

| Failed
| A thrown exception
| The evaluator could not run. The runtime logs the exception and records a failed evaluation.
|===

Keep inconclusive and not applicable apart.
Inconclusive says that a verdict is missing; not applicable says that none was due.
In the xref:testing:evaluation/gates-and-reports.adoc#outcomes[evaluation runner] an attempt with an inconclusive result does not pass, and a not applicable result does not count. A pass rate of one evaluator leaves both out.

An evaluator records one verdict per evaluation.
When one evaluator judges several criteria, combine them into one `Evaluation`: `passed` is the overall verdict, and the explanation and the attributes carry the result per criterion.
Use one evaluator per criterion when the criteria do not combine into one verdict.
Each evaluator bound to an agent adds one trigger and one ledger record for each interaction that it evaluates.

== Binding evaluators to agents

Evaluators are bound to agents under `akka.javasdk.evaluation.evaluators`, keyed by the evaluator's `@Component` id.
Each binding declares a `trigger`. The supported value is `interaction`, meaning the runtime triggers the evaluator for the interactions of the bound agent:

[source,conf,indent=0]
.src/main/resources/application.conf
----
akka.javasdk.evaluation.evaluators {
  interaction-quality-evaluator {                 // <1>
    agents {
      support-agent { trigger = interaction }     // <2>
      billing-agent { trigger = interaction, enabled = false } // <3>
    }
    agent-roles {
      customer-facing { trigger = interaction }   // <4>
    }
  }
}
----
<1> The evaluator's `@Component` id.
<2> Bind the evaluator to `support-agent`. It runs for each of that agent's interactions.
<3> A binding can be disabled, for example in a deployment override, with `enabled = false`.
<4> Bind the evaluator to every agent annotated with `@AgentRole("customer-facing")`.

Under `agent-roles`, the key `*` binds every agent that has any role.

WARNING: A `*` binding also binds a judge agent that has an `@AgentRole`. The evaluator's own call to the judge is then an interaction of a bound agent, which triggers the evaluator again, without end. Give judge agents no role, or add an entry with `enabled = false` for them under `agents`.

When an agent matches more than one entry, the runtime uses one of them, in this order:

. The entry for the agent under `agents`.
. The entry for the agent's role under `agent-roles`.
. The `*` entry under `agent-roles`.

In the example, `billing-agent` has its own entry under `agents`, and that entry is disabled. The runtime does not evaluate `billing-agent`, even though it has the `customer-facing` role.

The `enabled` setting defaults to `true`. Set `enabled = false` on an evaluator entry to disable the evaluator: the runtime evaluates no interactions of its bound agents, and a start on request, see <<workflow-run>>, fails with `IllegalStateException`. Set it on a single binding to disable only that binding.

A binding can set `sampling-ratio`, a number from 0.0 to 1.0. For each interaction of the agent, the runtime triggers the evaluator with that probability, so the evaluator evaluates about that share of the interactions. A binding can set `trigger-on-failure = true`. The evaluator then also evaluates the failed interactions of the agent, and the sampling ratio applies to them as well. The defaults are `sampling-ratio = 1.0` and `trigger-on-failure = false`. Set both keys on a binding or under `akka.javasdk.evaluation.defaults.agent`, not on the evaluator entry.

With `trigger-on-failure`, the evaluator also receives interactions that ended in a failure. The record of such an interaction can still hold model text, for example a reply that a guardrail blocked. In the evaluator, check link:{attachmentsdir}/api/akka/javasdk/ledger/InteractionRecord.html[`InteractionRecord.failed()`] before you judge the reply, and read the reason from `failureSummary()`.
The record also lists a tool call that a guardrail denied before the tool ran, with an empty response. A check such as "no refund was issued" must not treat that call as a call that ran.

The default values for evaluator entries are under `akka.javasdk.evaluation.defaults.evaluator`, and the default values for bindings are under `akka.javasdk.evaluation.defaults.agent`. A value set on an individual entry overrides the default for that entry. The entry that the runtime uses for an agent supplies all settings of the binding. A key that this entry does not set takes the default from `akka.javasdk.evaluation.defaults.agent`, not the value of a less specific entry. For example, when the `*` entry sets `sampling-ratio = 0.1` and the entry for the agent's role sets no ratio, the binding of the agent has the default ratio of 1.0, not 0.1.

The same configuration binds a xref:_durable_evaluators[durable evaluator]. The key is its `@Component` id.

=== Configuration properties of an evaluator

An evaluator can have configuration properties of its own, next to the keys the SDK reads. The SDK reserves the keys `enabled`, `trigger`, `sampling-ratio`, `trigger-on-failure`, `control-id`, `agents` and `agent-roles`, so do not use them as property names. Set the properties on the evaluator entry, or in a binding to vary them per agent:

[source,conf,indent=0]
.src/main/resources/application.conf
----
akka.javasdk.evaluation.evaluators {
  reply-length-evaluator {
    min-length = 20                                          // <1>
    agents {
      support-agent { trigger = interaction }
      billing-agent { trigger = interaction, min-length = 50 } // <2>
    }
  }
}
----
<1> A property of the evaluator. It applies to every agent the evaluator is bound to.
<2> The binding for `billing-agent` overrides it.

The evaluator reads them with `EvaluationContext.config()`:

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/main/java/com/example/evaluator/ReplyLengthEvaluator.java[ReplyLengthEvaluator.java]
----
include::example$doc-snippets/src/main/java/com/example/evaluator/ReplyLengthEvaluator.java[tag=all]
----
<1> A missing key throws, so the evaluation fails and the runtime records it as failed.

`config()` returns the binding that the runtime used for the agent, with the evaluator entry as fallback, key by key. For an agent without an enabled binding, it returns the evaluator entry. The keys `agents` and `agent-roles` are left out. The other keys the SDK reads, such as `trigger` and `enabled`, are present when the entries set them. The defaults under `akka.javasdk.evaluation.defaults` are not included, and a property of an evaluator is not allowed there. The SDK does not validate the properties of an evaluator, so a missing key fails at the first evaluation, not at startup.

A xref:_durable_evaluators[durable evaluator] reads `config()` from the running service at the start and in each step. A step that runs after a deployment with a changed configuration sees the changed configuration.

Set `control-id` on the evaluator, not on a binding, to name the control that the evaluator implements. See xref:concepts:governance-and-the-runtime.adoc#control-ids[control ids]. The runtime records the control id on each evaluation that the evaluator runs, and link:{attachmentsdir}/api/akka/javasdk/ledger/EvaluationRecord.html[`EvaluationRecord.controlId()`] returns it.

NOTE: Evaluators typically call a model, so each evaluation has a cost. In a high-volume deployment, use a deployment override to set a lower `sampling-ratio`, which evaluates a smaller share of the interactions, or to set `enabled = false`, which turns a binding off.


[#_durable_evaluators]
== Durable evaluators

For an evaluation that runs in several steps and must survive restarts, extend link:{attachmentsdir}/api/akka/javasdk/evaluation/DurableEvaluator.html[`DurableEvaluator`] instead of `Evaluator`.
Each evaluation runs as its own durable instance. The instance keeps a state of your choice across its steps and, if it is stopped for any reason, resumes from the last completed step.
Use it for composed evaluations that accumulate results from several judge calls.

A durable evaluator starts in `onEvaluation(EvaluationContext)` and progresses through step methods. Each step is a method that returns `Effect`, and an effect either transitions to the next step or finishes the evaluation.
The example has one step, which judges the interaction:

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/main/java/com/example/evaluator/TranscriptJudgeDurableEvaluator.java[TranscriptJudgeDurableEvaluator.java]
----
include::example$doc-snippets/src/main/java/com/example/evaluator/TranscriptJudgeDurableEvaluator.java[tag=all]
----
<1> Extend `DurableEvaluator` with the state type as the type parameter. This evaluator keeps no state, so it uses `Void`.
<2> Override `settings()` to set the evaluation timeout, the default step timeout, and the number of step retries. Without `settings()`, the runtime defaults apply and a failed step is not retried.
<3> `onEvaluation` is the entry point. It transitions to the first step.
<4> A step method takes no parameters, or one input parameter, and returns `Effect`. `evaluationContext()` gives the subject, the evaluation id and the configuration in every step. The step fetches the interaction from the ledger by id instead of receiving it.
<5> The judge runs in a session derived from the evaluation id, separate from the evaluated agent's session. The judge agent uses `MemoryProvider.none()`, so a retried step does not see the earlier attempt and no session memory remains after the evaluation.
<6> `complete` records the verdict and removes the evaluation instance.

Like a workflow, a durable evaluator can chain any number of steps. A step transitions to the next one with `effects().transitionTo(step)`, passes a value into a step that takes a parameter with `withInput(value)`, and keeps a state across steps with `updateState(newState)`, which the next step reads with `currentState()`. The state must be serializable with Jackson, in the same way as workflow state. Keep it small: the interaction itself stays in the ledger, and each step fetches it by id. Use the state for results that steps accumulate, for example the verdicts of several judge calls that a final step combines.

The `Effect` of `onEvaluation` and of every step is one of:

* `effects().transitionTo(step)`, optionally preceded by `updateState(newState)`: continue with the given step.
* `effects().complete(evaluation)`: record the verdict and remove the instance.
* `effects().inconclusive(reason)`: record that no verdict was reached and remove the instance.
* `effects().notApplicable(reason)`: record that the interaction gave the evaluator nothing to evaluate and remove the instance.

There is no other way to finish. When a step exhausts its retries or the evaluation timeout expires, the runtime records a failed evaluation and removes the instance.
An evaluation that has completed cannot transition further.

[#_reacting_to_a_verdict_in_a_workflow]
== Reacting to a verdict in a workflow

When a workflow must react to a verdict, for example retry a step whose result fails a check, call a judge agent from the workflow step with the component client.
Select the next step from the result of the judge.
This step asks the `LabelJudge` agent from xref:sdk:evaluators/examples.adoc[] whether the summary that a previous step wrote is good:

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/main/java/com/example/evaluator/ReviewedSummaryWorkflow.java[ReviewedSummaryWorkflow.java]
----
include::example$doc-snippets/src/main/java/com/example/evaluator/ReviewedSummaryWorkflow.java[tag=check]
----
<1> The judge runs in its own session, separate from the session of the summarizer agent.
<2> The step sends the summary and the document with the prompt of `SummarizationJudgeEvaluator`.
<3> A `good` label accepts the summary and ends the workflow.
<4> Any other label passes the explanation of the judge to the summarize step, which asks the summarizer agent for a better summary.
<5> After the last attempt, the workflow ends without an accepted summary.

A model call can take longer than the default step timeout of a workflow, so set a longer step timeout, as described in xref:sdk:workflows.adoc#_timeouts[Timeouts].

The runtime records this call as an interaction of the judge agent.
It does not record an evaluation of the interaction that the judge assessed, so the verdict does not appear in the evaluation records or in the `akka.evaluation.result` metric.

To stop a reply before it reaches the caller, use a xref:sdk:agents/guardrails.adoc[guardrail] instead.

[#workflow-run]
== Evaluating a workflow run

An evaluator bound to an agent judges a single interaction. A workflow that orchestrates several agents produces a combined result: the outcome of the entire run.
To evaluate that outcome, the workflow starts the evaluation directly with `ComponentClient.forEvaluator(evaluatorClass)`, typically from its final step.
The subject is a `Subject.Workflow`, identifying the workflow instance by its workflow ID and component ID.
You can also pass trigger attributes when starting the evaluation, such as the IDs of agent interactions from the run.

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/main/java/com/example/evaluator/EvaluatedAgentTeamWorkflow.java[EvaluatedAgentTeamWorkflow.java]
----
include::example$doc-snippets/src/main/java/com/example/evaluator/EvaluatedAgentTeamWorkflow.java[tag=all]
----
<1> The state keeps the ids of the agent interactions of the run.
<2> `withDetailedReply()` returns the reply together with the id of the interaction it came from.
<3> The final step starts the evaluation. `startEvaluation` returns the evaluation id once the trigger is durably queued. The evaluation runs in the background.
<4> The subject names this run: the workflow id and the component id of the workflow.
<5> The trigger attributes point the evaluator at the interactions to judge. An attribute value is a string, so a list of ids is one value with a separator. Pass ids, not content: the evaluator fetches the records from the ledger.

The evaluation can start before the runtime persists the step that calls `startEvaluation`. Persist the result to evaluate in an earlier step, and start the evaluation from a step that does not update state, as shown in the final step above. An evaluator that reads workflow state then sees the persisted result.

The evaluation ID is derived from the evaluator, the subject, and the trigger attributes. A retried step that calls `startEvaluation` again with identical arguments receives the same ID.
The runtime delivers the trigger at least once. For an `Evaluator`, each repeated call runs the evaluator again and records another run under that ID. A retried step can therefore run the evaluator twice.
In contrast, a durable evaluator runs once per ID while its instance exists. A repeated call returns the ID without running anything.
To evaluate the same subject again intentionally, for example after updating a prompt, pass a distinct trigger attribute such as the prompt version.

The evaluator reads the subject and the trigger attributes from the `EvaluationContext`:

[source,java,indent=0]

<1> The evaluator is not bound to an agent in configuration. The workflow starts it directly by its `@Component` ID.
<2> `Subject` is sealed. An evaluator that expects a specific type checks for it and reports any other type as not applicable.
<3> Trigger attributes passed by the workflow. If an attribute the evaluator requires is missing, report the evaluation as not applicable.
<4> Interactions of the run, fetched from the ledger by ID. Evaluators can also read workflow state through `ComponentClient` using the workflow ID.
<5> The final response of the last agent call represents the answer of the run.
<6> Verdict attributes, separate from trigger attributes. The ledger records the verdict under the workflow run with both attribute sets.

[#_the_ledger_client]
== The ledger client

The ledger is the log of recorded agent interactions and their evaluations. It is also used for console visibility and auditing.
A link:{attachmentsdir}/api/akka/javasdk/ledger/LedgerClient.html[`LedgerClient`] fetches records from it. It can be injected into any component, but in practice it is mainly evaluators that use it.

[#_optional_ledger_records]
=== Optional ledger records

Each ledger record adds database load and stored data. Turn off these records in `application.conf`:

[source,conf,indent=0]
.src/main/resources/application.conf
----
akka.javasdk.agent.ledger.records {
  tool-call-intent = false
  guardrail-allow = false
  sanitizer-no-masking = false
}
----

`tool-call-intent`:: The record that the runtime writes before each tool call, with the arguments that the runtime sends to the tool. The runtime writes the interaction record when the interaction ends. It holds the same call with the arguments from the model, which differ when an MCP `ToolInterceptor` changes them in `interceptRequest`. Without the intent, a tool call leaves no trace when the runtime stops before the interaction ends. The only exception is a tool that a before-tool-call guardrail checks while `guardrail-allow` is on: the runtime records the allow decision before the call, with the name of the tool and without the arguments. Keep the intent for a tool that performs a protected operation.
`guardrail-allow`:: The record of a guardrail decision that allows, for enforcing and report-only guardrails. Without it, the ledger has no record that the guardrail checked an interaction or a tool call that it allowed, and no allow count to compute a pass rate from. Metrics still count the decision.
`sanitizer-no-masking`:: The record of a sanitizer that masked nothing in an interaction. Without it, the ledger has no record that the sanitizer ran in that interaction. A sanitizer that masked text keeps its record.

The defaults keep all of these records. The keys also apply in dev mode and in tests, where the ledger itself is always enabled. The ledger always holds the interactions, the evaluations, and the guardrail denials and failures, so evaluators work with all three keys off. Each runtime node writes a control configuration record that lists the guardrails, sanitizers and evaluators it runs, and the keys that are off. With a key off, that record still shows that the control was active, and a reader can tell a record that the configuration skipped from a record that was lost.

=== Integration testing with the runtime

An integration test runs the service in the local runtime, so the runtime triggers the evaluator the same way it does in production. Use it in two cases:

* To test a durable evaluator. `EvaluatorTestKit` covers only `Evaluator`; there is no unit testkit for `DurableEvaluator`.
* To test that an evaluator is bound to the right agent, because the binding is read from configuration and a unit test does not see it.

The test extends `TestKitSupport` and has three parts. First, bind the evaluator to the agent in the testkit configuration and replace the models with `TestModelProvider`. Second, call the agent with `withDetailedReply()` to get the interaction id. Third, read the recorded evaluation from the ledger with `getLedgerClient()`. The evaluation runs after the agent has replied, so the test polls until the record appears.

<1> Call the agent with `withDetailedReply()` to get the interaction id.
<2> The evaluation runs in the background, so poll `getLedgerClient().getEvaluations(interactionId)` until the record appears. For a workflow run, poll `getWorkflowEvaluations(workflowComponentId, workflowId)`.
<3> Check that the outcome is a verdict before reading the `Evaluation`. A failed, inconclusive or not applicable evaluation has no `Evaluation`.
