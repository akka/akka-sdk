= Guardrails

== Overview

Guardrails are runtime-enforced checks that validate what goes into and comes out of your agents.
They protect against harmful inputs, such as jailbreak attempts and prompt injection, and damaging outputs, such as toxic language, hallucinated claims, or accidental disclosure of a competitor's product.
A guardrail can also intercept a tool call and reject it before it runs.

Unlike external validation layers that sit outside your application, Akka guardrails are **part of the runtime itself**.
You declare them in configuration, and the runtime enforces them on every interaction, whether the request targets a model, an MCP tool, or a function tool.
This distinction matters: bolt-on governance fails because it depends on developers remembering to call the right library at the right time.
When governance lives in the runtime, it cannot be bypassed, forgotten, or misconfigured by individual teams.

This architecture directly supports regulatory frameworks such as the **EU AI Act**, which requires that high-risk AI systems embed risk controls into their design rather than relying on after-the-fact auditing.
Because every guardrail evaluation is recorded in logs, metrics, and traces, you get an auditable compliance trail without extra instrumentation.

NOTE: For protecting sensitive information like PII, see xref:sdk:sanitization.adoc[Sanitization].

== Kinds of guardrail

A guardrail implements one of three interfaces. The interface sets where the runtime evaluates the guardrail:

* link:{attachmentsdir}/api/akka/javasdk/agent/ModelCallGuardrail.html[`ModelCallGuardrail`] evaluates the input to each model call. The runtime evaluates it before the first model call. It evaluates the guardrail again before each later call that sends tool results back to the model.
* link:{attachmentsdir}/api/akka/javasdk/agent/AgentResponseGuardrail.html[`AgentResponseGuardrail`] evaluates the agent's final reply, once per interaction. On an autonomous agent, it also evaluates the message of each `broadcast`, `direct`, and `submit_turn` tool call.
* link:{attachmentsdir}/api/akka/javasdk/agent/ToolCallGuardrail.html[`ToolCallGuardrail`] evaluates a function tool call or an MCP tool call before the runtime runs the tool. It sees the tool name and the raw JSON arguments.

A guardrail class implements exactly one of these interfaces.
To check several points, write one class per interface.

[NOTE]
====
An agent that returns `StreamEffect` streams its reply. The caller receives the reply before the runtime evaluates an `AgentResponseGuardrail`, so the guardrail cannot block that reply.

The service fails to start when such an agent has an `AgentResponseGuardrail` entry without `report-only = true`.
Fix the startup failure in one of these ways:

* Change the agent's command handler to return `Agent.Effect`.
* Remove the agent from the `agents` or `agent-roles` list of the entry. If the entry binds agents through `*` or an agent role, list the other agents by name instead.
* Remove the agent from the entry as above. Then add a separate entry for this agent with `report-only = true`. The guardrail then observes the reply without blocking it. The stream completes after the guardrail returns.

Do not set `report-only = true` on the existing entry. The guardrail would then stop blocking for every agent that the entry binds.

The runtime evaluates a `ModelCallGuardrail` before each model call of a streaming agent too.
A deny fails the stream. See <<Handling a denied interaction>>.
====

All three return a link:{attachmentsdir}/api/akka/javasdk/agent/Decision.html[`Decision`]:

* `Decision.Allow`: the guardrail found nothing wrong and the call proceeds.
* `Decision.Deny`: the call must not proceed. The `report-only` setting controls the outcome (see <<_configuring_guardrails>>). If false, the runtime aborts the interaction. If true, it only records the denial. On abort, the runtime returns the `reason` to the user as the failure message.
* `Decision.Fail`: the evaluation itself failed and reached no verdict. The `fail-mode` setting decides whether the interaction continues (see <<_configuring_guardrails>>). With `fail-mode = fail-closed`, the default, the runtime aborts the interaction. The runtime passes the `reason` and the `cause` to the failure handling as the message and cause of a `Guardrail.GuardrailException`. With `fail-mode = fail-open`, the interaction continues. The runtime treats three cases as `Decision.Fail`: throwing from `decide`, returning a failed `CompletionStage` from `decideAsync`, and returning `null`.

The runtime reports a `Deny` or `Fail` with a null or blank `reason` as "no reason given".
The runtime applies no timeout to a guardrail. An interaction waits forever if its guardrail never completes.
A guardrail that never completes is not a `Decision.Fail`, so `fail-mode` has no effect on it.

== Implementing an agent response guardrail

An `AgentResponseGuardrail` receives a `CallContext` with the `agentId()`, `sessionId()`, and `modelName()` of the interaction, and returns a `Decision`.
The `reply()` method returns the agent's final reply as a `Guardrail.Message.AiMessage`:

----

----
<1> Implement `AgentResponseGuardrail`.
<2> An optional link:{attachmentsdir}/api/akka/javasdk/agent/GuardrailContext.html[`GuardrailContext`] constructor parameter gives access to the guardrail's configured name and its config section. Here the guardrail reads the `search-for` property from configuration.
<3> `decide` receives the per-call `CallContext`.
<4> Return `Decision.Deny` to reject the reply, with a reason surfaced to the user.
<5> Return `Decision.Allow` to let the reply through.

The reply also carries the model's thinking in `thinking()` and provider-specific values in `attributes()`.
Both are empty when the model returns none.
On an autonomous agent, the runtime also evaluates the guardrail on the message of each call to the built-in `broadcast`, `direct`, and `submit_turn` tools.
There, `text()` holds the message, and `thinking()` and `attributes()` come from the model reply that requested the tool call.
The runtime does not evaluate the guardrail on the other built-in tools, such as `provide_prompt` and `complete_task`.

`decide` may block, because the runtime evaluates guardrails on virtual threads. To compose futures instead, override `decideAsync`. The default `decideAsync` delegates to `decide`.

== Implementing a model call guardrail

A `ModelCallGuardrail` receives the conversation that enters a model call.
Its `CallContext` holds the `systemMessage()`, all `messages()` in the conversation, and the `newMessages()` after the last `AiMessage`.
On the first model call, `newMessages()` holds the user message.
On each later call, it holds the tool results that the runtime sends back to the model.

Each message is a `Guardrail.Message` that keeps its origin: a `UserMessage`, an `AiMessage`, or a `ToolCallResponse`.
Each `AiMessage` carries the model's thinking in `thinking()` and provider-specific values in `attributes()`.
`ToolCallResponse.isError()` is true when the MCP server reported the result as an error, or when the runtime turned a failed tool call into an error result.
When the model calls several tools at once, each result is a separate `ToolCallResponse`:

== Implementing a tool call guardrail

A `ToolCallGuardrail` evaluates a function tool call or an MCP tool call before the runtime runs the tool.
`CallContext` exposes `agentId()`, `sessionId()`, `toolName()`, `toolCallId()`, `origin()`, and `arguments()`.
`arguments()` returns the raw JSON of the tool call:

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/main/java/com/example/guardrail/PaymentToolGuard.java[PaymentToolGuard.java]
----
include::example$doc-snippets/src/main/java/com/example/guardrail/PaymentToolGuard.java[tag=all]
----
<1> Implement `ToolCallGuardrail`.
<2> `decide` inspects the tool call described by `CallContext`.
<3> The runtime delivers the arguments as a raw JSON string.
<4> Return `Decision.Deny` to block the tool call before the runtime runs the tool.

The `origin()` method returns where the tool runs.

For a function tool, it returns a `ToolOrigin.FunctionTool`.
For an MCP tool, it returns a `ToolOrigin.RemoteMcp` that holds the `endpoint()` of the MCP server.
Some MCP servers take credentials in the URI, for example as a query parameter. In that case, `endpoint()` returns
the credentials too.

For an MCP tool, `toolName()` returns the name of the tool on the MCP server.
If the `RemoteMcpTools` has a `ToolInterceptor`, the runtime evaluates the guardrail after `interceptRequest`.
The guardrail then sees the arguments that the interceptor returns.

== Configuring guardrails

You enable guardrails in configuration, so you can enforce at deployment time that certain guardrails are always active.

[source,conf,indent=0]
.src/main/resources/application.conf
----
akka.javasdk.agent.guardrails {
  "profanity guard" {                                       // <1>
    class = "com.example.guardrail.ProfanityResponseGuard"  // <2>
    agents = ["planner-agent"]                              // <3>
    agent-roles = ["worker"]                                // <4>
    category = TOXIC                                        // <5>
    report-only = false                                     // <6>
    fail-mode = fail-closed                                 // <7>
    search-for = "bad stuff"                                // <8>
  }

  "tool result injection guard" {
    class = "com.example.guardrail.ToolResultInjectionGuard"
    agents = ["*"]
    category = PROMPT_INJECTION
  }

  "payment tool guard" {
    class = "com.example.guardrail.PaymentToolGuard"
    agents = ["*"]
    category = POLICY
    tools = ["transferFunds"]                               // <9>
  }
}
----
<1> Each configured guardrail has a unique name.
<2> Implementation class of the guardrail.
<3> Enable this guardrail for agents with these component ids.
<4> Enable this guardrail for agents with these roles.
<5> The type of validation, such as PII and TOXIC.
<6> If the guardrail denies or fails, the runtime either aborts the interaction or lets it continue. With `report-only = true`, the runtime lets it continue, regardless of `fail-mode`. The runtime records the result in logs, metrics, and traces in every case.
<7> Sets what happens when the evaluation fails with `Decision.Fail`. `fail-closed` aborts the interaction. `fail-open` lets it continue. The default is `fail-closed`. The setting applies only when `report-only` is false.
<8> An application-specific property, read by the guardrail from its `GuardrailContext`.
<9> Optional, for a `ToolCallGuardrail` only. Restricts the guardrail to the named tools. Without it, the guardrail sees every tool call on the selected agents. For a function tool, use `ClassName_methodName`, or the `name` set in `@FunctionTool`. For an MCP tool, use the name on the MCP server. The filter matches by name only, so it also matches a tool with the same name from another origin. Use `origin()` to tell them apart.

The `class` property sets the implementation class. The class must implement `ModelCallGuardrail`, `AgentResponseGuardrail`, or `ToolCallGuardrail`, be public, and have a public constructor. The constructor may take a link:{attachmentsdir}/api/akka/javasdk/agent/GuardrailContext.html[`GuardrailContext`] parameter, which holds the name and the config section of the guardrail. The `ProfanityResponseGuard` example reads its `search-for` property this way.

The runtime shares one guardrail instance across concurrent calls from different sessions and agents. The implementation must be thread safe.

The guardrail interface sets where the runtime evaluates the guardrail, so the configuration has no boundary setting.

=== Agent selection

You select which agents a guardrail applies to by matching `agents` or `agent-roles` configuration.

* `agents`: enabled for agents with these component ids. If `agents` contains `"*"`, the guardrail is enabled for all agents.
* `agent-roles`: enabled for agents with these roles. If `agent-roles` contains `"*"`, the guardrail is enabled for all agents that have a role, but not for agents without a role.

If both `agents` and `agent-roles` are defined, it is enough that one of them matches to enable the guardrail for an agent.

This role is defined in the `@AgentRole` annotation.

=== Names, categories, and observability

The name and the category are reported in logs, metrics, and traces. The `category` should classify the type of validation. It can be any value, but a few recommended categories are JAILBREAK, PROMPT_INJECTION, PII, TOXIC, HALLUCINATED, NSFW, FORMAT.

Set `control-id` to name the control that the guardrail implements. See xref:concepts:governance-and-the-runtime.adoc#control-ids[control ids].

== Classifier-backed guardrails

A guardrail can delegate its decision to a xref:sdk:agents/classifiers.adoc[classifier], resolved by name through `GuardrailContext.classifierClient()`.
The classifier computes the score, for example how toxic the text is, and the guardrail turns that score into an allow or a deny.
Because the classifier name comes from config, you can configure the guardrail to use a different classifier without rebuilding. The blocking `classify` call is safe here, because guardrails are evaluated on virtual threads; to compose futures instead, use `classifyAsync` and override `decideAsync`:

== Handling a denied interaction

When a `ModelCallGuardrail`, an `AgentResponseGuardrail`, or a `ToolCallGuardrail` returns `Decision.Deny` with `report-only = false`, the runtime aborts the interaction. The runtime surfaces the reason to the agent's failure handling as a `Guardrail.GuardrailException`, which you can map in `onFailure`:

----

----

An agent that returns `StreamEffect` has no `onFailure`.
For such an agent, a deny fails the stream.
The error message names the guardrail, its category, and the reason.
The error type is not `Guardrail.GuardrailException`.

With `report-only = true`, a `Deny` is recorded in logs, metrics, and traces but the interaction continues.
With `report-only = true` or `fail-mode = fail-open`, a `Decision.Fail` lets the interaction continue.
The user does not see the `reason`.
The runtime logs the `reason` as a warning in the service log. The log code is `AK-01210` for `report-only = true` and `AK-01213` for `fail-mode = fail-open`.
The runtime also records the failure in metrics, traces, and the xref:sdk:evaluators.adoc#_the_ledger_client[ledger].

== Similarity guardrail

The built-in link:{attachmentsdir}/api/akka/javasdk/agent/ModelCallSimilarityGuard.html[`ModelCallSimilarityGuard`] is a `ModelCallGuardrail`. Before each model call, the runtime compares the user message and tool results with a dataset of "bad examples". If the similarity reaches the threshold, the runtime denies the call.

This is how to configure the `ModelCallSimilarityGuard`:

[source,conf,indent=0]
.src/main/resources/application.conf
----
akka.javasdk.agent.guardrails {
  "jailbreak guard" {
    class = "akka.javasdk.agent.ModelCallSimilarityGuard"
    agents = ["planner-agent", "weather-agent"]
    category = JAILBREAK
    threshold = 0.75
    bad-examples-resource-dir = "guardrail/jailbreak"
  }
}
----

Here, it is using predefined examples of jailbreak prompts in `guardrail/jailbreak`. Those have been incorporated from https://github.com/verazuo/jailbreak_llms/[https://github.com/verazuo/jailbreak_llms, window="new"], but you can define your own examples and place in a subdirectory of  `src/main/resources/`. All text files in the configured `bad-examples-resource-dir` are included in the similarity search.

You can use this for other things than jailbreak attempt detection.

== Testing

Guardrails run in integration tests the same way they run in production. Configure the guardrail in `src/test/resources/application.conf`, run the agent with `TestKitSupport`, and use a `TestModelProvider` to produce text that triggers or passes the guardrail. A denied interaction surfaces as a `GuardrailException`, which the agent handles as shown in <<Handling a denied interaction>>.
