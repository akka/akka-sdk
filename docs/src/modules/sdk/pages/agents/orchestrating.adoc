= Multi-agent orchestration

include::ROOT:partial$include.adoc[]

Several agents that work toward a common goal need a *supervisor* that decides which agent runs and in what order. A xref:sdk:workflows.adoc[Workflow] is the supervisor when the sequence of agent calls is fixed in code, and an xref:sdk:autonomous-agents.adoc[Autonomous Agent] coordinator is the supervisor when the model decides which agent runs next. The supervisor pattern and how to choose a supervisor are explained in xref:concepts:ai-orchestration-patterns.adoc[Multi-agent coordination], and the coordination patterns in xref:concepts:ai-orchestration-patterns.adoc#coordination-patterns[Coordination patterns].

[NOTE]
====
This page covers workflow-based orchestration of request-based xref:sdk:agents.adoc[Agents]. For model-driven coordination (delegation, handoff, teams, moderation) without writing a workflow, see xref:sdk:autonomous-agents.adoc[Autonomous Agents] and the xref:sdk:autonomous-agents/coordination.adoc[coordination patterns].

To choose between the two, see xref:concepts:ai-orchestration-patterns.adoc#_choosing_a_supervisor[Choosing a supervisor].
====

== Workflow-driven orchestration

First, look at how to define a workflow that orchestrates several agents in a predefined steps. It uses both the `WeatherAgent` and the `ActivityAgent`. First it retrieves the weather forecast and then it finds suitable activities.

<2> Weather forecast is retrieved by the `WeatherAgent`, which must extract the location and date from the user query.
<3> The forecast is stored in the state of the workflow.
<4> The forecast is included in the request to the `ActivityAgent`.
<5> The final result is stored in the workflow state.

In image:concepts:steps-4.svg[width=20] we explicitly include the forecast in the request to the `ActivityAgent`. That is not strictly necessary because the agents share the same session memory and thereby the `ActivityAgent` will already have the weather forecast in the context that is sent to the AI model.

The workflow runs these steps durably: a failed call is retried by the step's recovery strategy, and a restarted workflow continues from its current step. See xref:sdk:agents/calling.adoc#_drive_the_agent_from_a_workflow[Drive the agent from a workflow].

== Model-driven orchestration

When the orchestration sequence itself is a model judgment, the supervisor is an xref:sdk:autonomous-agents.adoc[Autonomous Agent] coordinator. The coordinator declares a xref:sdk:autonomous-agents/capabilities.adoc#delegation[`Delegation`] capability listing the worker agents it may call. The runtime exposes each worker to the coordinator's model as a tool. The model picks which worker to invoke based on the workers' `@Component` descriptions and what previous calls returned. The runtime persists task state, retries failed steps, and bounds the loop by an iteration limit.

Workers stay as plain request-based xref:sdk:agents.adoc[Agents]. They do not know they are being orchestrated; the coordinator handles the routing.

<3> Declare the accepted task type. `maxIterationsPerTask` bounds the model loop as a safety net.
<4> List the workers the coordinator may delegate to. `Delegation.to` accepts both request-based Agents and other Autonomous Agents.

The model picks workers based on their `@Component` descriptions, so a worker's description should describe what it is for, not how it is invoked. The `WeatherAgent` advertises itself as the source of weather information:

== Combining the two approaches

The two approaches are not mutually exclusive. A workflow can invoke an xref:sdk:autonomous-agents.adoc[Autonomous Agent] from any of its steps, the same way it invokes a request-based Agent. This fits scenarios where the overall sequence is fixed but a particular stage benefits from model-driven coordination. For example, a research stage where a coordinator delegates to several specialists, or a review stage that runs as a team or a moderated conversation. The workflow keeps the durable state machine across stages, while the Autonomous Agent handles the elaboration within a stage.

A step that waits for an Autonomous Agent is subject to the step timeout, and a step that times out does not stop the agent. If the agent can run longer than the step timeout, let the step only start the task: store the task id in the workflow state and end the step. A Consumer on the task events (`@Consume.FromEventSourcedEntity(TaskEntity.class)`) then sends the result to the workflow when the task completes.

Because the agent keeps running after a step timeout, do not terminate it from a step that can time out. A stopped agent instance id cannot be reused, so choose the instance id for each attempt in an earlier step and commit it to the workflow state before the step that starts the agent.
