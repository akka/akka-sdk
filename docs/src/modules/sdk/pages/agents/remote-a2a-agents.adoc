= Remote A2A agents
:page-component-type: agent
:page-summary: A remote A2A agent is an agent in another system that your service calls over the Agent2Agent (A2A) protocol, with credentials and TLS settings that you configure by name.
:page-when-to-use: Calling an agent that another team or vendor runs, and that publishes an Agent Card.
:page-related: sdk:agents/extending.adoc, sdk:mcp-endpoints.adoc, sdk:setup-and-dependency-injection.adoc
:page-prerequisites: An Akka project and the URL of the remote agent's Agent Card.
:page-persona: builder-developer, builder-ai-ml

include::ROOT:partial$include.adoc[]

A remote A2A agent is an agent that runs outside your service and speaks the Agent2Agent (A2A) protocol. The remote agent publishes an Agent Card, which is a JSON document that names the agent, lists its skills, and says how to reach it. A skill is one task that the agent can do. Your service calls the agent with `A2aClient`, which reads the Agent Card, sends the requests, and applies the credentials and TLS settings that you configure for that agent.

This page describes how an agent offers the skills of a remote agent to its model as tools, how to name a remote agent in configuration, how to give your service credentials for it, how to set the certificates that TLS uses to reach it, how to require a signed Agent Card, how to choose the skills and the timeout of the tools, how a tool hands a long remote task to a workflow, and how a workflow step calls a remote agent and waits for its task.

Autonomous agents take no part in A2A. An xref:sdk:autonomous-agents.adoc[autonomous agent] does not call remote A2A agents. A request-based agent that offers remote A2A agents as tools can still be a worker of an autonomous agent.

[#remote-agents-as-tools]
== Remote A2A agents as tools

An agent can offer the skills of a remote A2A agent to its model as tools. Pass one or more `RemoteA2aAgent` instances to `a2aAgents` in the effect of the agent, as you pass remote MCP servers to `mcpTools`.

----
include::example$doc-snippets/src/main/java/com/example/a2a/ClaimsAssistantAgent.java[tag=a2a-agents]
----
<1> `a2aAgents` takes one or more remote agents.
<2> `RemoteA2aAgent.named` takes a name configured under `akka.javasdk.a2a.remote-agents`. The tool calls use the credentials and TLS settings of that configuration. See <<naming-remote-agents>>.
<3> `RemoteA2aAgent.fromCard` takes the URL of an Agent Card. The tool calls use no credentials and no custom TLS settings.

`RemoteA2aAgent.fromService` takes the name of another Akka service in the same project that has an A2A endpoint. The agent reaches the service by its name, as `RemoteMcpTools.fromService` reaches an MCP endpoint, and the calls carry the identity of the calling service, so the `@Acl` of the other service can allow it. The tool calls use no credentials and no custom TLS settings.

When the agent handles a request, it reads the Agent Card of each remote agent. The client caches the card, as <<naming-remote-agents>> describes. The agent offers each skill on the card to the model as one tool:

* The name of the tool is the name of the remote agent and the id of the skill, joined by `_`, for example `claims_claim-status`. For a remote agent from `named`, the name is the configured name. For a remote agent from `fromCard` or `fromService`, the name is the name of a configuration under `akka.javasdk.a2a.remote-agents` with the same `card-url`, or else the `name` on its Agent Card. A remote agent therefore has the same name whether your code gives it by name or by URL. Characters that model providers do not accept in tool names become `_`. A name longer than 64 characters is shortened and ends with a hash of the full name.
* The description of the tool is the description of the skill, followed by the names of the skill and of the remote agent.
* The tool takes a required `message` string and an optional `data` object. The agent sends the message as a text part and the data as a data part.

When the model calls the tool, the agent sends the message to the skill with `SendMessage`. The agent uses its session id as the A2A context id, so the remote agent can keep one conversation for each session. The agent returns the reply to the model as text:

* A message returns its text parts. A data part becomes its JSON text. A file part becomes a line with its file name and media type, and its URL when it has one.
* A completed A2A task returns the parts of its artifacts and of its status message.
* An A2A task that failed, was rejected or was canceled returns a text that starts with `Error:` and names the state.
* An A2A task that has not finished, such as a submitted or working task, or a task that needs input, returns the id and the state of the task. The agent does not wait for the task to finish. To receive the outcome of such a task later, see <<hand-off>>.

The agent stores the tool call and its result in session memory and records them in the interaction log, as for any tool.

A failed call does not fail the agent request. When the remote agent answers with an error, does not answer within the timeout, or cannot be reached, the model receives a text that starts with `Error:` and describes the failure. The model can then try again or answer without the remote agent. A tool call without a message gets the same kind of text. The result does not carry the error flag that an MCP tool error carries.

When the Agent Card of a remote agent cannot be read, for example because the agent is unreachable or its card is not signed as <<signed-cards>> requires, the agent logs a warning and offers no tools of that remote agent for this request. The model is called with the other tools, and the next request reads the card again.

The agent request fails before the model is called in two cases:

* The settings of a remote agent are not valid, or `named` gives a name that is not configured. The request fails with `IllegalArgumentException`.
* The name of a tool is the same as the name of a function tool of the agent, or of another skill. The request fails with `IllegalArgumentException`. Use `withAllowedSkills` to leave out a skill whose name clashes. See <<skills-and-timeouts>>.

A `ToolCallGuardrail` can allow or deny each call. The origin of a call to a remote A2A agent is `ToolCallGuardrail.ToolOrigin.RemoteA2a`, which carries the name of the remote agent as the tool names use it, the URL of its Agent Card, and the id of the skill. A guardrail can match the agent by its name or by its card URL. See xref:sdk:agents/guardrails.adoc#_implementing_a_tool_call_guardrail[Implementing a tool call guardrail].

<1> `A2aClient` is injected into the constructor.
<2> `forAgent("claims")` reads the settings of `akka.javasdk.a2a.remote-agents.claims`. It throws `IllegalArgumentException` when the name is not configured or its settings are not valid.
<3> `A2aMessage.user` creates a message from the client with one text part and a new message id. The `with` methods set the other fields, such as the context id.
<4> `send` takes the id of a skill and a message. A2A has no field for the skill, so the client sends the id as `skillId` in the metadata of the request. Without a skill id, `send(message)` leaves the choice to the remote agent. Call `inContext` on the request to continue a conversation with a context id.
<5> The reply is a task or a message. `A2aSendMessageResponse` is a sealed interface, so a `switch` covers both cases.

Each method of `RemoteA2aAgentClient` returns a request that is not yet sent: `card()`, `send(...)`, `getTask(taskId)` and `cancel(taskId)`. Send it with `invoke()`, which blocks for the reply, or with `invokeAsync()`, which returns a `CompletionStage`, as with the requests of `ComponentClient`. `stream(...)` returns a `Source` of the events, and the request starts when the stream is materialized.

For a one-off call, pass the URL of an Agent Card to `forCardUrl`. To call the A2A endpoint of another Akka service in the same project, pass its name to `forService`. An agent that you give by URL or by service has no credentials and no custom TLS settings, and takes its timeouts from `akka.javasdk.a2a.defaults`. For this reason, the `defaults` cannot hold credentials: the service fails to start when `akka.javasdk.a2a.defaults.auth.type` is not `none`.

The settings of a remote agent are:

[cols="2,1,4",options="header"]
|===
| Setting | Default | Meaning

| `card-url`
|
| The URL of the Agent Card. It must start with `http://` or `https://`.

| `timeout`
| `60s`
| The longest time to wait for the agent to answer a request. For a streamed response, the limit applies to the start of the response.

| `card-refresh`
| `10m`
| How long the client uses a cached Agent Card before it fetches the card again.

| `poll-interval`
| `30s`
| How often the service asks for the state of a remote task that it follows without push notifications. See <<workflow-step>>.

| `auth`
| `type = none`
| Credentials. See <<credentials>>.

| `ca-bundle`, `client-certificate`, `client-key`, and their `-file` forms
|
| TLS settings. See <<tls>>.

| `require-signed-card`, `card-signing-key`, `card-signing-key-file`, `card-jwks-url`
| `false`
| A signed Agent Card. See <<signed-cards>>.
|===

The client reads the Agent Card on the first call and caches it. It then chooses a protocol binding from the interfaces that the card lists. The client uses the JSON-RPC binding when the card lists it, and the HTTP+JSON binding otherwise. When the card lists neither binding, every call fails with `A2aClientException`.

Each request carries an `X-Akka-Caller` header that identifies the calling component, and the `A2A-Version` header. A call that runs inside a traced request also carries the trace headers.

A call fails with one of two exceptions:

* `A2aRemoteErrorException` means that the remote agent answered with a protocol error. Its `code()` is the JSON-RPC error code, for example `-32001` for a task that does not exist. Its `reason()` is the A2A reason, for example `TASK_NOT_FOUND`, when the remote agent reported one.
* `A2aClientException` covers every other failure, such as an unreachable agent, a timeout, a rejected credential, a failed TLS handshake, or a reply that is not valid A2A. `A2aRemoteErrorException` is a subclass of `A2aClientException`.

[#credentials]
== Credentials for remote agents

The `auth` setting of a remote agent chooses how the service proves its identity. The client sends the credentials on every request to the agent, including the request for the Agent Card.

The client sends credentials only to `https://` URLs, and to `http://` URLs on `localhost` for local development and tests. `forAgent` throws `IllegalArgumentException` when the `card-url` or the `token-url` of an agent with credentials is another `http://` URL. A call fails with `A2aClientException` when the Agent Card lists an interface at such a URL.

Take secret values from environment variables with an optional substitution, such as `${?POLICIES_API_KEY}`. Do not write secrets in `application.conf`. To supply the variables to a deployed service, see xref:operations:projects/secrets.adoc[]. An optional substitution for a variable that is not set leaves the setting out. When the setting is required, such as `client-secret`, `forAgent` throws `IllegalArgumentException` with a message that names the missing setting.

=== OAuth 2.0 client credentials

With `type = oauth2-client-credentials`, the client gets an access token from the token endpoint and sends it as a bearer token. The `scope` setting is optional.

.{sample-base-url}/doc-snippets/src/main/resources/application.conf[application.conf]
----
include::example$doc-snippets/src/main/resources/application.conf[tag=a2a-remote-agent-oauth]
----

The client requests a token with a form post of `grant_type=client_credentials` and, when you set it, the `scope`. By default, the client sends the `client-id` and the `client-secret` in an HTTP Basic `Authorization` header (`client_secret_basic`). For a token endpoint that expects them in the form instead, set `token-endpoint-auth-method = "client_secret_post"`. It reuses the token until 30 seconds before the token expires. When the token lives for less than one minute, the client refreshes after half of its lifetime. When the token endpoint does not give a lifetime, the client assumes five minutes. Calls that start at the same time share one token request.

When the remote agent answers a request with status 401, the client discards the token, requests a new one, and sends the request again once. A second 401 fails the call.

[#tls]
== TLS and client certificates for remote agents

A remote agent at an `https://` URL is reached over TLS. By default, the client verifies the certificate of the agent against the certificates that the Java runtime trusts, and checks that the host name of the URL matches the certificate. The settings below change this for one agent. They apply to the Agent Card and to the calls.

[source,hocon,indent=0]
.{sample-base-url}/doc-snippets/src/main/resources/application.conf[application.conf]
----
include::example$doc-snippets/src/main/resources/application.conf[tag=a2a-remote-agent-tls]
----

`ca-bundle`:: One or more PEM certificates of the authorities that signed the certificate of the agent. The bundle replaces the certificates that the Java runtime trusts for this agent. Use it when the agent has a certificate from a private authority.

`client-certificate` and `client-key`:: The certificate chain and the private key that the service presents when the agent requires mutual TLS. Put the certificate of the service first, followed by any intermediate certificates. Set both settings or neither.

Each of the three settings holds PEM text. To read the PEM text from a file instead, set the setting with `-file` appended to its name, such as `ca-bundle-file = "/etc/claims/ca.pem"`. Set one form of a setting, not both. Passing the PEM text in an environment variable avoids a file in the container image.

The token endpoint of OAuth 2.0 client credentials has its own TLS settings, because it is usually another server than the agent. By default, the client verifies the token endpoint against the certificates that the Java runtime trusts and presents no client certificate. For an identity provider with a certificate from a private authority, or one that requires mutual TLS, set `auth.token-ca-bundle`, `auth.token-client-certificate` and `auth.token-client-key`, or their `-file` forms. They take the same values as the settings above.

The private key must be an unencrypted PKCS#8 key, which starts with `-----BEGIN PRIVATE KEY-----`. The key can be an RSA, EC or Ed25519 key. `forAgent` throws `IllegalArgumentException` for a key in another format. The `openssl pkcs8 -topk8 -nocrypt` command converts a PKCS#1 or SEC1 key.

A TLS failure, such as an untrusted certificate, a certificate for another host name, or a missing client certificate, fails the call with `A2aClientException`. The message of the exception names the cause that the TLS layer reported.

[#signed-cards]
== Requiring a signed Agent Card

An Agent Card can carry JSON Web Signatures of its content. To use a remote agent only when its card is signed by a key that you trust, set `require-signed-card = true` and give the key in one of two ways:

`card-signing-key`:: The public key as PEM text, which starts with `-----BEGIN PUBLIC KEY-----`. `card-signing-key-file` names a file that holds it instead. The client accepts a signature made with this key, whatever its key id.

`card-jwks-url`:: The URL of a JSON Web Key Set. The client fetches the key set without the credentials of the agent, and accepts a signature whose key id names a key in the set. The client never follows a `jku` that the card itself names.

The client checks the card each time it fetches it. A card that has no valid signature fails every call with `A2aClientException`, and no request reaches the agent.

To require signed cards from every remote agent, including the agents that your code gives by URL or by service, set `require-signed-card = true` under `akka.javasdk.a2a.defaults`. Those agents are checked against the `card-signing-key`, `card-signing-key-file` or `card-jwks-url` that you set in `defaults`. When `defaults` sets none of them, no key is trusted for those agents, and every call to them fails with `A2aClientException`. A named agent takes the setting from `defaults` too, and must then have a key of its own or one in `defaults`.

[#skills-and-timeouts]
== Choosing skills and timeouts

By default, the agent offers every skill on the Agent Card to the model. Each tool adds to the request that the model reads, and a remote agent can have skills that your agent must not use. `withAllowedSkills` offers only the skills with the given ids, given as a set or as arguments. The model cannot call a skill that the agent does not offer. When the set names a skill that the Agent Card does not list, the agent logs a warning.

`withTimeout` limits how long a tool call waits for the reply of the remote agent. It replaces the `timeout` of the configuration for the requests of this agent, including the request for the Agent Card. When the time passes, the model receives a text that starts with `Error:`.

[#hand-off]
== Handing long remote tasks to a workflow

A remote skill can take minutes or hours, which is longer than a tool call should wait. `handOffTasksStillWorkingAfter` limits how long a tool call follows the remote task before it hands the task to a workflow.

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/main/java/com/example/a2a/ClaimReviewAgent.java[ClaimReviewAgent.java]
----
include::example$doc-snippets/src/main/java/com/example/a2a/ClaimReviewAgent.java[tag=hand-off]
----
<1> A tool call follows the remote task for at most 30 seconds.

With this setting, the tool call works as follows:

. The agent sends the message to the skill with `returnImmediately`, so the remote agent answers as soon as it has accepted the task.
. The agent reads the task until it ends or needs input, for at most the hand-off time. When the task ends or needs input in that time, the model receives the reply as <<remote-agents-as-tools>> describes.
. When the task is still working after the hand-off time, the model receives a text with the id of the task, which says that the task continues in the background. The agent request then continues without the remote agent.
. A workflow that Akka adds to your service follows the remote task, in the way that <<workflow-step>> describes for your own workflows.
. When the remote task ends or needs input, the workflow reads the task and adds its outcome to the session memory of the agent. The outcome is a user message that names the task id and the tool. The model reads it with the next request in the same session.

The outcome goes to the session memory that Akka provides for the agent, keyed by the session id. Akka writes it even when the agent's current request is still running, so it can appear in the history before the end of that request.

The workflow is a built-in component, like the session memory, and Akka registers it in each service that has an agent.

[#workflow-step]
== Calling a remote agent from a workflow step

A xref:sdk:workflows.adoc[workflow] calls a remote agent when the exchange is fixed in code, runs for minutes or hours, or must stop for a person. A step sends the message with `A2aClient` and pauses. `notifyWorkflow` delivers the later updates of the remote task to a command of the workflow, which resumes it.

[source,java,indent=0]

----
include::example$doc-snippets/src/main/java/com/example/a2a/ClaimAssessmentWorkflow.java[tag=send]
----
<1> `notifyWorkflow` takes a method reference of the component client. The reference names the workflow by its id and the command that receives the updates. The command takes an `A2aTaskUpdate`.
<2> The client sends the message with `returnImmediately`, so `invoke` returns as soon as the remote agent has accepted the task. The reply carries the task as it is then.
<3> The step pauses with a timeout. The timeout handler runs when no update resumes the workflow in time.

The reply is not delivered to the command. When the reply is a message, or a task that has already ended, no updates follow, so the step handles the reply itself.

When the task in the reply has not ended, each later change of the task is delivered to the command:

[source,java,indent=0]
.{sample-base-url}/doc-snippets/src/main/java/com/example/a2a/ClaimAssessmentWorkflow.java[ClaimAssessmentWorkflow.java]
----
include::example$doc-snippets/src/main/java/com/example/a2a/ClaimAssessmentWorkflow.java[tag=update]
----
<1> The command receives each update. `A2aTaskUpdate` is a sealed interface, so a `switch` covers both kinds.
<2> `A2aTaskArtifactUpdate` carries an artifact of the task. The workflow keeps it in its state and stays paused.
<3> `A2aTaskStatusUpdate` carries a new status. A completed task ends the workflow.
<4> A status that does not end the task, such as working, leaves the workflow paused.
<5> The timeout handler of the pause.

Akka follows the remote task in one of two ways:

Push notifications:: When the Agent Card of the remote agent says that it sends push notifications, and your service has a public URL, the client registers a push notification configuration on the task. Its URL points at an endpoint that Akka adds to your service, and it carries a token that is bound to the workflow and the task. The endpoint refuses a notification whose token does not match, and accepts notifications from any caller otherwise, because the remote agent runs outside your project. Right after it registers the configuration, Akka reads the task once, to catch a change that happened before the registration.

Polling:: When the remote agent does not send push notifications, or your service has no public URL, a workflow that Akka adds to your service asks for the task with `GetTask` every `poll-interval` of the remote agent, until the task ends or needs input. The workflow pauses between two requests, so the polling continues when the service restarts.

Set the public URL of your service, and the poll interval of a remote agent, in `application.conf`:

[source,hocon,indent=0]
.{sample-base-url}/doc-snippets/src/main/resources/application.conf[application.conf]
----
include::example$doc-snippets/src/main/resources/application.conf[tag=a2a-push]
----

`akka.javasdk.a2a.push.public-url` is the base URL at which remote agents reach your service. When it is empty, Akka uses `akka.javasdk.a2a.endpoint.public-url`. When both are empty, the service polls. The notification URLs are under `/a2a-push/` on that base URL, so the route of your service must reach that path from the remote agents.

Delivery is at least once. An update that a command already received for the same task is not delivered again: a status is known by its state, its timestamp and the id of its message, and an artifact by its id and its content. A command can still receive an update twice when the service fails between the delivery and recording it, so make the command safe to repeat. When a delivery of a push notification fails, the endpoint answers with an error and the remote agent retries, as its push notification policy allows. A failed delivery while polling is retried at the next poll.

When a task needs input, the remote agent waits for the next message on the task. Send it from a step with `withTaskId` on the message, and call `notifyWorkflow` again to follow the task further. Akka does not register a second push notification configuration for the same workflow and task.

The workflows and the entity that follow remote tasks are built-in components. Akka registers them in a service that has an agent, or a component that takes `A2aClient` in its constructor. It registers the push notification endpoint only when the service also has a public URL.

[#testing]
== Testing agents that call remote A2A agents

`MockA2aAgent` is a remote A2A agent for tests. It runs a server on a free local port, serves an Agent Card, and answers each skill with a reply that you choose. Start it before the TestKit and name it in the settings with `withMockedA2aAgent`, so that `RemoteA2aAgent.named` and `A2aClient.forAgent` reach it. Give the agent a `TestModelProvider` as xref:testing:integration.adoc[] describes, so that the test calls no model.

<1> The name of the tool is the name of the remote agent and the id of the skill, joined by `_`.
<2> `received` lists the messages that the mock has received, with the skill id, the text, the first data part, the context id and the task id. Call `reset` after each test to clear them.

A reply is one of these:

`Reply.text(text)`:: A message with one text part.
`Reply.data(map)`:: A message with one data part.
`Reply.workingThenCompleted(duration, text)`:: A task that is working when the mock accepts it. After the duration, `GetTask` finds it completed, with an artifact that has one text part. Use it to test <<hand-off>> and <<workflow-step>>.
`Reply.failed(message)`:: A task that has failed, with the message as the text of its status.
`Reply.error(message)`:: A JSON-RPC error. The agent under test receives `A2aRemoteErrorException`, or a tool result that starts with `Error:`.

A message that names no skill goes to the first skill. A message that names a skill that the mock does not have gets an invalid parameters error.

The mock does not send push notifications, and its Agent Card says so. A workflow that follows a task of the mock therefore polls for it. Set a short `poll-interval` for the remote agent in the test, as the tests of the a2a-agents sample do, and wait for the outcome with Awaitility. The mock does not check credentials and serves plain HTTP on `localhost`, so it tests the calls of an agent but not its credentials or TLS settings.

The link:{sample-base-url}/a2a-agents/README.md[a2a-agents sample] has two services. Its `claims-assistant` service calls the other service once as a tool and once from a workflow step, and its tests use `MockA2aAgent` as the remote agent.
