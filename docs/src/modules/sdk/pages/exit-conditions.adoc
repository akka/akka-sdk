Spec-driven development treats "done" as something the system can check, not a judgment call. A feature is done when a defined set of conditions is met, and every condition is backed by a check the tooling can run. This page explains the model.

== The three layers

Akka Specify separates "done" into three layers, each with a distinct owner and purpose:

[cols="1,2,2"]
|===
| Layer | What it is | Who authors it

| *Definition of Done*
| The business statement of done, in the customer's own terms ("greetings are personalized", "the service survives a node loss").
| The project owner and the organization.

| *Exit condition (EC)*
| The technical translation of a Definition of Done item into a precise, binary `pass` predicate over an observable surface.
| Derived by the tooling; refined by the developer.

| *Auditor*
| The executable check that evaluates an exit condition and returns a verdict.
| Akka (built-in) or the organization (custom).
|===

The layers roll up in the other direction. An auditor produces a verdict; verdicts determine each exit condition's status; exit-condition statuses aggregate into a *Definition-of-Done type* status. The result is that a developer sees progress in business language ("Reliability: covered", "Functional: 2 of 3 met") while the machine works in precise, checkable conditions underneath.

== Exit conditions are binary

Every exit condition resolves to a single boolean `pass`. There is no "mostly done". If a condition cannot be expressed as a binary predicate over an observable surface — an endpoint response, entity state, a build result, a git state — it is not yet an exit condition; it is a Definition of Done item still waiting to be made precise.

This is what makes the definition of done auditable: the full set of conditions is either met or it is not, and the tooling can say which.

== Definition-of-Done types

Every exit condition is tagged with a *Definition-of-Done type* — a fixed, versioned category such as Functional, Data Integrity, Reliability, or Repository Hygiene. Types are organized into three tiers by subject: *Product* (does the software work), *Project* (is the codebase healthy and standards-compliant), and *Process* (did the AI build stay honest and efficient).

Each type is pinned to a distinct Akka observable surface, which is what lets the tooling both check a condition and, during xref:sdk:conformance-modes.adoc[the DEFINE step], infer which conditions a feature needs. See xref:sdk:definition-of-done-types.adoc[Definition-of-Done types] for the full taxonomy.

== Provenance: where a condition comes from

Every exit condition carries a *provenance* that determines whether a developer can change it:

[cols="1,3"]
|===
| Provenance | Meaning

| `akka-intrinsic`
| A guarantee the Akka platform provides (observability, resilience, scalability). Always on, asserted green, and never authored by the developer.

| `recommended-default`
| A best-practice condition from the default library. On by default; a developer can strike it if it does not apply.

| `corporate`
| A condition inherited from the organization's governance floor. Locked — a developer can add stricter conditions but cannot remove it.

| `developer`
| A condition the developer adds for this feature, on top of everything above.
|===

Done is *layered and additive*: the organization sets a floor, and developers add to it. A developer can always tighten "done", never loosen what the platform or the organization mandated. See xref:sdk:conformance-modes.adoc[Conformance modes] for how the floor is enforced.

== How a condition resolves

When the tooling evaluates the definition of done, each exit condition resolves to one of these states:

[cols="1,3"]
|===
| State | Meaning

| ✓ green
| The auditor ran and the condition passed.

| ✗ red
| The auditor ran and the condition failed.

| ○ open
| The condition has no runnable auditor yet, or needs a human sign-off.

| ⟳ deferred
| The auditor cannot run in this environment (for example, a live-service check before deployment) and is exported downstream to where it can.

| asserted
| The condition is guaranteed by the platform (`akka-intrinsic`) and is trusted green without re-running a check.
|===

Deferral is what lets "done" travel. A push-to-repository handoff cannot run live-service auditors, so those conditions defer downstream and are recorded in a *conformance receipt* rather than failing. See xref:sdk:auditors.adoc[Auditors] for how each condition is bound to a check, and xref:sdk:shipping-and-receipts.adoc[Shipping and receipts] for how deferred conditions are carried across a handoff.

== Where you see it

The full set of conditions — grouped by tier, with provenance, lock status, and resolution state — is the *definition-of-done manifest*. It is shown when you define a feature and whenever you run `/akka:status`, so the entire contract is visible on one screen. See xref:sdk:conformance-modes.adoc[Conformance modes] for the workflow that drives every condition to green.
