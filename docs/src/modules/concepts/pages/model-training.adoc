Training specializes an open-weight base model for one use case on your data. Promotion decides when the trained model takes traffic for that use case, and grading after promotion decides when it is retrained or reverted.

The cost of a task is the price per token multiplied by the number of tokens, and a frontier API fixes both. A smaller model trained for one task lowers the price per token, because it runs on accelerators that you allocate, and it often lowers the tokens per task, because it needs less prompt context to stay on the task. The trade only holds if the smaller model does the task at least as well. This page explains how a model is trained, how it is measured against the model it would replace, and how it moves into traffic. The trainer documentation defines each term in detail: see xref:optimize:concepts.adoc[Training concepts].

== How it works

=== Base models

A training run starts from a base model: an open-weight model that its publisher trained named by its repository and pinned to a commit. Each deployment allows a fixed set of base models that its hardware and training engines support. You select an allowed model to prepare it for training, evaluation or serving, and selecting it registers it.

=== Training data

A dataset is a set of examples in chat format. The artifact registry holds each dataset under a name, with numbered versions that never change and aliases that you can move between versions. A run records the exact version it resolved, so moving an alias later does not change what a past run trained on. Training and evaluation datasets are kept separate, because an example in both inflates the score.

Training data comes from the traffic of the use case:

* Captured exchanges of the use case, including the answers that the frontier model gave. See xref:concepts:capture-and-grading.adoc[].
* Sessions: raw conversation corpora that you upload, including OpenTelemetry traces from agents that do not send their traffic through the gateway.
* Curation: a judge scores each exchange of a set of sessions, and the exchanges that score at or above a threshold become a dataset.

Personal data and secrets are scrubbed from the data before training, and a scrub failure is reported as an incident. Training runs on accelerators in your environment, including environments with no connection to the internet, so the data does not leave it.

=== Training methods

[cols="1,2,2", options="header"]
|===
| Method
| Learns from
| Suits

| Supervised fine-tuning (`sft`)
| The assistant messages in the dataset
| Tasks where every example has a known correct output, such as classification or extraction, including answers recorded from a frontier model

| Reinforcement learning (`grpo`, `gspo`)
| Sampled completions that a reward scores
| Tasks where an answer can be checked but there is no single correct text, such as generating SQL that returns the right rows
|===

A reward is a weighted sum of terms. A term can compare JSON labels, call a function in a scoring bundle, ask a model, or reuse the grader of the training project. A reinforcement run can start from an adapter that supervised fine-tuning produced.

=== Training projects, runs and snapshots

A training project is the training record of one use case. It names the evaluation dataset and the grader that every candidate is scored with, and its name is the namespace that its models are registered under.

A run is one training operation: one dataset, one base model, one configuration. The configuration covers what decides the trained model, such as the method, the learning settings and the reward. The execution settings, such as devices and save interval, do not change the result, so two runs with the same configuration and base model are comparable. A run has a training budget, the number of optimizer updates it may make.

The trainer runs as durable operations on Akka. A run can be paused and resumed, and each resumption is a new attempt of the same run, with the same identity, metrics and cost accounting. A snapshot is a verified, immutable save from an attempt. A branch starts a new run from an exact snapshot of a parent, with its own identity, training budget and outputs, to try a different configuration without changing the parent. A pipeline submits curate, train and evaluate stages together, and each stage has a durable identity, so an interrupted pipeline resumes without repeating finished stages.

=== Offline evaluation

An evaluation is one scoring of one model against one dataset with one grader. The score belongs to the evaluation, not to the model, so a model can be evaluated many times.

* A _baseline_ is the score of the model the use case uses now, or of the base model, on the same dataset with the same grader.
* A _candidate_ is a trained model, registered from a run or a snapshot, that is scored against the baseline.
* A _comparison_ scores one source snapshot and several branch models with one pinned dataset, grader and completion limit, so they are compared under the same conditions.

=== Registries

Two registries hold models, with different jobs:

* The _artifact registry_ stores datasets, scoring bundles and models. Each named artifact has immutable versions and movable aliases, and the registry records every move of an alias.
* The _model registry_ of your organization is an index of the models it sanctions, not a store of weights. Each entry has a lifecycle from candidate to active, deprecated and retired, and carries conditions that a person signs off, waives for a time or strikes, with attestations of evaluations run elsewhere. Retiring an entry ends the sanction and does not delete the weights.

[#_promotion]
=== Promotion

A new model is promoted only when its quality on the use case is at least the baseline and its token use drops by the target that the improvement policy sets. The comparison that justified the decision is saved to the ledger. See xref:concepts:specification.adoc[] for the improvement policy.

A promoted model moves into traffic in stages, under the routing policy of its use case:

. _Shadow_: a copy of a share of the traffic goes to the new model, and its answers are graded and not returned.
. _Canary_: a share of real traffic goes to the new model, and its answers are returned.
. _Fleet_: the new model serves the use case.

In the artifact registry, promotion moves the `champion` alias of the named model to the new version, and in the model registry it makes the candidate active. Because every alias move is recorded, the previous version is one move away.

=== After promotion

A promoted model is still graded on live traffic. Model drift, a fall in its graded quality as the traffic of the use case changes, starts retraining on newer data. A model whose quality slips below the baseline is reverted: the routing policy rolls back and the alias moves back to the previous version.

== Guarantees

[cols="2,3,2", options="header"]
|===
| Failure or situation
| What Akka does
| Precondition

| A dataset alias moves after a run starts
| The run keeps the exact version it resolved.
| None.

| A run is interrupted
| Resuming creates a new attempt of the same run from its latest committed snapshot.
| The run saved a snapshot.

| An upload of a snapshot is interrupted
| The snapshot is not listed and cannot be restored from.
| None.

| A pipeline stops part way
| Resuming continues from the unfinished stage without repeating finished ones.
| None.

| A comparison has failed targets
| It reports the completed results and declares no winner.
| None.

| A promoted model slips below the baseline
| Traffic returns to the previous model.
| The use case is graded after promotion.
|===

== Choosing between supervised and reinforcement training

[cols="1,2,2", options="header"]
|===
| Attribute
| Supervised fine-tuning
| Reinforcement learning

| What it needs
| Examples with a correct answer
| A reward that can score any answer

| Cost per step
| One pass over the examples
| Several sampled completions, each scored

| Use when
| Good answers already exist, for example from a frontier model
| Answers can be checked but vary, or the recorded answers are not good enough to copy
|===

== Limits and trade-offs

* A deployment allows a fixed set of base models, and you cannot add to it.
* The training methods are supervised fine-tuning, GRPO and GSPO.
* A trained model is specialized for one use case. It is promoted for that use case only.
* A snapshot that holds only training state, with no adapter weights, cannot be registered as a model.
* A trainer endpoint serves a model for testing with your own requests, not for production traffic, and reserves devices until it is deleted or stops after its idle timeout. Production traffic reaches a model through a model endpoint. See xref:concepts:model-serving.adoc[].
* A use case that cannot be graded cannot be promoted onto a trained model, because there is nothing to compare against the baseline.
