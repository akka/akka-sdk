Multi-agent coordination is how several agents work toward one goal under a supervisor that decides which agent runs, when, and with what context. Models perform best with focused context. As a task grows, one agent's context fills with too much information, too many concerns and competing objectives. Splitting the work across agents scopes each agent's context so it can work with clarity. It also allows parallel work, and lets each agent use the model that suits it: a small, fast model for triage, a stronger model for complex reasoning, or a model trained for one domain.

== How it works

=== The supervisor

In many AI frameworks, agents call other agents directly. That makes sample applications easier to write, but it is a design compromise that is not ready for production. Consider an activity recommendation application with a weather agent and an activity agent. The weather agent retrieves the forecast for when the user wants to plan an activity and passes it to the activity agent. If the weather agent is coded to call the activity agent, it must always call it, and it cannot be reused in any other flow.

In Akka, agents stay small and do one thing, and a supervisor composes them. The supervisor decides which agents are called, in what order, whether they run concurrently, and what to do with their outputs. This is the supervisor pattern: a central supervisor coordinates worker agents, which do not communicate with each other directly. Agents stay simple and reusable, and reliability concerns such as durable steps, retries and failure handling live in one place.

Akka has two supervisors:

* A xref:sdk:workflows.adoc[Workflow] supervises agents from outside, with explicit steps that you write. Use it when the orchestration sequence is fixed in code.
* An xref:sdk:autonomous-agents.adoc[Autonomous Agent] supervises through declared coordination capabilities: delegation, handoff, teams and moderation. The runtime drives the loop and the model decides which agent runs next. Use it when the sequence itself is a model judgment.

Both run on the Akka runtime with the same durable execution, retries and record. The coordination tools that the runtime offers an Autonomous Agent's model are durable and mediated by the platform.

=== Route communication through a supervisor

The corollary of the supervisor pattern is a rule about how agents communicate. Inside a service, route coordination through a supervisor rather than having one agent call another from its own code. An agent that reaches another agent directly fixes the supervision structure in place, so it can no longer be composed into other flows. A call made outside a supervisor also gives up the supervisor's retries and durable steps.

Agents can call agents in other services or frameworks over A2A or MCP. Make those calls from the supervisor, as a workflow step or a tool, so that they get the same retries and record. See xref:tools-and-protocols.adoc[] and xref:sdk:component-and-service-calls.adoc[].

=== When to use several agents

A well-designed single agent with the right tools can do a lot. Multi-agent patterns add overhead in tokens, coordination and complexity. Consider several agents when:

* Accumulated context is degrading performance.
* The context of one subtask is contaminating other work.
* A single perspective is limiting the quality of the solution.
* The agent's tools or prompt are too broad to be effective.
* Subtasks are independent and could run in parallel.
* Explainability and auditability are requirements. Distinct agents with clear roles make reasoning auditable.

Several agents also allow more dynamic behavior. Each run is shaped by the interplay between agents rather than by one initial prompt. The trade-off is predictability: the more dynamic the coordination, the harder it is to anticipate and test what the system does for a given input. Start with the simplest approach that works, and add agents when there is evidence that one agent is reaching its limits. It can also be worth experimenting with several agents early to understand the trade-offs, particularly when explainability or auditability matters.

=== Patterns

A supervisor applies one of four coordination patterns, or a blend of them: sequential, delegative, collaborative and emergent. Each pattern decides which agent is active, how much runs in parallel and what context each agent sees. The patterns, their examples, how to decompose work into agents and how patterns compose are explained in xref:coordination-patterns.adoc[].

== What crosses an agent boundary

Each Autonomous Agent keeps a private session with its full iteration history, tool calls and intermediate reasoning. None of it is shared automatically. What crosses from one agent to another is narrower, and it depends on the pattern:

Handoff:: The source agent writes a summary into the handoff. That summary, with the summaries of any earlier handoffs, is added to the next agent's context.

Delegation:: The worker starts fresh, with the subtask's instructions and attachments only. The coordinator receives the typed task result and nothing else. The worker's iterations and tool results stay with the worker.

Team:: Members share a task list and a point-to-point message channel. Each member sees only the messages addressed to it and changes to the task list. There is no shared transcript.

Moderation:: The moderator sees the full transcript. Each participant builds a private view of the entries delivered to it on each turn, plus the moderator's prompt for that turn.

With request-based agents, a shared session is the boundary: every agent that uses the session identifier sees the history it is allowed to see. The ways to scope context, by focus, relevance, isolation and independence, are explained in xref:agent-memory.adoc#_context_management[Context management].

== Waiting for a person

Some plans stop at a decision that a person makes: an approval, a correction or missing input. A workflow supervisor pauses at that step and waits, for hours or days if needed, without holding resources. The person's answer arrives as a command that resumes the workflow at the step where it stopped. Because the paused state is durable, the wait survives restarts and deployments.

With an Autonomous Agent, the decision is a task that no agent is assigned to. The tasks that depend on it wait until a person, through an endpoint, or another system completes or fails it. An approval gate between drafting and publishing is built this way, with the person's decision as the task's typed result. A running Autonomous Agent can also be suspended, resumed or terminated from outside.

How the wait is kept durable is explained in xref:durable-execution.adoc[]. The authority that a named person holds over a decision is a control; see xref:controls.adoc[]. The xref:sdk:workflows.adoc#_pausing_workflow[Pausing a workflow] section shows a workflow that waits for a person to accept a transfer.

== Guarantees

[cols="2,3,2", options="header"]
|===
| Failure or situation | What Akka does | Precondition

| A worker agent call fails
| The supervisor retries the step or the delegated task by its recovery strategy, then runs its failure handling.
| The agent is called from a workflow step or a coordination capability.

| The service restarts during coordination
| The workflow resumes at its current step, or the Autonomous Agent recovers its tasks and continues its loop.
| None.

| A coordinator loops without finishing
| The iteration limit fails the task.
| The limit is configurable for each task type.

| A person takes days to decide
| The paused workflow or the open task waits without holding resources and survives restarts.
| None.
|===

== Choosing a supervisor

[cols="1,2,2", options="header"]
|===
| | Workflow | Autonomous Agent

| Who decides the sequence
| Your code
| The model

| Model interaction in a step
| At most one round trip
| Several iterations

| Retries and compensation
| Explicit policies for each step, and compensation of external effects
| Retries and iteration limits from the runtime

| Use when
| The sequence is fixed, you want explicit retry policies or compensation, or the orchestration crosses service boundaries over A2A or MCP
| The model decides what to consult, which specialist to ask, or whether to iterate, based on what earlier steps returned
|===

Both give the same durable execution, retries and record.

== Limits and trade-offs

* Every agent added costs tokens and coordination time.
* Dynamic coordination is harder to predict and test than a fixed sequence.
* Each pattern has its own trade-offs; see xref:coordination-patterns.adoc#_limits_and_trade_offs[Coordination patterns].
