A distributed system is any system that distributes logic or state across more than one process. Agentic systems, microservices and edge applications are all distributed systems, and they need more than scalable infrastructure. They must stay responsive under load and under failure, scale with demand and remain maintainable as they grow. Akka applies a set of distributed-computing principles to the nondeterminism of concurrency, distribution and failure.

Akka makes the inherent complexity of the problem first-class in the programming model: the _nondeterminism_ of distributed systems and the _stochastic_ nature of large language models (LLMs). Hiding that complexity behind abstractions that leak later, when the system reaches production, adds _accidental complexity_. Accidental complexity that is not kept under control raises the cost of maintaining, understanding and extending a system, and of running it.

== Properties of a distributed system

Distributed systems can run in any location: on your development machine, in the cloud, at the edge, embedded in a device, or across several of these. Combined, the following properties make a system responsive.

[cols="1,3", options="header"]
[.compact]
|===
| Property | Definition
| Elasticity
| The system adjusts its resources automatically, scaling up or down to handle changes in workload.
| Resilience
| The system continues to function, and recovers quickly, when parts of it fail.
| Agility
| The system adapts to new requirements or changes in its environment with little effort.
| Responsiveness
| The system responds to users and events in a timely manner. This is the property the others serve.
|===

== The Reactive Manifesto and the Reactive Principles

Akka's design follows the {url-ext-reactive-manifesto}[Reactive Manifesto, window="new"] and the {url-ext-reactive-principles}[Reactive Principles, window="new"].

The Reactive Manifesto defines four traits of a well-architected distributed system:

[cols="1,3", options="header"]
[.compact]
|===
| Trait | Description
| Responsive
| The system responds in a timely manner. Responsiveness underpins usability and the other traits.
| Resilient
| The system stays responsive when parts of it fail. This applies to every user-facing system, not only to mission-critical ones.
| Elastic
| The system stays responsive under varying workload, scaling up or down as needed.
| Message-driven
| The system uses asynchronous message passing to set a boundary between components. This gives loose coupling, isolation and location transparency.
|===

The Reactive Principles turn these traits into guiding principles for design:

[cols="1,3", options="header"]
[.compact]
|===
| Principle | Description

| Stay responsive
| Respond in a timely and consistent manner, so that users can rely on the system and its behavior is predictable.

| Accept uncertainty
| Expect nondeterminism in a distributed system, and build designs that tolerate it.

| Embrace failure
| Treat failure as a first-class concern, with fault tolerance and recovery built into the architecture.

| Decentralize
| Distribute responsibility across components and teams, to avoid single points of failure or contention.

| Isolate state
| Encapsulate state and protect it from concurrent access, to avoid race conditions and allow scaling.

| Communicate via messages
| Use asynchronous message passing to decouple components, for concurrency, fault tolerance and scalability.
|===

Akka turns these principles into concrete mechanisms: durable in-memory state with event sourcing, streaming view projections, replication across regions and clouds, CRDT-based data coordination, cluster membership and sharding.

== Patterns the platform is built on

The foundation of Akka is described in the {url-book-principles-and-patterns}[O'Reilly technical guide _Principles and Patterns for Distributed Application Architecture_, window="new"], by Akka's founder Jonas Bonér. It covers the patterns that Akka applies:

* Event sourcing and CQRS, for reliable state management and auditability. See xref:state-model.adoc[] and xref:views.adoc[].
* Event-driven communication, coordination and integration. See xref:delivery-guarantees.adoc[].
* Consistency boundaries, with commands separated from side effects, to keep behavior deterministic under concurrency and to balance strong and eventual consistency.
* Location transparency, for a dynamic topology, fault tolerance and elastic scaling.
* Autonomous stateful agents and services with guarantees over time, to keep a system of distributed agents consistent.
* Back-pressure and flow control, so that communication channels between services or agents do not become bottlenecks or fail under data overload. See xref:streaming.adoc[].
* Failure signaling and supervision, so that systems heal themselves and degrade gracefully.
* Automatic replication of agents and services for failover, redundancy and scale.

In the SDK these patterns appear as xref:sdk:agents.adoc[Agents], xref:sdk:event-sourced-entities.adoc[Entities], xref:sdk:views.adoc[Views], xref:sdk:http-endpoints.adoc[Endpoints], xref:sdk:workflows.adoc[Workflows] and xref:sdk:consuming-producing.adoc[Consumers]. The runtime backs them with actors, event-sourced persistence, replication between regions, durable streaming projections and sharded clusters.

== Strong and eventual consistency

Consistency in Akka follows the consistency boundary. Inside one entity or workflow instance, state is strongly consistent: one instance owns the state, processes one command at a time, and a read through its own command handler returns the latest write. Across instances, data moves by events, and anything built from those events is eventually consistent. A xref:views.adoc[view] reflects a change after the entity has persisted it, not in the same transaction, and a region that receives replicated events sees them after the region that wrote them.

Designing with this boundary in mind is what lets a system scale without global locks. Put the data that must change together in one entity, and accept eventual consistency for reads and reactions that span entities, services or regions.

== Applied to multi-agent AI

Multi-agent AI systems combine the _nondeterminism_ of distributed systems with the _stochastic_ behavior of AI models, particularly those based on LLMs. Many autonomous, stateful and often long-lived agents need orchestration, streaming, memory and behavior over time, while you still reason about the system as a whole. Akka's approach to multi-agent architectures includes:

* Actor-based isolation and concurrency control for stateful xref:sdk:agents.adoc[agents] that reason and act independently while they coordinate with others.
* Asynchronous messaging and streaming that separate computation from communication, for flow control and resilient communication between agents. This matters for latency-sensitive inference and decisions.
* Replicated stateful agents that restart and recover in place.
* Short-term (session) and long-term memory built into the agent on durable in-memory storage, so that an agent can replay its history from event logs and recover, reflect, reason and explain past behavior.
* Dynamic scaling and routing through automatic sharding and cluster management.
* Loose coupling and evolution through schema-versioned messages and contract-first APIs.
* Replication between regions based on CRDTs, for shared knowledge and eventual consistency without global locking.

== Why it matters

Agentic systems and cloud-native services built on unstable foundations become brittle architectures that fail under real conditions. Akka applies principles and patterns that anticipate failure, load, inconsistency and change, so that a system of many autonomous agents, or a set of business-critical services, behaves predictably in production.
