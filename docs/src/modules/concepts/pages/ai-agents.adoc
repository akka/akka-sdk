An agent is a component that calls an AI model to perform a task, with session memory, tools and governance supplied by the runtime. Agents perceive their environment through the input and context they receive, decide with the help of a model, and act through tools and the components they call. The degree of human intervention varies from none, where the agent is fully autonomous, to a person approving each action the agent takes.

A model call is slow compared with a function call, costs money for each token, can fail, and does not return the same answer twice. An agent in production also needs the history of the conversation, the tools it may use, and a record of what it did. In Akka, the runtime provides these to every agent, so the agent code declares what it needs and the runtime does the rest.

== How it works

Akka has two agent components. Both use the same model configuration, function tools, MCP integration, session memory and guardrails. They differ in who drives the work.

=== Request-based Agent

An xref:sdk:agents.adoc[Agent] handles one request and returns one response. Its command handler returns an effect that declares the model to use, the system message and user message, the session memory settings and the tools the model may call. The runtime then sends the request to the model, runs any tools the model asks for, and returns the reply. One request can include several tool calls before the model produces its final answer.

You do not give an Agent an instance identifier. You give it the identifier of the session it takes part in. Several agents with different component identifiers can work in the same session and share its history. See xref:agent-memory.adoc[].

An Agent is a small, single-purpose component. It should do one thing, with a single goal, and it may use any knowledge and model inference to reach that goal. Real applications rarely do only one thing, so agents work together under a supervisor. A xref:sdk:workflows.adoc[Workflow] that calls an Agent as one of its steps gives that call retries, timeouts and recovery. See xref:durable-execution.adoc[].

=== Autonomous Agent

An xref:sdk:autonomous-agents.adoc[Autonomous Agent] runs as a durable process that works on typed tasks. Each task has its own identity, instructions and result schema. You declare the agent's description, the task types it accepts, the tools it can use and its coordination capabilities. The runtime drives the model through a decision loop until each task is done:

* The task succeeds when the model produces a result that conforms to the task's result schema.
* The task fails when the model reports that it cannot make progress. The runtime records the reason.
* An iteration limit ends a task that reaches neither outcome.

A task exists independently of the agent that works on it. It can be created in advance with dependencies on other tasks, queried by clients while it runs, and handed between agents. Its typed result outlives the agent that produced it. Agent and task state are persisted at each step, so work survives crashes and restarts, and the agent is stateless from your point of view.

Coordination is part of the Autonomous Agent's definition. An agent can declare that it delegates subtasks to workers, hands off work to peers, leads a team that shares a task list, or moderates a turn-taking conversation. The runtime offers each capability to the model as a tool. See xref:ai-orchestration-patterns.adoc[].

A running Autonomous Agent can be suspended, resumed and terminated from outside. Suspending stops the agent at the next iteration boundary, and resuming continues with the tasks still in its queue.

=== Models and tokens

An agent declares its model rather than hard-coding a provider, so you can change the provider or the model without rewriting the agent. See xref:sdk:model-provider-details.adoc[].

Most agents call large language models (LLMs). An LLM predicts text: each token it streams back is the token it predicts to come next. An agent can stream those tokens to its client as they arrive, typically over server-sent events, so a chat interface shows the answer while it is generated. An agent can also ask the model for structured output, such as JSON, and map it to a typed result.

When you consume a model as a service, you usually pay for each block of tokens. You need control over how often an agent calls the model and how many tokens each call spends. Session memory compaction, tool-call limits and iteration limits all bound that spend, and xref:models.adoc[] explains how traffic can be routed to a smaller model.

Not every agent needs an LLM. As you build teams of agents, look for work that a smaller, task-specific model does as well. A smaller model costs less and often responds faster.

=== Prompts and context

An agent talks to a model through prompts. A prompt is natural language input that tells the model the role it plays, how it should respond, for example as JSON, and what the task is. The quality and detail of the prompt can make the difference between a good result and a bad one, which is why prompt engineering has become a discipline of its own.

Here is a sample prompt:

[source,text]
----
You are a friendly and cheerful question answerer.
Answer the question based on the context below.
Keep the answer short and concise. Respond "Unsure about answer"
if not sure about the answer.

If asked for a single item and multiple pieces of information
are acceptable answers, choose one at random.

Context:
 Here is a summary of all the action movies you know of. Each one is rated from 1 to 5 stars.

Question:
  What is the most highly rated action movie?
----

The agent supplies everything except the question. The context in the prompt is how an agent adds knowledge the model does not have. Retrieval-augmented generation (RAG) works this way: the agent retrieves relevant data, for example from a vector database, and adds it to the prompt.

Prompts can be fixed in code or loaded from the built-in prompt template entity. A template can change at runtime without a restart or a redeployment, and because it is an entity, its full change history is kept. See xref:sdk:agents/prompt.adoc[].

=== Governance and the record

Each model call names the agent that made it. The runtime applies the agent's guardrails before and after the call. It saves the interaction and its tool calls as records in the ledger, and the verdicts of its controls as evidence. See xref:controls.adoc[] and xref:evidence.adoc[].

=== Evaluation

Model answers are non-deterministic, so a test cannot expect one exact reply. Instead, you evaluate the agent: you run it through a set of eval cases, built-in evaluators check each reply and the tool calls the agent made, a model judge can score the replies, and a gate decides whether the results are good enough. See xref:evaluation.adoc[] and xref:testing:evaluation/index.adoc[Evaluation].

== Guarantees

[cols="2,3,2", options="header"]
|===
| Failure or situation | What Akka does | Precondition

| A model call fails or times out
| The agent's failure handler returns a fallback response. When a workflow step calls the agent, the step is retried by its recovery strategy.
| A failure handler is defined, or the agent is called from a workflow step.

| The service restarts while an Autonomous Agent works on a task
| Agent and task state are recovered, and the decision loop continues from its last persisted iteration.
| None.

| The model keeps requesting tools
| The number of tool-call steps between a request and the final answer is capped, and the request fails at the cap.
| The cap is configurable.

| A task never reaches a result
| The iteration limit fails the task.
| The limit is configurable for each task type.

| A conversation spans several requests
| Each user message and model reply is stored in session memory and added to the next request.
| Session memory is enabled, which is the default.
|===

== Choosing between Agent and Autonomous Agent

[cols="1,2,2", options="header"]
|===
| | Agent | Autonomous Agent

| Execution model
| Request and response
| Durable process loop

| Model interaction
| One round trip, with tool calls
| Several iterations until the task is done

| Orchestration
| External, from a Workflow
| Built in, driven by the model

| Unit of work
| The command handler's return value
| A task with a typed result and its own lifecycle

| Use when
| The interaction is request and response, you need fine control over each prompt, or a fixed sequence of steps runs in a Workflow.
| The work is open-ended, the model decides what to do next, several agents coordinate, or results must be tracked outside one request.
|===

A standalone Agent is lighter than an Autonomous Agent, which carries durable orchestration state and a task queue. Once an Agent is combined with a Workflow, the two weigh about the same, and the choice rests on whether code or the model decides the sequence.

== Limits and trade-offs

* A request-based Agent does not run multi-step work on its own. Compose it with a Workflow for anything that outlives one request.
* An Autonomous Agent's behavior depends on the model's decisions, which makes it harder to predict and test than a fixed sequence.
* Tokens cost money and add latency. Every iteration, tool call and line of history adds to both.
* Suspending an Autonomous Agent does not interrupt the iteration in progress. Terminate it to stop a task at once.
* Some model providers do not accept every input type, such as multimodal tool results. See xref:sdk:model-provider-details.adoc[].

Whether you are starting out with AI or brushing up on terms that appear more and more in development work, this video is a good place to start.
