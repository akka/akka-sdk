= Views and CQRS
:page-summary: A view is a read model that Akka builds from entity events, workflow state or topic messages, so that you can query across many instances by any attribute.

A view is a read model that Akka builds and keeps up to date from a stream of changes, and that you query with a SQL-like language. An entity answers questions about itself, by its ID. Questions that span many entities, such as "all orders for this customer" or "every device in a region", need a different shape of data. Command Query Responsibility Segregation (CQRS) is the pattern of keeping that read side separate from the write side, so that each can be shaped and scaled for its own job. In Akka, entities and workflows are the write side and views are the read side.

== How a view is built

A view subscribes to a source of changes and turns each change into rows in its own table. The sources are:

* the events of an Event Sourced Entity,
* the state changes of a Key Value Entity,
* the state changes of a Workflow,
* events consumed from another Akka service,
* messages from a topic on a message broker.

You write an update handler, a `TableUpdater`, that receives each change and returns an effect: update the row, delete it, or ignore the change. The runtime stores the rows, maintains the indexes your queries need, and runs the queries. Because the view keeps its own copy of the data, the read side scales independently of the write side, and several views can project the same events into different shapes.

A view can also start from an entity's snapshot instead of replaying all of its events, which shortens the time to build a view over long-lived entities.

== Querying a view

Each query is a method on the view with a query string. A query can return one result, a list, or a page of results, and it can transform rows into a different result type. A query can also stream its results to the caller. The receiver sets the pace, so a large result does not have to fit in memory. A streaming query can stay open and emit every later change that matches the query, which you can pass on to a client through a gRPC endpoint or an HTTP endpoint with server-sent events. Streamed updates are a convenience for clients; they do not guarantee delivery, and are not a way to propagate changes between services.

== Consistency

Views are eventually consistent. A view is updated after the entity has persisted a change, not in the same transaction, so a query can return data that is a short time behind the entity. During failures, such as network instability, the delay can be longer than in normal operation. In the end, every change becomes visible.

This has a direct consequence for design: do not read your own write through a view in the same request that made the write. If an endpoint writes to an entity and must return the result, return it from the entity's reply.

== Delivery to a view

Changes are delivered to a view at least once. A change can be delivered again after a network failure, a restart or a rebalance.

For views built from Event Sourced Entities, Key Value Entities, Workflows or another Akka service, Akka tracks the sequence number of each source instance and does not apply a change it has already applied. Update handlers for these sources do not need their own deduplication. For views built from a topic, there is no such sequence number, so make the update handler idempotent or deduplicate in it. See xref:delivery-guarantees.adoc[].

A view built from a Key Value Entity receives the latest state, not every intermediate state. If the entity is updated several times in quick succession, some intermediate states can be skipped during restarts or rebalances; the latest state is always reflected.

== Views and regions

Views are not replicated between regions. Each region builds its own copy of a view from the entity events that are replicated to it, so identical views exist in every region. Each event carries its origin region, so an update handler can treat local and remote changes differently. A view built from a broker topic is regional or global depending on how the broker is configured.

== Changing a view

Some changes to a view are compatible with the data it already holds, such as changing the fields a query filters or sorts on, or adding a query. Others, such as changing the table's row type incompatibly, need the view to be rebuilt from its source. You rebuild a view by deploying it under a new component identifier next to the old one, letting it catch up, and then switching queries to it. A view built from a topic cannot be rebuilt from earlier messages, because the topic might not hold them any more; the new view starts from new messages. See xref:sdk:views.adoc#changing[How to modify a View].

== Choosing between a view and an entity read

[cols="1,2,2", options="header"]
|===
| | Entity read | View

| How you find the data
| By the entity ID
| By any attribute, across many instances

| Consistency
| Strongly consistent
| Eventually consistent

| Extra component
| None; a read command handler
| A view and its update handlers

| Use when
| You know the ID
| You search, list, sort, page or aggregate, read an entity's history, or combine several sources into one shape
|===

A view whose only query is "find by ID" should be an entity read instead. See xref:sdk:components/index.adoc#cs2-view-or-entity-read[View, or query the entity directly].

== Limits and trade-offs

* A view lags its sources. The lag is short in normal operation and longer during failures.
* A view built from a Key Value Entity does not see every intermediate state.
* A view built from a topic cannot be rebuilt from past messages.
* Streamed view updates do not guarantee delivery.
