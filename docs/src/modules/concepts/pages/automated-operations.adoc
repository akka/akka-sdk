= Automated operations

Automated operations are the operational tasks that Akka Automated Operations (AAO) performs on running services without operator action: scaling, rolling updates, runtime patching, rotation of security material and moves between environments. AAO runs the runtime in Serverless, Dedicated, your own cloud and your own Kubernetes. In the self-managed option, these tasks are yours.

== The problem

Running a distributed, stateful system by hand is where most of the effort and most of the risk lie. Capacity has to follow demand. New versions have to reach every instance without dropping traffic, even when they change how data is stored. Runtimes need security patches, and certificates expire. Each of these is routine, and each one done by hand is a chance for an outage.

AAO takes these tasks over. Operators state intent: where services run, how far they may scale and how data moves. The platform carries it out and keeps it true as conditions change.

== How it works

=== Supervision of deployed services

AAO supervises every service you deploy. It provisions capacity, places instances, replicates data, watches health and reacts to changes. The Akka operators in each region carry out this work: route management, elasticity, metadata synchronization, rolling deployments, certificate management, key rotation, and multi-region failover and recovery. See xref:deployment-model.adoc#_federation_plane_and_application_plane[Federation plane and application plane].

=== Elastic scaling

AAO adjusts the number of instances of each service to the traffic it receives. When load rises, it starts more instances; when load falls, it removes them. Each service scales between a minimum and a maximum number of instances that you set, and AAO also scales memory automatically. You do not pre-provision for peak load. As instances are added or removed, the runtime rebalances shards across them, so state follows the capacity. See xref:runtime.adoc[].

On Serverless, a service that is idle scales to zero, and the first request after an idle period starts an instance again. AAO handles that cold start, so an idle service still answers when traffic returns. In the other options, every service keeps at least one running instance.

=== No-downtime updates

A new version of a service is rolled out in waves, across the instances of each region and across regions. Some instances run the new version while others still run the old one, so some instances keep serving traffic throughout the rollout.

This holds when the new version changes the data model. Old and new versions run side by side during the rollout, and both read the same journal, so a new version must be able to read the events and state written by the old one. See xref:sdk:serialization.adoc[Serialization] for how to evolve event and state types.

=== Live patching

AAO applies runtime and infrastructure patches while services keep running: the JVM, the runtime and the platform underneath. A patch does not create a new version of your service and needs no redeployment or repackaging.

=== Certificate and key rotation

Traffic between services and between regions uses mutual TLS. AAO issues, rotates and renews the certificates and keys involved on an ongoing basis, without manual coordination and without interrupting service. See xref:security-and-identity.adoc[].

=== Moving between environments

AAO moves a running project between environments by replication: from one cloud to another, from Akka's cloud into your own account, or back to your own data centers. The same mechanism runs infrastructure upgrades. See xref:availability.adoc#_moving_between_environments[Moving between environments].

=== Observability and isolation

AAO collects logs, metrics and traces from every service, and lets you export them to the tools you already run; see xref:observability.adoc[]. It isolates projects from each other and enforces security policy on every workload; see xref:security-and-identity.adoc[].

== Guarantees

[cols="2,3,2", options="header"]
|===
| Situation | What AAO does | Precondition

| Traffic to a service rises or falls
| Instances are added or removed, and shards rebalance across them.
| The new count is within the service's minimum and maximum.

| A new version is deployed
| It is rolled out in waves, with healthy instances serving traffic throughout.
| The new version can read the data written by the old one.

| A runtime or security patch is released
| It is applied to running services without a redeployment.
| The service runs in an option Akka operates.

| A certificate or key approaches expiry
| It is rotated while the service keeps running.
| The service runs in an option Akka operates.
|===

== Limits and trade-offs

* Scaling to zero is available on Serverless only. In the other options, the minimum instance count is at least one.
* The first request to a Serverless service that has scaled to zero waits for an instance to start.
* Each service scales within the minimum and maximum you set. See xref:operations:services/instance-sizing.adoc[] for the limits and for sizing instances.
* During a rolling update, two versions run at once. Changes to event and state types must stay readable by both.
* In the self-managed option, none of these operations is automated. The runtime still clusters, rebalances and recovers.
