= Evaluation
:page-summary: Evaluation measures what an agent does against what good means for its task, in tests before it ships, on batches of recorded traffic, by replaying recorded interactions, and continuously on live traffic.

Evaluation measures what an agent does against what good means for its task. A model does not give the same reply twice, so an assertion on the exact reply does not work. Evaluation instead checks properties of the reply and of the tool calls behind it, and decides over many cases whether the agent is good enough.

The same agent is evaluated at several points in its life: in a test before it ships, against recorded traffic when something changes, and on live traffic while it runs. Each point uses the same ideas, cases, evaluators, judges and gates, and each records its results so that they can be compared. An eval is one of the five xref:concepts:controls.adoc[control types].

== Where evaluation runs

[cols="1,2,2", options="header"]
|===
| Where | What runs | Use it to

| In a test
| Eval cases run against the agent in the TestKit runtime, with stubbed tools and either a mocked or a real model.
| Check tool use and reply quality in every build, before the agent ships.

| By replay
| Recorded production interactions become eval cases that expect the agent to use its tools as production did.
| Hold an agent to what production did, before a prompt, model or tool change.

| On a batch of recorded traffic
| An experiment runs one dataset of recorded interactions against one target with one set of evaluators.
| Measure a change, or a new evaluator, over real traffic without touching production.

| On live traffic
| An evaluator component runs after each interaction of the agents it is bound to, in the background.
| Track quality, detect drift and keep a verdict for each interaction.

| As an adversarial test
| Eval cases whose user message is an attack, and whose evaluators state what a breached reply looks like.
| Check that known attacks fail, before release and after every change.
|===

A test or a replay runs in the build, and nothing leaves the test runtime. A batch runs against recorded traffic. A live evaluation runs in production and writes its verdict to the xref:concepts:evidence.adoc[ledger].

== How an evaluation works

An eval case is one input to the agent and the checks that apply to its result. The input is a command, such as a user message. The checks are evaluators. In a test, the runtime traces every model call and tool call of the case, and each evaluator reads the reply and that trace.

An evaluator is one check. It reads only the evidence it names and reports a result: pass, fail, or inconclusive when the evidence it needs is absent. A tool that was never called fails the check that expected the call, and makes the checks of its order and arguments inconclusive, so one missing call is reported once. An inconclusive result is never counted as a pass. A case whose outcome rests on a check that could not run is therefore visible, not silently passed.

Checks come in cost order. An exact check over the reply or the tool calls is free and reproducible. A regular expression decides clear cases. A judge, a model that scores the reply against a criterion stated as a sentence, catches what exact checks cannot, such as the same content written as fiction. A judge costs one model call per case and is not deterministic, so its results are gated on a rate, not on one run.

A gate decides over the results of a batch. By default every case must pass. With a real model, a gate usually requires a minimum pass rate instead, because one run of one case is not a stable measure. A case can run several times, and the gate then counts each attempt.

The report records whether the gate passed, the pass rate, every case result with its evidence, and the inconclusive results.

== Evaluating replies and actions

An eval case checks two things: what the agent said and what the agent did. The reply can be checked for content that must or must not appear, for its format, or by a judge. The actions are the tool calls, checked for which tools ran, in what order and with what arguments, and for the tokens, model calls and latency they cost.

An adversarial case reverses the stance. An eval case states what a good reply does. An adversarial case states what a breached reply looks like and requires its absence. An attack can enter through the user message, through a tool result that someone else wrote, or show only in what the agent did: a tool call that changed data outside the agent is a breach even when the reply looks correct. Keep quality suites and adversarial suites separate, because they gate differently: checks that must never fail need a full pass rate, while judged checks need a lower one.

== Evaluating live traffic

On live traffic, an xref:sdk:evaluators.adoc[evaluator] component is bound to agents in configuration, and the runtime triggers it for their interactions. The evaluator returns a verdict, optionally with a score, a label and attributes, and the runtime records it in the ledger with the evaluator's control id. A durable evaluator runs in several steps and resumes after a restart, for evaluations that call several judges or wait for a person.

Because a live evaluator runs after the interaction, it cannot change what the agent did. When the verdict must change the outcome, run the check inline as a guardrail. See xref:concepts:controls.adoc#guardrails[Guardrails].

Live evaluators usually call a model, so each evaluation has a cost. A sampling ratio evaluates a share of the interactions.

== Evaluating models

The same ideas apply to models. Before a trained model is promoted, it is evaluated against an evaluation dataset with a grader, and an evaluation gate decides whether it does the task as well as the model it replaces. A score belongs to one evaluation of one model against one dataset with one grader, so a model can be evaluated many times. See xref:optimize:concepts.adoc[Training concepts].

A gate turns many results into one decision. A specification's conformance verdict is `READY_TO_SHIP` or `NOT_READY`. A TestKit gate passes or fails the batch.

== Guarantees

[cols="1,2,2", options="header"]
|===
| Situation | What Akka does | Precondition

| The evidence an evaluator needs is absent
| The result is inconclusive and never counted as a pass.
| None.

| A judge cannot answer
| The result is a failure with its reason, and it counts against the pass rate.
| The evaluation runs in the TestKit.

| A live evaluator throws
| The runtime logs the exception and records a failed evaluation.
| None.

| A durable evaluator's node restarts
| The evaluation resumes from its last completed step.
| The evaluator extends `DurableEvaluator`.

| A test evaluation runs
| No model call or tool call leaves the test runtime unless the test uses a real model.
| Tools are stubbed.
|===

== Limits and trade-offs

* A live evaluator cannot change the interaction it judges.
* A judge is not deterministic. A single judged result is not a stable measure; gate on a rate.
* A sampling ratio lowers the cost of live evaluation and the number of interactions with a verdict.
* An agent that streams its reply sends it before any check on the reply completes.
* A replayed case can only hold the agent to the fields its recording carries.
