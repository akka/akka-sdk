Serving a model means running an open-weight or trained checkpoint on accelerators in your project and exposing it on an address that OpenAI-compatible clients call. A client reaches a served model by its served name, the name it sends in the `model` field of a request.

A hosted model API fixes the price per token, the hardware and the location of your data. Running a model yourself changes all three, and it adds work that a hosted API hides: claiming hardware, choosing an engine, pinning the exact weights, putting the model on an address and deciding who may call it. This page explains how Akka divides that work into resources that you declare, and how a served model fits into the loop described in xref:concepts:models.adoc[].

== How it works

=== Three resources

You describe what to run in a model descriptor, a YAML file that declares three kinds of resource:

[cols="1,3", options="header"]
|===
| Resource
| What it declares

| `AcceleratorAllocation`
| A number of whole devices that your project claims from one of the region's accelerator pools.

| `Model`
| One checkpoint, the engine that serves it, and the device of an allocation that it runs on.

| `ModelEndpoint`
| The models that one endpoint serves, and the secret that holds its API keys.
|===

Applying a descriptor writes these in dependency order, allocations, then models, then endpoints, so nothing refers to a resource that does not exist yet. Deleting by descriptor removes them in the reverse order. A descriptor never holds a secret or a route: credentials live in project secrets that the descriptor names, and a project route puts an endpoint on a hostname.

=== Accelerator pools and allocations

Every region that can serve models declares pools of accelerator devices. A pool is inventory: you do not create one, you claim devices from it. The kind of device a pool holds, its product and any partition profile, is its accelerator class. A pool name is a regional identifier only, so two regions can name the same hardware differently. Compare the product and profile when you compare hardware across regions.

An allocation claims whole devices from one pool for your project. The region decides how many devices it admits, and the allocation is ready when every device it claims is bound. A model is placed on a device of an allocation, never on a pool, so an allocation exists before any model can run.

Several models can share one device. A model names an allocation entry and the index of a device in it, and models that name the same entry and index share the physical device. Each one bounds its share of the device memory.

=== Models and engines

A model is one checkpoint served by an engine on a device. The model names:

* the checkpoint, pinned to a full commit hash so the weights cannot change under a running model,
* the engine and its settings, such as the data type, the quantization method and the cache type,
* the serving envelope: the context length, the number of concurrent requests and the resources of the engine container,
* the parser for tool calls, when clients call tools through the model.

A model generates text by default, and it can serve embeddings instead. The weights can be cached across restarts, so a restart does not download them again. A gated checkpoint needs a token, held in a project secret.

=== Adapters

An adapter is a small set of weights, trained for one task, that changes the behavior of a base model. A LoRA adapter is served next to its base model and addressed by its own name, so one base model on one device can answer for several specialized tasks. Adapters come from a model hub or from object storage in your project, and a fetch from storage fails when the weights do not match their declared digest. The set of adapters a model serves is fixed in its declaration, and changing it restarts the engine.

Adapters are how a model trained by the trainer reaches traffic. See xref:concepts:model-training.adoc[].

=== Served names and endpoints

A served name is a name that a client can send in the `model` field of a request. Each model has one, and each adapter adds another. A served name is unique across the project, and the region refuses a duplicate.

A model endpoint serves a set of models behind one address. The unit is the endpoint, not the model: a client chooses between the endpoint's models with the `model` field, so one base URL covers every served name the endpoint lists. A request for a name that the endpoint does not serve returns not found.

The served name also appears in the `model` field of the response body. Spend is priced per served name, read from that field. See xref:concepts:spend.adoc[].

=== Reaching a served model

An endpoint is reachable inside the project only. A project route puts it on a hostname, and Akka provisions a TLS certificate for the hostname. Any OpenAI-compatible client, including an Akka agent, calls it with a base URL and an API key.

An endpoint names a secret that holds its API keys, one key for each client, so one client's key can be revoked without disturbing the others. The endpoint refuses every request until the secret holds a key, so a new endpoint is never silently open.

A served model is reachable on its own hostname whether or not any routing rule names it. To put it in the request path of your agents, register it as a destination with the gateway proxy, and route a use case to it. A new model moves in by shadow and canary traffic under a routing policy. See xref:concepts:model-routing.adoc#_routing_policies_and_staged_traffic[Routing policies and staged traffic].

== Guarantees

[cols="2,3,2", options="header"]
|===
| Failure or situation
| What Akka does
| Precondition

| A checkpoint is named by a branch or a tag
| The region refuses the model, because a branch or tag can change under a running model.
| None.

| Adapter weights fetched from storage do not match their digest
| The fetch fails and the adapter is not served.
| The adapter comes from object storage.

| A served name is declared twice in a project
| The region refuses the duplicate.
| None.

| A request reaches an endpoint with no key
| The endpoint refuses it.
| None.

| A model is not ready
| Its status names the reason, such as weights still downloading or a device not yet bound.
| None.
|===

== Choosing between a hosted provider and a served model

[cols="1,2,2", options="header"]
|===
| Attribute
| Hosted provider
| Served model

| What you pay for
| Tokens, at the provider's price
| Accelerator capacity that your project allocates

| Models available
| The provider's catalog
| Open-weight checkpoints and models you train

| Where requests and data go
| The provider's infrastructure
| Accelerators in your project's region

| Use when
| Broad capability, or traffic too uneven to keep hardware busy
| A narrow task at steady volume, a trained model, or data that must stay in your region
|===

== Limits and trade-offs

* A model runs one replica. Serving more traffic for a task means declaring more models on more devices, and routing between them.
* Models come from a model hub, and the engine is vLLM.
* A project can serve at most 64 endpoints.
* The set of adapters on a model is fixed. Adding or removing one restarts the engine.
* The region checks that a tool-call parser exists, not that it matches the model. A wrong parser returns tool calls as plain text.
* Allocated devices are held whether or not traffic arrives, so a served model costs capacity when it is idle.
