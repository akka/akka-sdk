Coordination patterns are the ways several agents divide and share work: sequential, delegative, collaborative and emergent. Each pattern answers the same questions differently: which agent is active, how much runs in parallel, and what context each agent sees. A supervisor applies the pattern; xref:ai-orchestration-patterns.adoc[] explains the supervisor and when several agents are worth their cost.

== How it works

Four patterns cover the design space. Each has its own view of how context is scoped and flows between agents, a corresponding single-agent approach, and an analogy to an established concurrency model. They are conceptual tools, and real systems often blend them.

[cols="1,2,2,2", options="header"]
|===
| Pattern | Also known as | With a Workflow supervisor | With an Autonomous Agent

| Sequential
| Pipeline, relay, handoff
| Steps call agents in a fixed order
| Handoff capability

| Delegative
| Fan-out and fan-in, concurrent, magentic (dynamic planning)
| A step calls agents concurrently, or starts child workflows
| Delegation capability

| Collaborative
| Team, group chat, shared session, moderation
| Agents share a session under a planning workflow
| Team leadership and moderation capabilities

| Emergent
| Swarm, blackboard
| Not typical
| Built on team leadership with a shared data space
|===

=== Sequential

Control passes from agent to agent, and one agent is active at a time. Context accumulates or is transformed as it moves along the chain.

[cols="1,3", options="header"]
|===
| Aspect | Description

| Group | Relay: passing along a chain.
| Single-agent counterpart | An agent with a plan, running steps in order.
| Concurrency analogy | Continuations. Each agent picks up where the previous one stopped.
| Parallelism | None. One agent is active at a time.
| Context flow | Forward. Each agent receives context from the previous stage, accumulated, summarized or transformed, adds its contribution and passes it on.
|===

This is the simplest and most coherent pattern: one thread of reasoning runs throughout. The trade-off is path dependency. Early decisions constrain later ones, and errors compound rather than correct. Order matters: research then plan gives a different result from plan then research. Real processes are often graphs rather than chains, which is where sequential composes with delegative.

*Fixed pipeline.* When the order is known at development time, a workflow calls the agents one after another and passes each output to the next agent's input.

image::ai_orch_sequential.jpg["Sequential orchestration: a workflow calls agents in a fixed order",width=720]

A fixed pipeline suits multi-step processes with clear linear dependencies that do not change between runs, steps that cannot run concurrently, and data transformation pipelines, though if the work is only data transformation, agents and models may not be needed. Avoid it when steps can run in parallel without downstream dependencies, when you might branch or short-circuit based on the results of single steps, or when the interaction between agents is collaboration rather than handing work along. The xref:getting-started:planner-agent/team.adoc[agent team tutorial] shows a workflow with fixed steps that calls agents in sequence.

*Handoff.* When the plan is not known until the input arrives, an agent defers the work to whichever agent fits it. Choosing which agents take part is part of the planning.

image::ai_orch_handoff.jpg["Handoff orchestration: work moves to the agent best suited to it",width=720]

An Autonomous Agent implements handoff as a capability. The agent declares the peers it can hand off to, and the runtime offers the model a handoff tool. When the model hands off, ownership of the task moves to the next agent and the first agent steps back. The durability, retries and record come from the runtime, not from agent code. The `support` sample in the {sample-base-url}/autonomous-agent-playground[autonomous agent playground, window="new"] shows a triage agent that classifies a customer request and hands off to a billing or technical specialist.

With request-based agents, a workflow reaches the same outcome by calling a planning agent that chooses the next worker. The planning agent asks the model, through a structured response, which agent best suits the request, and the workflow calls that agent. Tool calls, for example over MCP, add deterministic logic to the choice when the model's judgment alone is not predictable enough. If the worker agents themselves decided whether to handle an input, they could not be recomposed for any other purpose. This plan-and-execute loop can be combined with any of the other patterns.

*Example:* A triage agent receives a customer request, decides its category and hands control to the right specialist, which then owns the interaction.

=== Delegative

A coordinator assigns subtasks to workers. Workers run in isolated contexts, and their results come back to the coordinator for synthesis.

[cols="1,3", options="header"]
|===
| Aspect | Description

| Group | Hierarchy: a coordinator and its workers.
| Single-agent counterpart | An agent with skills, loading focused capabilities as needed.
| Concurrency analogy | Fork and join, or futures. The coordinator fans out work and collects results.
| Parallelism | High. Subtasks can run at the same time.
| Context flow | Partitioned. Each worker sees only its slice and is isolated from the other workers. The coordinator sees the original task and the results, but not each worker's reasoning.
|===

Context isolation is the defining feature. Each worker can go deep on its subproblem without distraction or influence from the others. Isolation also means no cross-pollination, so coherence depends on the coordinator, which must do well at both decomposition and synthesis. In competitive delegation, the coordinator gives the same task to several workers and selects the best result; at large scale, with many agents and statistical selection, this blurs into the emergent pattern.

Use delegation when a task decomposes into distinct subtasks that benefit from focused contexts, when you need independent perspectives, when parallel execution reduces latency, or when you want broad exploration with many independent attempts.

*Concurrent workers.* A workflow step starts several agents at once and collects their results before the next step. The workflow decides which agents are needed, and the runtime provisions them; agents do not start sub-agents of their own.

image::ai_arch_concurrent.jpg["Concurrent orchestration: a workflow runs agents in parallel and collects their results",width=720]

For larger work, a parent workflow starts child workflows. Each child performs a multi-step task and delivers its result to the parent as a message. The parent pauses while it waits, stores the results in its state, and moves to its next step when it has what it needs. The runtime handles the distributed state, the long-running timers and the recovery of each workflow. When the coordinator is an Autonomous Agent, the delegation capability configured for parallel workers does the same: the model picks which workers to start, and the runtime runs them concurrently and gathers their results into the coordinator's context. See xref:sdk:workflows.adoc[Workflows] for concurrent steps.

*Dynamic planning (magentic).* For open-ended problems without a predetermined plan, a model creates the plan, decides the next step, evaluates the results and decides when the goal is met. Agents in this pattern often have access to tools.

image::ai_orch_magentic.jpg["Magentic orchestration: a model plans and directs the workers",width=720]

Either supervisor works. With a workflow supervisor, the model influences what happens, and the workflow makes sure it happens reliably, with durable steps and retries. With an Autonomous Agent coordinator that delegates, the model picks the next worker and the runtime persists the task, retries failures and bounds the number of iterations. When the supervisor coordinates everything and agents stay small, the individual patterns matter less: to change how agents are used, you change the planning agent, a little workflow logic or the coordinator's declaration, not the agents. The xref:getting-started:planner-agent/dynamic-team.adoc[planner agent tutorial] shows an Autonomous Agent coordinator that delegates to worker agents.

*Example:* A research coordinator delegates fact-gathering to a researcher and trend analysis to an analyst. Both work in parallel with isolated contexts, and the coordinator combines their findings into a brief.

=== Collaborative

Peer agents share context and communicate as they work on a common problem.

[cols="1,3", options="header"]
|===
| Aspect | Description

| Group | Team: cooperation between peers.
| Single-agent counterpart | An agent with internal debate or chain-of-thought verification.
| Concurrency analogy | The actor model. Independent agents exchange messages.
| Parallelism | Medium. Agents work at the same time, limited by coordination.
| Context flow | Exchanged. Agents send messages that shape each other's reasoning. Each agent keeps its own context, influenced by what it receives, more like a conversation than a shared view.
|===

The strength of this pattern is mutual awareness. Agents build on, question and correct each other, and debate can surface better answers than any one agent finds. Shared context also enables groupthink: agents converge too early, reinforce each other's biases, or defer to whichever agent speaks first or most confidently. The more interdependent the collaboration, the more it behaves like a single agent.

Use collaboration when subtasks are interdependent and agents need to see each other's work, when quality benefits from debate or review between peers, or when different expertise must be integrated as the work happens rather than combined afterward.

*Shared sessions.* This pattern is often called group chat, where a chat manager coordinates agents in a shared discussion. The name can mislead: the general form is a shared session, in which several agents have different levels of access to a common conversation history. Some agents can only read the history, some can only write to it, and some do both. A shared session can be applied to any of the patterns on this page.

image::ai_orch_chat.jpg["Group chat orchestration: agents work in a shared session",width=720]

In a typical example, a parent workflow calls a planner agent, which asks a model for an execution plan and returns it as structured data. The workflow follows the plan and delegates to agents and child workflows, and all of them use one shared session when they build context for the model. A caller joins an agent to a session through the `inSession` option of the component client. The xref:getting-started:ask-akka-agent/index.adoc[Ask Akka agent tutorial] and its {sample-base-url}/ask-akka-agent[sample, window="new"] use explicit sessions in this way.

Shared sessions suit collaboration between agents, workflows and child workflows, and quality control that checks the session history. Avoid them when a sequential pipeline is enough, when conversations can grow without an upper limit or very many sessions start in a short time, and when there is no objective way to decide that a conversation is complete.

*Teams and moderation.* An Autonomous Agent that leads a team shares a task list with its members, and members message each other directly. Moderation is a more structured form: members still share context, but a moderator decides who speaks when, sees the full transcript and decides when the conversation ends. It trades some autonomy for a predictable cadence. Use it when the value comes from a shaped exchange, such as a peer review, a negotiation or a panel discussion, rather than from members claiming and completing work in parallel. See xref:sdk:autonomous-agents/capabilities.adoc[].

*Example:* A team lead splits a project into tasks. Developer agents claim tasks from the shared list, work on them independently and message peers when they need to coordinate. The lead monitors progress and disbands the team when the work is done.

=== Emergent

Many agents work in parallel with little individual context, following simple rules. Each agent changes a shared environment, and the environment influences what the other agents do. Complex behavior emerges from these indirect interactions.

[cols="1,3", options="header"]
|===
| Aspect | Description

| Group | Swarm: independent action, collective effect.
| Single-agent counterpart | An agent with sampling diversity, such as several completions with the best one chosen.
| Concurrency analogy | Tuple spaces and blackboard systems. Agents interact through shared data rather than direct communication.
| Parallelism | High. Agents work independently.
| Context flow | Indirect. Agents see the environment, not each other, and influence each other only through what they leave in the shared state.
|===

This pattern is for scale and exploration, and it is the hardest to make work. Behavior is statistical, the sum of many simple actions. That makes the system resilient, with no single point of failure, and also unpredictable. Selection turns many independent contributions into a useful result: emergent selection reinforces good contributions as other agents build on them, and external selection brings in something outside the swarm to evaluate and curate. In practice you may want both.

Use it for large problems with many similar agents and tolerance for probabilistic outcomes, for broad exploration, and to avoid converging early on one solution. There is no dedicated capability for it. It is usually built on team leadership as a blackboard system, in which the shared data space replaces direct messaging. The blackboard can be the team's task list, or an entity or view offered to the agents as a tool.

*Example:* A brainstorm team adds ideas to a shared board, each agent independently. A lead curates the board, and the result emerges from accumulation and refinement rather than explicit coordination.

== Decomposing work into agents

The intuitive split is by type of work: one agent plans, another implements, a third reviews. Often each of these agents then needs most of the same context, so the separation is artificial and adds coordination cost. Boundaries work better when they follow context rather than the structure of the problem: where focus narrows to a different task, where isolation prevents concerns from contaminating each other, or where independence gives more diverse results than shared attention.

For the choice between a tool, a task and a separate agent for a piece of work, see xref:sdk:autonomous-agents/coordination.adoc#_choosing_the_unit_of_decomposition[Choosing the unit of decomposition].

== Composing patterns

The patterns compose at different levels:

* *A sequential pipeline with delegative stages.* A document moves through research, analysis, writing and review. The analysis stage fans out to workers that examine different aspects in parallel, then combines their results before passing the document on.
* *A delegative coordinator with collaborative teams.* A coordinator delegates to specialist teams. Inside each team, agents debate approaches, catch errors and build on each other's work. The coordinator sees only each team's final output.
* *A collaborative debate with delegative research.* Agents debate an approach, and when they need evidence they delegate fact-gathering to workers. The debate resumes with the findings. This suits a decision that needs research that can run in parallel.
* *A delegative coordinator with sequential workers.* A coordinator fans out to workers, and each worker runs its own pipeline, such as research, draft and self-review, before returning a result.

== Guarantees

A pattern adds no guarantees of its own. Every pattern runs under a supervisor, a Workflow or an Autonomous Agent, and the supervisor gives the retries, recovery and iteration limits described in xref:ai-orchestration-patterns.adoc#_guarantees[Multi-agent coordination].

== Limits and trade-offs

* Sequential coordination is path dependent: early decisions constrain later ones, and errors compound.
* In delegation, coherence depends entirely on the coordinator.
* Collaboration risks groupthink and early convergence.
* Shared sessions that grow without an upper limit put load on the model and on storage.
* Emergent behavior is statistical and needs a selection step to produce a usable result.
