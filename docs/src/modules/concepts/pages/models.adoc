A model call is an inference: the execution of a trained model on an input to produce an output. Code performs inference when it sends a prompt to a large language model, requests an embedding, or classifies a piece of text. An agentic system makes many inference calls for each request it serves, and how those calls behave decides the latency, the cost and the reliability of the system.

This page explains what makes an inference call different from a function call, why the count of calls matters, and the loop that Akka runs over model traffic: observe and grade, route, train, serve.

== How an inference call differs from a function call

A function call is deterministic. It receives arguments, runs a fixed sequence of instructions, and returns a value of a declared type. The same arguments produce the same value.

An inference call has the following properties:

* _The result varies._ The same input can produce a different output on the next call.
* _The result is untyped at the language level._ A model returns text, and the calling code parses and validates it. See xref:sdk:agents/structured.adoc[Structured responses].
* _Latency can be measured in hundreds of milliseconds to minutes._ Communicating with a model is a streaming operation that can take a long time to finish, and long-running streams bring their own infrastructure and development challenges.
* _Providers bill per token_, so the cost of a call depends on the size of the input, the context and the output.

These properties decide what the surrounding code has to do. It validates the response before using it. It handles a malformed or failed response as a normal path, described in xref:sdk:agents/failures.adoc[Failure handling]. It sets a timeout and a token budget for each call, and it defines the behavior when a model is unavailable and the failover rules when exceptions occur.

These properties apply to any use of a model, whether the model ranks search results or scores transactions for fraud.

== Inference in agentic systems

An agent uses a model to decide what to do next. Selecting a tool, judging whether a task is complete, and producing an answer are inference calls. See xref:concepts:ai-agents.adoc[] for the concept and xref:sdk:agents.adoc[Agents] for the component.

One request to an agentic system typically produces several inference calls. An agent that plans, calls tools and checks its own output makes several calls in sequence. Systems that run agents in parallel or pass work between them increase the count further. See xref:sdk:agents/orchestrating.adoc[Multi-agent orchestration].

The number of calls per request shapes four characteristics of the system:

* _Sequential calls add their latencies_, so response time follows the depth of the call chain.
* _Cost scales with the number of calls._ A request that expands into twenty model calls costs about twenty times a single call.
* _The chance that at least one call fails grows with the number of calls_, so retry and fallback behavior applies to every call.
* _Agents in the same system share provider rate limits and serving capacity._ A quota defined per application can run out of provider quota much sooner than expected.

When further inference calls judge the first ones, the number of calls grows faster still.

== How it works

Most agent traffic repeats a narrow task whose result can be checked. Such a task does not need the largest model available. Akka treats the model traffic of your agents as one loop with four parts, and each part feeds the next.

. *Observe and grade.* Every exchange that passes through the gateway is captured, and the outputs are graded. A targeting step ranks the use cases where a smaller model would pay off. See xref:concepts:capture-and-grading.adoc[].
. *Route.* A router in front of your models decides, for each request, which model serves it, from rules you declare or from the meaning of the request. See xref:concepts:model-routing.adoc[].
. *Train.* The trainer specializes an open-weight base model for a use case, on data drawn from the captured traffic, and evaluates it against a baseline. See xref:concepts:model-training.adoc[].
. *Serve.* Akka runs open-weight and trained models on accelerators in your project and exposes them to OpenAI-compatible clients. A promoted model takes traffic in stages, and grading continues after it does. See xref:concepts:model-serving.adoc[].

Every recorded exchange is also priced, so the loop reports what the traffic costs and what a change saved. See xref:concepts:spend.adoc[].

The parts work on their own as well. You can route traffic between hosted providers without serving a model, serve a model and call it directly without routing, or observe traffic before you route any of it.

=== Frontier models as fallback and as teacher

A frontier model is a large, general-purpose model, usually reached through a provider's API. It keeps two roles in the loop.

* _Fallback._ A routing ruleset names a default destination for traffic that no rule claims, and a rule that defers to a routing classifier names what happens when the classifier fails. The frontier model is the usual answer to both, so a request that a smaller model is not trusted with still gets served.
* _Teacher._ The frontier model's recorded answers to a use case are training examples for the smaller model. Supervised fine-tuning learns from those answers, and graders built from them score the smaller model's output.

=== What bounds the loop

The loop changes which model answers your users, so it acts only within limits that people set:

* The _improvement policy_ in a system's specification states what the system optimizes toward and how far it may tune itself. Routing changes, training and promotion stay inside it. See xref:concepts:specification.adoc[].
* Targeting applies an eligibility filter declared by your organization. Policy can remove a use case from consideration and never adds one.
* A routing policy can be vetoed for a use case, which refuses any routing change until the veto is lifted, and rolled back to its previous version.
* A new model is promoted only when it meets the promotion rule, and the comparison that justified it is saved. See xref:concepts:model-training.adoc#_promotion[Promotion].

== Guarantees

[cols="2,3,2", options="header"]
|===
| Failure or situation
| What Akka does
| Precondition

| A rule defers to a routing classifier and the classifier fails
| The rule's `onFailure` setting applies, for example the ruleset's default destination.
| The rule sets `onFailure`.

| A request matches no rule and no use case
| The ruleset's default destination serves it.
| A ruleset is applied.

| A trained model's quality falls on live traffic
| The model is retrained, and traffic returns to the previous model if the new one slips below the baseline.
| The use case is graded.

| A model call is made through the gateway
| The exchange is captured and priced from the catalog version in force.
| The traffic passes through the gateway, and the served name has a price.
|===

== Choosing between routed and direct model calls

[cols="1,2,2", options="header"]
|===
| Attribute
| Direct call to a provider
| Call through the gateway

| Where the model is chosen
| In agent configuration
| In rulesets and routing policies, outside agent code

| Changing the model
| A configuration change and a redeploy
| A ruleset or policy change, no redeploy

| Capture, grading and spend
| Not recorded by the gateway
| Every exchange is captured and priced

| Training a smaller model
| No training data from this traffic
| Captured traffic feeds training

| Use when
| A prototype, or a single model with no plan to change it
| Production traffic you want to observe, route or move to a smaller model
|===

== Limits and trade-offs

* Only traffic that passes through the gateway is captured, graded, routed and priced. A call made directly to a provider is outside the loop.
* A use case is a candidate for a smaller model only when its outputs can be graded. Open-ended output with no grader stays on the model that serves it now.
* A trained model is specialized: it is promoted for one use case and is not a replacement for a general-purpose model.
* A served model runs on accelerators that your project allocates, so serving trades a per-token price for a capacity cost.
