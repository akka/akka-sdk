An exit condition is a binary, machine-checkable statement of when a feature or a system is done. An auditor checks each exit condition, and the conformance verdict says whether every condition that applies has passed. Together they hold the code to its specification, and they make done something the system checks rather than a judgment call.

== The problem

"Done" usually means that someone looked at the change and was satisfied. That works when a person writes every line. When an AI coding assistant writes the code, the same review has to cover far more output, and a check that only looks like it covers a requirement can pass while the requirement is broken. Done has to be stated precisely, checked by something that cannot be talked out of its result, and recorded so the next owner can see what was verified.

== How it works

=== Three layers of done

Done is split into three layers, each with its own owner.

[cols="1,3,2",options="header"]
|===
| Layer | What it is | Who writes it

| Definition of Done
| The statement of done in business terms, such as "greetings are personalized" or "the service survives the loss of a node".
| The project owner and the organization

| Exit condition
| The technical form of one Definition of Done item: a binary pass predicate over something the system can observe.
| Derived by the plugin, refined by the developer

| Auditor
| The check that evaluates an exit condition and returns a result.
| Akka ships a built-in set; projects and the organization write the rest
|===

Results roll up in the other direction. An auditor's result sets the state of its exit condition, and the states roll up into a status for each Definition-of-Done type. You see progress in business terms, such as "Functional: 2 of 3 met", while the checks run on precise conditions underneath.

An exit condition resolves to pass or fail, with nothing in between. A requirement that cannot be stated as a binary predicate over an observable surface is not yet an exit condition. When you give feedback, the plugin creates an exit condition only if it can state a predicate that is false exactly when the requirement is violated. Otherwise it asks you a question instead of inventing a check. This is the falsifiability gate.

=== Definition-of-Done types

Every exit condition belongs to one fixed, versioned Definition-of-Done type, in three tiers:

Product:: Does the software work? Functional, Data Integrity, Reliability, Performance, Security and Compliance, Operability, and Experience.
Project:: Is the codebase healthy and standards-compliant? Documentation and Training, Repository Hygiene, Pipeline and Scanning, Code and Test Health, and Environment and Dependencies.
Process:: Did the AI build stay honest and efficient? Process Integrity and Build Efficiency.

The types are closed. An organization extends done by adding conditions within a type, not by adding types. The xref:reference:specify/catalog/index.adoc[exit condition catalog] lists candidate conditions for every type.

A prohibition is an exit condition that states something that must never become true, such as a committed secret or an unpinned dependency. A completion starts undecided and passes when its auditor passes. A prohibition holds while the banned thing is absent and fails the moment it appears. A prohibition with no auditor fails, because nothing is watching for the thing that must never happen, and a person's sign-off cannot clear it.

=== Auditors

An auditor is one of three kinds, set by where its check can run:

[cols="1,2,2",options="header"]
|===
| Kind | Where the check runs | How it resolves

| Introspective
| In the project's own tree: a compiler, a test runner, a linter or a prose linter. Either a built-in check or a command written for the project's ecosystem.
| Passes or fails locally

| Provisioned
| Through a harness asset wired to a system outside the project, such as a CI workflow or a scanner.
| Passes when the asset is present, current and enforcing

| Delegated
| Only in an external system, or as a judgment the engine cannot make.
| Stays undecided until someone records a check attestation, then passes
|===

The plugin prefers a tool that already decides the question, such as a compiler or a scanner, over new logic. A command written for one project does not run until you approve its exact text, and a changed command asks again. A delegated check that nobody attests stays undecided rather than passing, so the gap stays visible.

=== States, properties and staleness

An exit condition is always in one of three states:

`open`:: The auditor has not decided. The condition carries a reason: `needs-user-action` when a person on the project can move it forward, or `blocked-outside-project` when a required tool is missing or the policy names a requirement with no auditor mapped to it.
`green`:: The auditor ran and the condition passed.
`red`:: The auditor ran and the condition failed.

Three properties sit alongside the state:

Provenance:: Who guarantees the condition and who may change it: `akka-intrinsic` (guaranteed by the platform), `recommended-default` (from the default library), `corporate` (from the organization policy, locked) or `developer` (added for this feature).
Waiver:: An exit-condition waiver is a time-bound record, with the person who accepted it and a reason, that permits shipping while the condition is `red` or `open`. It does not change the state, and it stays visible.
Applicable:: Whether the condition applies to this project. An inapplicable condition stays visible but does not count.

When an auditor passes a condition, the time is recorded. If any file in the project changes after that, the condition is marked stale: it still shows `green`, but its auditor must run again before the project can ship.

=== Ship tiers

Every exit condition is declared at a ship tier, which says when it must pass:

* `author` conditions must pass in the developer's own loop, before any ship: compiling, unit tests, linting, secret scanning and the two process-integrity gates.
* `review` conditions must pass before the change is opened for team review: checks that run in minutes and may reach shared systems, such as static analysis, coverage thresholds and integration tests.
* `release` conditions must pass before the artifact reaches production: expensive or external checks, such as dynamic scans, security sign-offs and live-service probes.

An author-tier condition must be decidable on the developer's machine, so a condition that resolves only through an attestation belongs at a higher tier.

Tiers build on each other. `/akka:ship review` runs the author-tier and review-tier auditors, and `/akka:ship release` runs all three. The author tier is checked first; in enforced mode, a ship that fails it stops there, so you do not wait on a scan whose result cannot change the outcome.

=== The verdict and the conformance receipt

`/akka:conform` runs the auditors in scope and returns one of two verdicts:

`READY_TO_SHIP`:: Every applicable condition in scope is `green` and not stale, or covered by an effective exit-condition waiver.
`NOT_READY`:: Anything else. The manifest names each blocking condition with its state, its reason and any waiver.

`/akka:ship` reads the same verdict. When it passes, it runs the ship steps your organization declares for that target, such as opening a pull request or deploying. It then writes a conformance receipt: which conditions passed, which auditors ran, which stayed `open` and why, and which waivers applied. The receipt is what makes a build by an AI coding assistant auditable: whoever takes it over sees exactly what was verified and what remains.

=== The process-integrity gates

Two exit conditions are always on and cannot be removed. They make the checks police themselves.

The coverage gate:: Every material surface of the project must be covered. A surface is a code module found from build markers such as `pom.xml` or `package.json`, a harness the policy requires, or a documentable item the policy names. Add a web application and the gate fails until a check covers it. A surface that needs no coverage can be marked with a surface waiver, with a reason.
The adequacy review:: Every check must pass a current, adversarial review before the build advances. For each auditor, the review tries to construct an input where the check passes while its requirement is false. The review is keyed to the current set of checks, so a change to any check makes it run again. The engine guarantees that the review happened and covered every check; your approval of each new or changed check is what guarantees its depth.

=== Content governance

The same model applies to the prose a project generates, such as its documentation. Rules that can be decided mechanically, such as banned phrases, required terms and reading level, become introspective auditors that run a prose linter. Rules that need judgment, such as tone, become delegated checks: the AI coding assistant applies a rubric of single pass or fail questions, using a model from a different family than the one that wrote the text, and records a check attestation. A change to the text or to the rubric makes the attestation stale.

== Guarantees

[cols="2,3,2",options="header"]
|===
| Situation | What happens | Precondition

| A condition has not passed and has no effective waiver
| `/akka:ship` refuses and names the condition
| Enforced mode

| A file changes after a condition passed
| The condition is marked stale and its auditor must run again before shipping
| The file is part of the project tree

| A prohibition has no auditor
| The condition is `red`
| None

| A delegated check has no attestation
| The condition stays `open` and the ship is refused
| Enforced mode

| A check is added or changed
| The adequacy review runs again before the build advances
| The exit-condition set is active

| A new module appears with no check
| The coverage gate fails until a check covers it or a surface waiver is recorded
| The exit-condition set is active

| An exit-condition waiver expires
| The condition blocks the ship again in whatever state it is in
| None
|===

In à la carte mode the same states and verdicts are computed and reported, but `/akka:ship` proceeds and records an override.

== Limits and trade-offs

* Staleness is coarse: any change anywhere in the project makes every `green` condition stale.
* The adequacy review guarantees that every check was reviewed, not that every review was thorough.
* A delegated check is only as good as the evidence behind the attestation; the engine records the receipt, not the work.
* Local results are advisory. The organization's CI, running the same check against the same policy, is what stops a change from merging.
